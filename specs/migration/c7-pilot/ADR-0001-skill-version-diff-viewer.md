# ADR-0001: Skill Version Diff Viewer — UI 패턴 선택

## Status

Proposed (2026-04-07) — 구현 착수 전 최종 리뷰 필요

## Context

KonaI-Agent의 스킬(SKILL.md) 버전 이력 관리 기능에서, PM·기획자 등 **비개발자**가 v3 → v4 같은 두 버전 사이의 변경 사항을 빠르게 파악·검토할 수 있는 **diff 뷰어 UI**가 필요하다. 주 사용 시나리오:

- 어제 작성한 스킬을 오늘 누군가 수정했을 때 "어떤 부분이 어떻게 바뀌었는지" 리뷰
- 특정 버전으로 롤백 판단을 위한 사전 검토
- AI가 자동 생성·수정한 스킬의 변경 사항 감사(audit)

이는 **Agent가 생성한 artifact를 사용자가 수정 지시하는 edit flow**([[diff-review-patterns]])와는 별개의 review flow다.

### 제약

1. **대상 사용자가 비개발자**이므로 GitHub 스타일 코드 diff(`+`/`-` 접두사, `@@` hunk 헤더)는 시각적 노이즈가 크다.
2. **표시 공간이 두 가지**: 스킬 상세 화면의 우측 패널(400~500px)과 전체 확장 모달(800px+).
3. **콘텐츠가 한국어 자연어**이므로 단어 경계와 조사·어미 변화를 정확히 포착해야 한다.
4. **AI 요약**이 함께 제공되므로 요약 ↔ 원문 위치 연동이 가능해야 한다.
5. **렌더링 상태**(WYSIWYG)가 기본이어야 한다. 단, 마크다운 문법 자체의 변경도 놓치지 않아야 한다.

### 조사한 옵션

5개 서비스 심층 분석 결과는 [[version-diff-viewer-patterns]]를 참조. 요약:

| 서비스 | 강점 | 약점 |
|---|---|---|
| GitHub | 2단계 하이라이트, 접힘 | 코드 전용 메타 노출, 원문만 |
| Google Docs | WYSIWYG, 빨간펜 메타포 | diff 전용 뷰 부재, 접힘 없음 |
| Notion | 단순 렌더링 | 삭제/추가 구분 없음 |
| WordPress | Side-by-side, 2단계 단어 | HTML 태그 노출, 좁은 폭 취약 |
| Confluence | 렌더링 인라인, 자동 접힘 | 단어 수준 불균일, side-by-side 미지원 |

## Decision

**"Confluence + Google Docs 하이브리드"** 패턴을 채택한다. 세부 사양은 아래 4개 영역으로 분해한다.

### 1. 패널(400~500px) 뷰 — 기본 모드

**1-1. 색상 체계: 2단계 하이라이트 (GitHub/WordPress 방식)**

```
삭제: 연한 빨간 배경(#ffeef0) + 취소선
   └ 변경된 단어: 진한 빨간 배경(#fdb8c0)
추가: 연한 녹색 배경(#e6ffec)
   └ 변경된 단어: 진한 녹색 배경(#acf2bd)
```

**1-2. 비교 단위: 단어 수준(Word-level diff)**
- 줄 단위(line-level)는 코드에 최적화되어 있고 자연어에 부적합
- 한국어 특성상 문장 내 조사·어미 변경도 단어 단위로 포착

**1-3. 접두사·메타 제거**
- GitHub의 `+`/`-` 접두사 제거
- `@@` hunk 헤더 제거
- Google Docs/Confluence 방식의 "취소선 = 삭제, 색상 배경 = 추가" 사용

**1-4. 접힘/펼침 규칙**

| 규칙 | 값 | 근거 |
|---|---|---|
| 맥락 유지 줄 수 | 전후 2줄 | 좁은 패널에서 공간 효율 우선(GitHub의 3줄 대비) |
| 접힌 영역 텍스트 | `··· (변경 없음, N줄) ···` | Confluence 말줄임표 패턴 |
| 확장 방식 | 클릭 시 **전체 확장** | 좁은 패널에서 20줄 점진 확장(GitHub)은 과잉 복잡도 |
| 인접 변경 병합 | 두 변경 사이 ≤ 4줄이면 접지 않음 | 너무 짧은 접힘은 가독성 저하 |

### 2. 전체 확장 모달(800px+) — Side-by-Side 옵션

**2-1. 레이아웃**
- WordPress 방식의 좌우 병렬, 단 컬럼 헤더는 "삭제됨/추가됨" 대신 **"이전 (v2) / 이후 (v3)"** 사용
- 동기 스크롤 적용(Draftable 참고)
- 단어 수준 하이라이트는 패널 뷰와 동일

**2-2. Unified ↔ Side-by-Side 토글**
- 비개발자 친화 레이블: **"한 줄 보기 / 나란히 보기"** (Unified/Split 금지)
- 기본값: 한 줄 보기(패널 뷰 경험 연속성)
- 사용자 선택 기억(localStorage)

**2-3. 변경 간 이동 내비게이션**
- `↑ 이전 변경 / ↓ 다음 변경` 버튼(GitHub PR 리뷰 영감)
- 키보드 단축키: `J` / `K`

### 3. AI 요약 ↔ diff 연동 — 시장 공백 영역

5개 서비스 모두 제공하지 않는 차별화 포인트. 다음과 같이 구체화:

**3-1. 요약 → 원문 (앵커 스크롤)**

```
AI 요약 블록:
┌──────────────────────────────────────────┐
│ [추가] 빈 셀 처리 규칙 추가  ← 클릭 가능 │
│ [변경] 2단계를 차트 시각화로 수정        │
│ [추가] '분기 보고서' 트리거 추가         │
└──────────────────────────────────────────┘
         ↓ 클릭
원문 비교 영역:
  - 해당 변경 위치로 스무스 스크롤
  - 해당 변경 블록에 펄스 애니메이션(0.5초, 밝은 노랑 → 원래 색)
  - 접힌 영역 안에 있으면 자동 펼친 후 스크롤
```

**3-2. 원문 → 요약 (역방향 하이라이트)**

```
원문 변경 블록 hover 시:
  → AI 요약 블록의 대응 항목에 밑줄/볼드
  → 요약 블록이 스크롤 밖이면 상단 플로팅 배지로 표시
```

**3-3. 태그 색상 규칙**

| 요약 태그 | 태그 색상 | diff 배경색 | 의미 |
|---|---|---|---|
| [추가] | 녹색(#22863a) | 연녹색(#e6ffec) | 새 콘텐츠 추가 |
| [변경] | 주황(#e36209) | 연노랑(#fff8c5) | 기존 콘텐츠 수정 |
| [삭제] | 빨강(#cb2431) | 연빨강(#ffeef0) | 콘텐츠 삭제 |

[변경]은 삭제+추가의 복합이지만, 비개발자에게 "변경"이 더 직관적. diff에서는 내부적으로 삭제(빨강)+추가(녹색)로 표시하되 주황 좌측 보더로 "변경 사항" 추가 시그널링.

### 4. 마크다운 원문 vs 렌더링

**4-1. 기본값: 렌더링된(WYSIWYG) diff**
- `##`, `**`, `-` 등 마크다운 문법을 렌더링한 상태에서 변경 표시
- 비개발자가 "완성된 모습"을 보며 리뷰

**4-2. 토글: 마크다운 원문 diff**
- `[렌더링 보기 | 원문 보기]` 토글
- 고급 사용자용, 기본값은 렌더링 보기
- 마크다운 문법 자체 변경(`## → ###`) 확인 시 사용

**4-3. 렌더링 보기에서 문법 변경 배지**
- `## → ###` 같은 헤딩 레벨 변경은 렌더링 보기에서도 놓치지 않도록 **인라인 배지** 표시
- 예: `██ [H2→H3] ██ 데이터 분석 프로세스`
- Confluence "서식 변경 = 파란 하이라이트" 패턴에서 영감

## Consequences

### Positive

- **비개발자 친화성**: `+`/`-` 접두사·코드 메타 제거와 자연어 레이블로 PM·기획자 대상 직관성 확보.
- **정확성**: 단어 수준 2단계 하이라이트로 긴 단락에서도 정확한 변경 위치 파악 가능.
- **공간 효율**: 패널 뷰 접힘 규칙으로 400~500px 폭에서도 긴 스킬 문서 리뷰 가능.
- **차별화**: AI 요약 ↔ diff 양방향 연동은 경쟁 서비스에 없는 기능, 사용자 가치 크다.
- **장기 유지보수**: 일반 패턴(Vault) ↔ 결정(ADR) ↔ 구현(catalog) 3계층이 분리되어, 나중에 다른 컴포넌트가 같은 diff viewer를 재사용할 때 참조점 명확.

### Negative / Trade-offs

- **구현 복잡도**: 단어 수준 diff + 접힘 + 요약 연동은 순수 GitHub 스타일 대비 구현 비용 2~3배.
- **라이브러리 부재**: 한국어 단어 수준 diff + 마크다운 렌더링 동시 지원 OSS가 희박. 자체 구현 비중이 크다 (`diff-match-patch` + custom word boundary).
- **Side-by-side 드문 사용**: 전체 확장 모달에서만 제공되므로 UX 리소스 대비 사용 빈도 검증 필요. Phase 2 이후로 미룰 수 있음.
- **접근성**: 색상에 의존하는 diff는 색각 이상자에게 불친절 — 텍스트 레이블("삭제됨"/"추가됨") 보조 필수, WCAG AA 대비 확인.

### Neutral / Follow-up

- **테스트 시나리오**: 한국어 스킬 문서(500자, 2000자, 5000자) 각각에 대한 diff 렌더링 성능 측정 필요.
- **catalog 연결**: `specs/component-catalog.yaml`에 `skill_version_history`·`skill_diff_viewer` 컴포넌트 엔트리 추가 (별도 PR).
- **다국어**: 영어 스킬 문서는 word-level diff의 단어 경계 규칙이 다름(공백 기준) — i18n 분기 필요.

## Alternatives Considered

**A. GitHub 스타일 코드 diff 그대로 사용**
- 장점: 구현 간단, 기성 라이브러리(`react-diff-viewer`) 즉시 사용 가능
- 단점: `+`/`-` 접두사·줄 번호·hunk 헤더가 비개발자에게 시각 노이즈
- 기각 이유: 타겟 사용자가 비개발자이므로 이 노이즈는 핵심 UX 문제

**B. Google Docs 스타일 제안 모드만 사용**
- 장점: WYSIWYG 가장 직관적
- 단점: diff 전용 뷰 부재 → 긴 스킬 문서(500줄+) 리뷰 시 변경 위치 찾기 어려움, 접힘 기능 없음
- 기각 이유: 스킬 문서는 점점 길어지는 경향이라 접힘이 필수

**C. Notion 스타일 블록 하이라이트**
- 장점: 극단적 단순성
- 단점: 삭제/추가 구분 없음, 단어 수준 없음
- 기각 이유: "무엇이 바뀌었는지" 자체를 파악할 수 없어 리뷰 도구로서 가치 부족

**D. WordPress Side-by-Side를 기본값으로**
- 장점: "이전 vs 이후" 방향성 명확
- 단점: 좁은 패널(400~500px)에서 한국어 자연어 문장 줄바꿈으로 가독성 급락, HTML 태그 노출 학습 비용
- 기각 이유: 패널 뷰가 기본 사용 케이스인데 side-by-side는 좁은 폭 대응 어려움. 전체 확장 모달의 옵션으로만 제공.

## Implementation Notes

1. **Phase 1 (MVP)**: 패널 뷰 Unified 인라인 + 단어 수준 하이라이트 + 접힘/펼침 + AI 요약 앵커 스크롤
2. **Phase 2**: 전체 확장 모달 + Side-by-side 토글 + 변경 간 이동 네비게이션
3. **Phase 3**: 원문 ↔ 요약 역방향 연동 + 렌더링/원문 토글 + 문법 변경 배지
4. **Phase 4**: 접근성 개선(색각 이상자 모드, 스크린 리더 레이블, 키보드 내비게이션)

관련 컴포넌트 catalog 엔트리는 구현 착수 시 함께 생성.
