> **문서 목적**: AI 에이전트가 리서치 결과를 분석할 때 서비스의 맥락을 파악하기 위한 컨텍스트 앵커.
> 내부 개발팀의 설계 기준 문서로도 활용한다.
>
> **최종 수정**: 2026-03-23

## 1. 서비스 정의

**KonaI-Agent는 엔터프라이즈 현업 사용자가 AI 에이전트와 협업하여 데이터 분석, 문서 생성, 의사결정을 수행하는 에이전트 기반 업무 플랫폼이다.**

기존 엔터프라이즈 BI 도구는 대시보드를 "보여주는" 데 그친다. KonaI-Agent는 대시보드에서 발견한 인사이트를 기반으로 에이전트가 후속 액션(분석 리포트 작성, PPT 생성, 데이터 드릴다운)까지 수행하는 **관찰 → 해석 → 행동** 루프를 하나의 인터페이스에서 완결한다.

### 핵심 가치 제안

- **대화형 데이터 접근**: 자연어로 엔터프라이즈 데이터를 질의하고, 에이전트가 맥락을 이해한 채 응답한다.
- **멀티스텝 업무 자동화**: PPT 생성, 영업 분석 등 복수의 단계를 거치는 업무를 에이전트가 오케스트레이션하되, 핵심 분기점에서 사용자가 직접 판단한다(HITL).
- **엔터프라이즈 거버넌스**: 역할 기반 접근 제어(RBAC), 3계층 데이터 보안(테이블·행·컬럼)을 통해 기업 환경의 컴플라이언스 요구사항을 충족한다. 감사 로그는 규제 산업 고객 대응 시 Phase 2에서 추가한다. *[05-admin-ia.md 9절 후순위 항목 참조]*

### 차별점

일반적인 AI 챗봇이 "1회성 질의-응답"에 머무르는 반면, KonaI-Agent는 복수의 에이전트가 협업하는 멀티에이전트 오케스트레이션과, 사용자 승인이 워크플로우에 내장된 HITL 패턴을 통해 **신뢰할 수 있는 자동화**를 구현한다. 에이전트의 중간 결과물(아티팩트)을 채팅 옆 별도 패널에서 실시간 확인·편집할 수 있어, 에이전트가 작업하는 과정 자체가 투명하다.

### GNB 구조 (확정)

```
홈/대시보드 | AI 채팅 | 스킬 | 데이터 | 관리자
```

상단 네비게이션을 채택한다. Chat 화면이 4-column 레이아웃(좌측 사이드바 + 채팅 + 아티팩트 패널 + 우측 사이드바)으로 구성되어 있어 좌측 GNB를 추가하면 UI가 과도하게 복잡해진다. 리서치 대상 15개 서비스 중 13개가 좌측 사이드바를 사용하지만, 이는 1-column 기본 레이아웃(Claude, ChatGPT)이기 때문에 가능한 구조다. KonaI-Agent는 채팅 화면 자체가 멀티 컬럼이므로 상단 배치가 적합하다. *[근거: 06-gnb.md — 리서치 다수파(좌측)와 다르나, 레이아웃 제약에 의한 의도적 결정]*

2역할 체계(일반 사용자 / 관리자)를 사용하며, 역할별로 메뉴 가시성이 달라진다. 관리자 역할은 AI사업팀(서비스 제공자)과 코나아이 경영진에게 부여한다. 멀티테넌트 확장 시 역할 세분화를 검토한다. *[근거: 05-admin-ia.md — 단일 테넌트·소수 사용자 환경에서 4역할은 과도]*

| 메뉴 | 일반 사용자 | 관리자 |
|------|:-:|:-:|
| 홈/대시보드 | ● | ● |
| AI 채팅 | ● | ● |
| 스킬 | ● | ● |
| 데이터 | | ● |
| 관리자 | | ● |

### 3.1 홈/대시보드

**목적**: 서비스 진입점이자 AI 인사이트 + KPI 모니터링 허브. 기존 Liveboard를 통합한다.

#### 왜 홈과 대시보드를 통합하는가

리서치 대상 서비스들(Datadog, ThoughtSpot, Databricks)은 "홈(맥락 기반 추천)"과 "커스텀 대시보드"를 분리하는 경향이 있다. 그러나 이들은 수십~수백 개의 대시보드를 운영하는 대규모 플랫폼이다. KonaI-Agent의 대시보드는 채팅에서 pin한 시각화의 집합이므로, 사용자별로 하나의 핀 보드가 홈 역할을 겸하는 것이 자연스럽다. *[근거: 01-dashboard.md — Datadog, ThoughtSpot 패턴 참조]*

#### 핵심 컨셉: Pin 기반 대시보드

대시보드는 사전 구성된 위젯 그리드가 아니라, **사용자가 AI 채팅에서 도출한 시각화 결과를 pin하여 지속적으로 관찰하는 보드**다. 채팅에서 생성된 차트, KPI, 분석 결과에 pin 버튼을 누르면 대시보드에 고정되고, 데이터가 갱신되면 해당 시각화도 함께 업데이트된다.

이 접근은 "빈 대시보드에서 위젯을 골라 배치하는" 기존 BI 패턴과 다르다. 사용자가 실제로 필요한 인사이트만 대시보드에 축적되므로, 사용되지 않는 위젯이 화면을 차지하는 문제가 없다. *[근거: 01-dashboard.md — ThoughtSpot Liveboard의 "검색 결과를 Liveboard에 pin" 패턴 참조]*

#### 하위 구성

```
홈/대시보드
├─ 핀 보드 (위젯 배치·관리·드릴다운)
└─ 채팅창
```

#### 기능별 근거

| 기능 | 참조 서비스 | 구체적 기능 | 근거 문서 |
|------|-----------|-----------|----------|
| pin 기반 시각화 고정 | ThoughtSpot | Answer를 Pin 버튼으로 Liveboard에 추가 | 01-dashboard.md |
| 위젯 드래그 앤 드롭 배치 | ThoughtSpot, Datadog | Liveboard 재배치, Datadog Responsive Grid | 01-dashboard.md |
| 위젯 드릴다운 → 채팅 | ThoughtSpot, Databricks | SpotIQ Change Analysis, Genie Space↔대시보드 연동 | 01-dashboard.md |
| 필터 조건 자동 전달 | ThoughtSpot, Databricks | SpotIQ 드릴다운 컨텍스트 전달, Genie의 대시보드 연동 | 01-dashboard.md |

**드릴다운 → 채팅 연결**: 대시보드 위젯에서 이상치를 발견하면 컨텍스트 메뉴를 통해 "에이전트에게 분석 요청"이 가능하다. 이때 위젯의 현재 필터 조건과 드릴다운 경로가 채팅 컨텍스트로 자동 전달된다. *[근거: 01-dashboard.md — ThoughtSpot SpotIQ, Databricks Genie]*

### 3.2 AI 채팅

**목적**: 서비스의 중심 허브. 모든 업무 요청의 시작점이자 에이전트 실행 결과를 확인하는 인터페이스.

> Chat은 이미 프로토타입을 통과하여 실제 개발이 진행 중이다.
> 이 섹션에서는 다른 메뉴와의 연결점만 정의한다. *[근거: ia-research-plan.md 전제 조건]*

#### 레이아웃 (4-column)

Chat 화면은 Claude Cowork과 동일한 4-column 구조를 따른다:

```
AI 채팅 (4-column 레이아웃)
├─ 좌측 사이드바 (대화 이력, 지식 베이스)
├─ 중앙 채팅 (대화, HITL, 멀티에이전트 오케스트레이션, 스킬 생성)
├─ 아티팩트 패널 (결과물 렌더링, 인라인 편집)
└─ 우측 사이드바 (진행 상황, 작업 폴더, 컨텍스트)
```

**스킬 생성·테스트가 채팅에서 이루어지는 이유**: 스킬 생성은 멀티턴 대화를 통해 반복적으로 정의를 다듬는 과정이며, 중간 결과물(스킬 코드, 테스트 결과)을 아티팩트 패널에서 실시간 확인하면서 진행해야 한다. 스킬 메뉴의 별도 에디터보다 채팅 인터페이스가 이 워크플로우에 적합하다. *[참조: Claude Code의 SKILL.md 작성 + Artifact 기반 편집 패턴 — 03-skill.md]*

#### 기능별 근거

| 기능 | 참조 서비스 | 구체적 기능 | 근거 문서 |
|------|-----------|-----------|----------|
| 대화 이력 (좌측 사이드바) | Claude, ChatGPT | 사이드바 대화 목록, 날짜별 그루핑 | 06-gnb.md |
| 지식 베이스 파일 탐색 | Claude Projects | Project Knowledge Files | 03-skill.md |
| 멀티모달 입력 | Claude, ChatGPT | 텍스트·이미지·파일 업로드 | 06-gnb.md |
| ToolCall 시각화 | Claude Code | 스킬 호출 시각화, 실행 로그 표시 | 03-skill.md |
| HITL (Claude 형태) | Claude | Claude의 승인 워크플로우 | 자체 구현 확정 |
| 스킬 생성·테스트 (채팅 내) | Claude Code | SKILL.md 작성, Artifact 기반 생성/편집 | 03-skill.md |
| 아티팩트 패널 렌더러 | Claude Projects | Artifact Panel (마크다운, 코드 렌더링) | 03-skill.md |
| 우측 사이드바 — 진행 상황 | Claude Cowork | 에이전트 todo list | 자체 설계 (Claude Cowork 참조) |
| 우측 사이드바 — 작업 폴더 | Claude Cowork | Output 폴더, 생성 파일 목록 | 자체 설계 (Claude Cowork 참조) |
| 우측 사이드바 — 컨텍스트 | Claude Code | `<available_skills>` 블록, Knowledge Files | 03-skill.md |

**다른 메뉴와의 연결점**:

| 연결 방향 | 설명 |
|-----------|------|
| 대시보드 → 채팅 | 위젯 드릴다운에서 "에이전트에게 분석 요청" 시 필터 조건이 채팅 컨텍스트로 전달 |
| 채팅 → 대시보드 | 채팅에서 생성한 차트/분석 결과를 대시보드 위젯으로 저장 |
| 스킬 → 채팅 | 스킬 메뉴에서 선택한 스킬이 채팅에서 사용 가능한 도구로 활성화 |
| 채팅 → 스킬 | 채팅에서 생성·테스트한 스킬이 스킬 메뉴의 "팀 스킬"에 등록 |
| 마켓플레이스 → 팀 스킬 | 마켓플레이스에서 활성화한 스킬이 팀 드라이브에 참조 행으로 표시 |
| 팀 스킬 → 마켓플레이스 | 팀 스킬을 "전사 공개"하면 마켓플레이스에 카드로 노출 |
| 데이터 → 채팅 | 데이터 메뉴에서 정의한 접근 권한이 에이전트의 데이터 조회 범위를 결정 |

**대화 이력은 독립 메뉴가 아닌 채팅 좌측 사이드바에 위치**한다. 이미 채팅 사이드바에서 이력을 제공하므로 독립 메뉴(/history)는 중복이다. Claude, ChatGPT 등 모든 챗 기반 서비스가 이 패턴을 따른다. *[근거: ia-research-plan.md — CUT 판단]*

### 3.3 스킬

**목적**: 에이전트가 사용하는 도구(스킬)를 탐색하고 관리하는 허브. 스킬 화면은 **팀이 공유하는 드라이브**와 같다 — 누구나 올릴 수 있고, 올라간 스킬은 팀 전체에 즉시 보인다. 승인 절차나 관리자 검토 없이 자유롭게 공유된다. 스킬 생성·테스트는 AI 채팅에서 수행하며, 이 메뉴는 등록된 스킬의 조회·편집·활성화를 담당한다.

#### 왜 최상위 독립 메뉴인가

스킬/도구 관리의 위치는 서비스의 포지셔닝에 따라 달라진다. 엔터프라이즈 에이전트 빌더 플랫폼에서는 도구 관리가 핵심 워크플로우의 일부이므로 상위에 노출하는 경향이 뚜렷하다:

- **OpenAI Frontier**: Functions/Tools를 에이전트 빌더 내 핵심 섹션으로 배치
- **Salesforce Agentforce**: Agent Builder 내 Topics & Actions로 도구를 정의하며, 빌더 자체가 최상위 메뉴
- **Microsoft Copilot Studio**: Actions(Connector, Flow, MCP, Prompt)를 에이전트 편집의 핵심 탭으로 제공

Claude는 SKILL.md 기반 정의, MCP 서버 연결, 플러그인 스킬 허브 등으로 스킬 생태계를 선도하고 있으나, 스킬 관리 UI가 별도 최상위 메뉴가 아닌 프로젝트·설정·Cowork 맥락에 분산되어 있다. KonaI-Agent는 다중팀 협업 플랫폼이며 조직 단위의 스킬 재사용·관리가 핵심이므로, 스킬을 최상위 메뉴로 독립시켜 가시성을 높인다. *[근거: 03-skill.md, menu-structure.md 결정 2]*

#### 하위 구성

```
스킬
├─ 팀 스킬 ──────────── 단일 테이블 + 슬라이드 패널
│   ├─ 테이블 (활성화 그룹 / 비활성 그룹, 마켓플레이스 참조 스킬 포함)
│   ├─ 슬라이드 패널 (스킬 상세, 전체 확장 가능)
│   └─ 개인 수정본 (편집 시 자동 생성, 팀에 즉시 공유)
└─ 마켓플레이스 ─────── 전사 스킬 허브
    ├─ 카드 그리드 (검색·카테고리·정렬)
    ├─ 슬라이드 패널 (스킬 상세 — 팀 스킬과 동일 구조)
    └─ 기여도 랭킹 (인기 스킬·기여자)
```

팀 스킬과 마켓플레이스는 **탭 네비게이션**으로 전환한다. 팀 스킬이 기본 탭이다. *[상세: 03-skill-ia.md]*

*[설계 변경 (v6): 관리자 전용 탭 제거. 스킬 화면을 "팀 공유 드라이브"로 접근. (v10): 마켓플레이스 탭 추가 — 전사 스킬 탐색·채택·기여도 인정.]*

#### 스코프 모델: 팀 공유 드라이브

스킬은 **팀 공유 드라이브** 모델을 따른다. 생성·수정한 스킬은 즉시 팀 전체에 공유되며, 별도의 승인 절차나 검토 뱃지 없이 바로 노출된다. 팀 스킬 탭의 탐색 범위는 내 팀 스킬로 한정된다. 1인 1팀이며 다중 팀 소속은 없다. 다른 팀의 스킬은 **마켓플레이스 탭**에서 탐색하며, 마켓플레이스에서 활성화한 스킬은 팀 드라이브에 참조 행으로 자동 표시된다. *[상세: 03-skill-ia.md]*

*[설계 변경 (v6): (1) v4의 "미검토" 뱃지 + 관리자 확인 프로세스 제거. (2) 관리자 큐레이션(신규 검토, 개선 제안 승인, 중복 정리, 폐기 처리) 제거. 공유 드라이브 철학: 올라간 것은 바로 보이고, 관리 부담 최소화.]*

#### 활성화 모델

팀에 공유된 스킬 중 **내가 사용할 스킬만 활성화**한다. 활성화해도 사본이 생기지 않고, 원본(또는 내 수정본)을 그대로 참조한다.

- **활성화**: 팀 스킬을 내 채팅에서 사용하겠다고 선택. 에이전트가 해당 스킬을 호출 가능.
- **비활성화**: 내 채팅에서 더 이상 사용하지 않음. 에이전트가 호출하지 않지만, 팀에서 사라지지는 않음.

*[설계 변경: "허브 추가=사본 생성" 모델에서 "활성화=원본 참조" 모델로 전환. 사본이 난립하면 버전 관리가 불가능해지므로, 원본을 참조하되 수정 시에만 개인 수정본을 생성하는 구조로 변경.]*

#### 개인 수정본

팀 스킬을 수정하고 싶으면 **편집을 시작하는 순간 개인 수정본이 자동 생성**된다. 수정본은 팀에 즉시 공유되며, 별도 승인 절차 없이 내 채팅에 바로 적용된다. 같은 원본 스킬에 대해 사용자마다 각자의 수정본을 가질 수 있고, 누가 어떤 수정본을 가지고 있는지 테이블에서 확인 가능하다.

```
[채팅에서 편집] (주 경로) 또는 "..." → [직접 편집] (보조 경로)
  → 수정본 자동 생성 → 편집 → [저장]
  → 내 채팅에 즉시 적용 + 팀에 공유 (승인 불필요)
  → 계속 수정 가능 (반복)
  → 원본 복구 → 수정본 폐기, 원본으로 복귀
```

*[설계 변경 (v6): (1) 수정본이 개인에게만 보이던 것을 팀 공유로 변경. (2) 개선 제안 제출 → 관리자 승인 워크플로우 제거. 수정하면 바로 반영. (3) 삭제/폐기 기능 제거.]*

#### 품질 테스트 + AI 분석

스킬 등록 시 AI가 자동으로 테스트 프롬프트와 프롬프트별 검증 항목(expectations)을 생성·실행하여 품질을 검증한다 (Anthropic skill-creator의 Eval 패턴 차용). 테스트 결과는 슬라이드 패널의 **첫 번째 영역(기본 펼침)**으로 배치한다. 각 프롬프트에 [▸ 검증] 접힘 토글이 있어 검증 항목별 판정(✓/✗)과 근거(evidence)를 확인할 수 있으며, 실패한 프롬프트는 실패 evidence가 인라인으로 즉시 노출된다. 의미 있는 분석이 도출된 경우 AI 분석 노트(💡 참고)를 조건부로 표시한다.

*[설계 변경 (v8→v9): 실제 Anthropic eval 산출물 기반으로 재설계. 통과율("4/5") 제거 — 실제 시스템이 프롬프트 내 expectations 단위로 판정하므로 단일 분수 부적합. B안 채택: 검증 상세 접힘 + 실패 evidence 인라인. 상세: 03-skill-ia.md 3.2절]*

#### 버전 이력 + AI 변경 요약 + 비연속 비교

버전이 변경되면 AI가 **변경 내용을 한국어로 요약**한다 (사전 생성). 원문 diff를 그대로 보여주는 대신, 사용자가 빠르게 파악할 수 있는 자연어 설명을 제공한다. 원문 비교가 필요하면 [원문 비교 보기]로 side-by-side diff를 확인할 수 있다. 버전 이력은 **기본 접힘** 상태로 배치하며, 헤더에 최신 변경 한 줄 요약을 인라인으로 표시하여 펼치지 않아도 최근 변화를 파악할 수 있다.

비연속 버전 비교: 사용자가 기준 버전의 컨텍스트 메뉴에서 [다른 버전과 비교]를 선택하면, 대상 버전을 지정하여 AI가 **동적으로** 두 버전 간 차이를 분석한다 (예: v2↔v5). 인접 버전의 사전 생성 요약과 달리, 비연속 비교는 요청 시점에 생성되어 전체 변화 맥락을 제공한다.

*[설계 변경 (v6→v8): (v6) AI 요약 도입. (v8) 버전 이력 기본 접힘으로 변경, 헤더 인라인 요약 추가, 비연속 버전 동적 비교(Pattern C) 추가. 상세: 03-skill-ia.md 5.6–5.7절]*

#### 스킬 생성 경로

스킬 추가에는 두 가지 경로가 있다. 팀 스킬 테이블의 [+ 추가] 드롭다운에서 선택한다. 두 경로 모두 등록 즉시 팀에 공유되며, 생성자는 자동 활성화된다.

- **채팅에서 만들기**: AI 채팅으로 이동하며 스킬 생성 프롬프트(목적·트리거·결과물 템플릿)가 자동 입력된다. 에이전트가 대화형으로 Intent 확인 → 상세화 Interview → SKILL.md 초안 생성 → 사용자 확인 → 등록까지 안내한다. 복잡한 스킬은 보조 파일(scripts/, references/, assets/)도 자동 생성.
- **파일에서 가져오기**: 파일 업로드 모달에서 SKILL.md(단일 파일) 또는 .zip(패키지)을 업로드한다. 필수 검증(SKILL.md 존재, name/description 필드, 이름 중복) 통과 후 미리보기 → [등록]. 경고 검증(본문 길이, 누락 참조)은 표시만.

*[근거: Anthropic skill-creator Intent Capture → Interview → Write SKILL.md 패턴, Manus conversation-to-skill + .skill 업로드, Relevance AI "Invent" 자동 생성. 상세 설계: 03-skill-ia.md 4절]*

#### 화면 구성

**테이블 + 슬라이드 패널** 구조를 사용한다. 팀 스킬 전체를 단일 테이블로 표시하되, 활성화/비활성화 그룹으로 구분한다. 행 클릭 시 우측에 슬라이드 패널이 열리고, 테이블 컬럼이 축소된다. 패널은 전체 확장 옵션을 제공한다.

테이블 컬럼: 스킬 이름, 한 줄 설명, 카테고리, 작성자, 수정일, 버전, 사용 횟수, 활성화 토글. 품질 정보는 패널의 품질 테스트 영역에서 expectations+evidence로 확인하며, 테이블 수준의 품질 컬럼은 후순위.

스킬 상세 슬라이드 패널은 **헤더 → 품질 테스트 → 버전 이력 → 스킬 콘텐츠** 순서로 구성한다. 헤더에는 AI가 생성한 2-3줄 스킬 설명과 최신 변경 인라인 요약을 표시한다. 품질 테스트는 **기본 펼침**(첫 번째 영역)으로 배치하여 스킬의 용도와 품질을 즉시 전달한다. 버전 이력과 스킬 콘텐츠는 **기본 접힘** 상태로 배치하며, 각각 접힌 상태에서도 핵심 정보(최신 변경 한 줄, 파일 수)를 미리보기로 표시한다. 주 편집 경로는 **[채팅에서 편집]**이며 직접 노출된다. 보조 편집 경로인 **직접 편집**은 "..." 메뉴에 배치하여 경미한 수정에 사용한다.

### 3.4 데이터

**목적**: 에이전트가 참조하는 뷰테이블을 탐색하고, **ERP 및 외부 데이터 소스의** 접근 권한을 관리하는 데이터 거버넌스 허브.

데이터 메뉴는 **단일 화면**에서 뷰테이블의 메타데이터·스키마·데이터·접근 권한을 통합 관리한다. 좌측 뷰테이블 목록 + 우측 슬라이드 패널 구조이며, ERP 뷰는 패널 내 4개 탭([개요][스키마][데이터][접근 권한]), 비ERP 소스는 2개 탭([개요][접근 권한])으로 관점을 전환한다. *[근거: 02-data.md, data-access-policy.md]*

관리자 메뉴는 "누가 시스템에 접근하는가"(사용자·역할)를, 데이터 메뉴는 "뷰테이블에 어떤 데이터가 있고 누가 볼 수 있는가"(카탈로그·접근 권한)를 담당한다. 사용자 기준의 접근 확인("이 사용자가 뭘 볼 수 있는가?")은 주체 일관성 원칙에 따라 관리자 > 사용자 관리 메뉴에서 제공한다. *[근거: 02-data.md — Snowflake Governance, Databricks Unity Catalog]*

#### 화면 구성

```
데이터 (단일 화면)
└─ 뷰테이블 목록 (ERP + 비ERP 통합) + 슬라이드 패널
    ERP 뷰 패널 탭: [개요] [스키마] [데이터] [접근 권한]
    비ERP 소스 패널 탭: [개요] [접근 권한]
```

*[설계 변경 이력: (1) 4탭(뷰 테이블, 온톨로지, 접근 정책, 감사 로그) → 2탭(카탈로그, 접근 제어) → 단일 화면으로 통합. 카탈로그와 접근 제어의 좌측 목록이 동일하므로, 패널 탭으로 관점을 전환하는 것이 더 간결. (2) 사용자 기준 접근 확인은 관리자 > 사용자 관리로 이동. (3) 데이터 파이프라인 탭 제거 — 단일 소스 환경에서 불필요. (4) 컬럼 마스킹(CLS)은 현 기획 범위에서 제외.]*

#### 뷰테이블 목록 (좌측)

뷰테이블 이름, 소스, 도메인, 접근 주체(유형별 요약: `2부서 · 1그룹 · 1명`). 검색 + 도메인 + 소스 유형 필터를 제공한다. 페이지 헤더에 [+ 등록] 버튼을 배치하여 비ERP 데이터 소스 등록 다이얼로그를 열 수 있다.

#### 슬라이드 패널 (우측, 행 클릭 시)

패널 상단에 뷰테이블 이름과 [↗ 확장] 버튼, 그 아래에 소스 유형에 따라 탭을 배치한다. 기본 선택 탭은 [개요]이다.

- **[개요]**: 뷰테이블 메타데이터 (ID, 표시명, 설명, 도메인, auth_type, 원천 ERP 화면명/연결 정보, rls_type, 활성 여부). ERP 뷰는 읽기 전용. 비ERP 뷰만 [편집] 가능
- **[스키마]** (ERP 뷰 전용): 컬럼명, 데이터 타입, 설명. 탭 헤더에 컬럼 수 인라인 표시
- **[데이터]** (ERP 뷰 전용): 지연 로드, 최대 50행, RLS 미적용 (관리자 전체 데이터 확인용). 패널 확장 권장
- **[접근 권한]**: 접근 가능 **부서**/그룹/사용자 현황 + RLS 설정(rls_type, rls_config). ERP 뷰는 ERP 권한 기준 현황 표시(읽기 전용), 비ERP 뷰는 부서/사용자 단위로 직접 편집 가능. [편집] 버튼으로 수정 다이얼로그 열기. `_TCAOrgDeptSecu` 테이블 참조. *[상세: data-access-policy.md 8.1절]*

*[근거: Snowflake Database Explorer — 테이블 상세에서 Columns/Data Preview/Privileges를 탭으로 전환, Databricks Catalog Explorer — Overview/Schema/Sample Data/Permissions 탭 구조]*

### 3.5 관리자

**목적**: 관리자가 사용자·운영 현황·대화 이력을 관리하는 엔터프라이즈 거버넌스 모듈.

#### 하위 구성

```
관리자 (3탭 플랫 구조)
├─ 사용자 관리 ──────── 테이블 + 슬라이드 패널 (사용자 정보 + 뷰테이블 접근 현황)
├─ 운영 현황 ────────── 단일 스크롤 (에이전트 상태 + 비용/사용량 + 활동 리포트) + 모델 설정 팝업
└─ 대화 이력 ────────── 전체 폭 테이블 + 슬라이드 패널
```

**사용자 탭**: 슬라이드 패널에 **"뷰테이블 접근 현황"** 섹션을 추가한다. 사용자를 선택하면 해당 사용자가 접근 가능한 뷰테이블 목록과 허용 근거(어떤 부서(`_TCAOrgDeptSecu`) 권한인지, 그룹 권한인지, 사용자 오버라이드인지)를 표시한다. "이 사용자가 왜 이 데이터를 못 보는가?"라는 관리자의 질문에 답하는 용도이다.

*[설계 변경 (v4): (1) 2화면(사용자 관리 + 모니터링) → 3탭(사용자 관리 + 운영 현황 + 대화 이력)으로 변경. 대화 이력은 테이블+패널 구조로 독립 화면급 복잡도를 가지므로, 운영 현황의 대시보드형 콘텐츠와 분리. (2) "사용자 및 권한"→"사용자 관리"로 단순화 — 2역할 체계에서 별도 권한 관리 불필요. (3) 플랫폼 관리 섹션 제거 — 단일 테넌트 환경에서 불필요, 멀티테넌트 확장 시 별도 포탈로 구축. (4) 시스템 설정(모델 프로바이더)은 운영 현황 우상단 팝업으로 흡수.]*

**모니터링 기능을 관리자 하위에 배치**한다. 리서치 대상 중 Datadog만이 모니터링을 독립 최상위 메뉴로 두는데, 이는 Datadog 자체가 모니터링 전문 서비스이기 때문이다. AI 에이전트 플랫폼에서 모니터링은 관리 기능의 일부이므로 관리자 하위가 적합하다. *[근거: 05-admin.md — Dify, Salesforce 패턴]*

### 기존 메뉴의 재배치

기존 프로토타입에 있던 메뉴 중 독립 메뉴에서 제거되거나 다른 메뉴로 흡수된 항목:

| 기존 메뉴 | 판단 | 사유 | 재배치 |
|-----------|------|------|--------|
| **예약 작업** (/settings/scheduled-tasks) | 제외 | AI 채팅/에이전트 중심 플랫폼 15개 중 8개(Claude, ChatGPT, Manus 등)가 미제공. *[04-scheduled-tasks.md]* | 로드맵 후순위 |
| **대화 이력** (/history) | 제거 | 채팅 좌측 사이드바에서 이미 제공. 독립 메뉴는 중복 | — |
| **에이전트 설정** (/settings/agent-config) | 흡수 | 스킬 상세의 파라미터 설정으로 대체 | 스킬 메뉴 |
| **프롬프트 관리** (/settings/prompt-management) | 흡수 | 스킬 생성 과정(채팅)에 포함 | AI 채팅 |
| **기존 마켓플레이스** (/settings/marketplace) | 이동 | 스킬 메뉴의 "마켓플레이스" 탭으로 통합 (전사 스킬 허브) | 스킬 메뉴 |
| **지식 베이스** | 흡수 | 채팅 좌측 사이드바에 파일 탐색으로 제공 | AI 채팅 |

### 메뉴 간 연결 구조

```
┌──────────────────────────────────────────────────────────┐
│                    상단 GNB (5개 메뉴)                      │
│  [홈/대시보드] [AI 채팅] [스킬] [데이터] [관리자]              │
└──────────────────────────────────────────────────────────┘

    ┌─────────────┐         ┌──────────────┐
    │ 홈/대시보드   │ ←pin── │   AI 채팅     │
    │ (핀 보드)    │ ──────→│ (중심 허브)    │
    └─────────────┘ 드릴다운  └──────────────┘
                             ↑ 스킬       ↑ 접근
                             │ 활성화      │ 권한
                        ┌────┘            └────┐
                   ┌─────────┐          ┌─────────┐
                   │  스킬    │          │  데이터   │
                   │ 조회·관리 │          │ 카탈로그+접근제어│
                   └─────────┘          └─────────┘

              ┌──────────────┐
              │   관리자      │
              │ 사용자·권한    │→ 역할별 메뉴 가시성 결정
              │ 모니터링·감사  │→ 전체 서비스 활동 추적
              └──────────────┘
```

핵심 흐름: **AI 채팅에서 시각화 생성 → pin → 대시보드에 고정 → 드릴다운 → 다시 채팅으로** 순환한다. 스킬 메뉴는 채팅에서 사용할 도구를 관리하고, 데이터 메뉴는 에이전트의 데이터 접근 범위를 결정하며, 관리자 메뉴는 전체 서비스의 사용자·권한·모니터링을 담당한다.
