# KonaI-Agent IA 재설계를 위한 리서치 계획서 v4

> 작성일: 2026-03-20 | 수정일: 2026-03-23
> 목적: **프로토타입 재구성**을 위해 메뉴별 IA를 전문적으로 재설계하기 위한 **스킬 기반 에이전트 서비스** 중심 리서치 계획
> 의사결정자: 에이전트 서비스 개발 담당자 + 제품 팀장

## 0. 전제 조건

### 이 프로토타입의 목적
KonaI-Agent 프로토타입은 **실제 개발 진입 전 화면을 보고 의사결정하기 위한 것**이다.
데모 임팩트가 아닌, **제품 구조의 타당성 검증**이 목적이다.

### 현재 상태
- **Chat**: 프로토타입 통과, 이미 실제 개발 진행 중. 이번 리서치에서는 다른 메뉴와의 연결점만 가볍게 확인
- **그 외 메뉴**: IA 없이 만들어져 목적성이 불분명. 이번에 IA부터 재설계

### v4 변경 사항 (v3 대비)
- **리서치 대상을 스킬 기반 에이전트 서비스로 교체**: 순수 인프라/BI 도구(Datadog, Snowflake, Databricks, ThoughtSpot)를 제외하고, 에이전트가 스킬/도구를 사용하는 서비스에 집중
- **모든 리서치 영역에 스킬 관점 추가**: 대시보드, 데이터, 예약 작업, 관리자 영역에서도 "스킬이 어떻게 활용되는가"를 핵심 질문으로 포함
- **새 서비스 추가**: Dust.tt, Relevance AI 등 스킬 기반 에이전트 빌더 플랫폼 추가

### 핵심 차별화 포인트
1. **엔터프라이즈 데이터 거버넌스** — 누가 어떤 데이터에 접근 가능한지 통제
2. **올인원 AI 워크스페이스** — 채팅·분석·문서생성·대시보드를 하나의 플랫폼에서
3. **스킬 기반 에이전트 오케스트레이션** — 에이전트가 스킬을 조합하여 복합 작업을 수행

### 킬러 유스케이스
1. 자연어로 데이터 분석·시각화 (에이전트가 데이터 스킬을 활용)
2. AI 에이전트가 문서(PPT/보고서) 자동 생성 (문서 생성 스킬)
3. 데이터 접근 제어 + AI 거버넌스 (스킬 실행 시 접근 정책 적용)

### 데이터 아키텍처 (리서치 맥락)
```
ERP 데이터베이스
    ↓ (실제 사용자가 ERP 화면에서 보는 데이터)
뷰 테이블 (View Tables)
    ↑ (탐색)
Neo4j 온톨로지
    ↑ (경유)
AI 에이전트 → 스킬 실행 → 온톨로지를 거쳐 → 뷰 테이블 탐색 → 데이터 조회/분석
```
- ERP DB 원본 → 사용자 관점의 뷰 테이블로 변환
- Neo4j 그래프 DB로 온톨로지(데이터 관계/의미 구조) 구축
- 에이전트는 **스킬을 실행**하여 온톨로지를 탐색하고 적절한 뷰 테이블을 찾아 데이터에 접근
- "데이터 관리" 메뉴에서는 이 뷰 테이블 + 온톨로지 + 접근 제어를 관리해야 함

### 프로토타입 설계 원칙
- **미니멀**: 핵심 기능만. 존재가 혼란을 주는 메뉴는 제거
- **직관적**: 메뉴명만으로 목적이 즉시 전달
- **구조적 타당성**: 스킬 기반 에이전트 서비스들의 검증된 패턴에 기반

## 1. 메뉴 필요성 판단 (Keep / Cut / Merge)

### 판단 기준
- **KEEP**: 제품의 핵심 가치에 기여하거나, 없으면 제품 이해가 불가능한 메뉴
- **MERGE**: 독립 메뉴로 존재할 필요 없이 다른 메뉴의 일부로 통합 가능
- **CUT**: 제거. 존재가 사용성을 해치거나, 핵심 가치와 무관
- **리서치로 결정**: 위치나 독립성을 리서치 결과로 판단

### 판단 결과

| 현재 메뉴 | 판단 | 근거 |
|-----------|------|------|
| **대시보드 (/)** | **KEEP** — 재정의 필요 | 올인원 워크스페이스의 "홈". AI가 생성한 인사이트와 KPI를 보여주는 진입점 |
| **채팅 (/chat)** | **KEEP** — 이미 확정 | 실제 개발 진행 중. 다른 메뉴와의 연결점만 확인 |
| **데이터 관리 (/data)** | **재정의 후 KEEP** | 거버넌스 차별점의 핵심. ReactFlow 파이프라인 에디터가 아닌 "데이터 소스 + 접근 제어" 중심으로 재정의 |
| **스킬 관리 (/settings/skills)** | **KEEP** — 위치 재검토 | 스킬 활용이 제품의 핵심 가치. 현재 "설정 하위"가 맞는지 리서치로 검증 |
| **관리자 (/admin)** | **KEEP** | 고객사(클라이언트) 관리자가 자사 사용자·권한·데이터 접근 정책을 관리하는 화면 |
| **플랫폼 관리 (/platform-admin)** | **KEEP** | 서비스 제공자(우리)가 고객사들을 모니터링하는 내부 운영 화면. Admin과 사용자 자체가 다르므로 분리 유지 |
| **예약 작업 (/settings/scheduled-tasks)** | **KEEP** — 위치 리서치로 결정 | 필요한 기능이나, 독립 메뉴인지 다른 메뉴의 하위인지 리서치로 판단 |
| **대화 이력 (/history)** | **CUT** | 이미 채팅 사이드바에서 히스토리 제공. 독립 메뉴는 중복이자 혼란 |
| **에이전트 설정 (/settings/agent-config)** | **CUT** | 채팅 내 모드 전환이나 스킬 메뉴 하위로 대체 가능 |
| **프롬프트 관리 (/settings/prompt-management)** | **CUT** | 에이전트 또는 스킬의 하위 기능으로 흡수 가능 |
| **마켓플레이스 (/settings/marketplace)** | **CUT** | 스킬 탐색 기능으로 흡수 가능. 독립 메뉴 불필요 |
| **Liveboard (/liveboard)** | **MERGE → 대시보드** | 대시보드와 통합. 위젯 그리드가 대시보드의 핵심 기능이 되어야 |

### 프로토타입 메뉴 후보 (7개)

```
[일반 사용자 + 고객사 관리자 대상]
1. 홈/대시보드     — AI 인사이트 + KPI 위젯 (Liveboard 통합)
2. AI 채팅        — 이미 확정. 다른 메뉴와의 연결점만 이번 리서치에서 확인
3. 데이터         — 데이터 소스 연결 + 접근 제어 정책 (거버넌스 차별점)
4. 스킬           — 스킬 탐색·관리·생성 (위치는 리서치로 검증)
5. 예약 작업       — 에이전트 예약 실행 (위치는 리서치로 검증)
6. 관리자         — 고객사 관리자용: 사용자·권한·감사로그·사용량

[서비스 제공자(우리) 전용]
7. 플랫폼 관리     — 고객사 모니터링·테넌트 관리·전체 사용량 (별도 권한)
```

> **리서치에서 검증할 것:**
> - 스킬의 최적 위치 (독립 최상위 메뉴? 설정 하위? 다른 메뉴 하위?)
> - 예약 작업의 최적 위치 (독립 메뉴? 관리자 하위? 스킬 하위? 대시보드 하위?)
> - 관리자 vs 플랫폼 관리의 분리가 다른 SaaS에서 어떻게 처리되는지
> - 스킬 실행 결과가 대시보드·채팅·데이터에 어떻게 반영되는지
> - 빠진 필수 메뉴가 없는지

## 2. 리서치 대상 선정

### 선정 원칙

리서치 대상은 **"에이전트가 스킬/도구를 사용하는 서비스"**로 한정한다. 순수 인프라·BI·모니터링 도구는 제외하고, 에이전트의 스킬 활용 패턴이 존재하는 서비스만 포함한다.

| 기준 | 설명 |
|------|------|
| **① 스킬 기반 에이전트** | 에이전트가 스킬/도구/플러그인/액션을 사용하여 작업을 수행하는 플랫폼 |
| **② 직접 경쟁** | KonaI-Agent와 같은 "엔터프라이즈 AI 에이전트 플랫폼" 카테고리 |
| **③ 스킬 생태계 선도** | 스킬 정의·관리·마켓·오케스트레이션에서 혁신적 패턴을 보유 |
| **④ 높은 시장 점유율** | 엔터프라이즈 에이전트 시장에서 검증된 IA |

### 선정 결과

에이전트가 스킬/도구를 핵심 메커니즘으로 사용하며, 전체 IA 구조를 참조할 수 있는 서비스.

### 영역 ① 대시보드 & 인사이트 — 메뉴 "홈/대시보드"

**대응 메뉴**: 홈/대시보드 (AI 인사이트 + KPI 위젯, Liveboard 통합)
**리서치 대상**: OpenAI Frontier, Salesforce Agentforce, ServiceNow AI Control Tower, Dify, Coze, Dust.tt

**이 리서치로 결정할 것:**
- "홈"과 "대시보드"를 하나로 합칠 것인가
- 대시보드에 어떤 위젯 유형이 필요한가
- AI 에이전트의 스킬 실행 결과를 대시보드에 어떻게 반영할 것인가
- 스킬 실행 모니터링(에이전트 활동 로그, 스킬 사용량)을 어디에 배치할 것인가
- 채팅에서 스킬로 생성한 분석 결과를 대시보드로 저장하는 경로

**구체적 질문:**

1. **홈 vs 대시보드 관계**
   - 서비스에 처음 접속했을 때 보이는 화면은 무엇인가?
   - "홈"과 "대시보드"가 분리된 서비스가 있는가? 있다면 각각의 역할은?
   - 커스텀 대시보드를 여러 개 만들 수 있는가?

2. **위젯 구성과 커스터마이징**

   - 위젯 추가/삭제/배치를 사용자가 직접 하는가?
   - 위젯 드릴다운(클릭→상세) 인터랙션은?

3. **스킬 실행 결과의 대시보드 통합** ← 스킬 관점

4. **스킬 활동 모니터링** ← 스킬 관점
   - 에이전트별/스킬별 실행 로그가 대시보드에 포함되는가, 별도 섹션인가?

### 영역 ② 데이터 거버넌스 & 소스 관리 — 메뉴 "데이터"

**대응 메뉴**: 데이터 (데이터 소스 연결 + 접근 제어)
**리서치 대상**: OpenAI Frontier, Microsoft Copilot Studio, Dify, Dust.tt, Relevance AI, Coze

**우리의 데이터 구조 맥락:**
ERP DB → 뷰 테이블 + Neo4j 온톨로지 → 에이전트가 스킬을 실행하여 온톨로지를 거쳐 뷰 테이블 탐색.
따라서 "데이터" 메뉴에서 관리할 대상은: (1) 뷰 테이블 목록/스키마, (2) 온톨로지(데이터 관계 구조), (3) 접근 제어 정책.

**이 리서치로 결정할 것:**
- "데이터" 메뉴의 핵심 기능은 파이프라인 에디터인가 거버넌스인가
- 스킬이 데이터에 접근하는 경로(Connections/Connectors)를 어떻게 관리하는가
- 데이터 소스 연결과 접근 제어 정책을 같은 메뉴에 둘 것인가
- Knowledge Base(RAG)를 어디에 배치할 것인가 — 데이터인가 스킬인가
- 시맨틱 레이어/온톨로지를 통한 스킬의 데이터 탐색 경로를 어떻게 관리하는가

**구체적 질문:**

1. **데이터 소스 관리 IA**
   - 데이터 소스(DB, API, 파일) 연결이 독립 메뉴인가 설정 하위인가?
   - 연결된 데이터 소스 목록을 어떻게 표시하는가? (카드? 테이블? 트리?)
   - 스키마 탐색(테이블→컬럼) UI는?

2. **스킬의 데이터 접근 경로 (Connections/Connectors)** ← 스킬 관점
   - 에이전트의 스킬이 데이터에 접근하는 설정이 어디에 있는가? (데이터 메뉴? 스킬 메뉴? 에이전트 빌더 내부?)
   - OpenAI Frontier의 "Business Context"는 에이전트 스킬이 데이터를 탐색하는 시맨틱 레이어인가?
   - Dust.tt의 "Connections"와 Copilot Studio의 "Connectors"는 데이터 접근 스킬인가 데이터 설정인가?
   - 스킬이 접근 가능한 데이터 범위를 설정하는 UI가 있는가?

3. **스킬 실행 시 접근 제어** ← 스킬 관점
   - 에이전트가 스킬로 데이터를 조회할 때 접근 제어가 어떻게 적용되는가?
   - 스킬별로 접근 가능한 데이터 범위를 다르게 설정할 수 있는가?
   - 정책 생성 UX: 코드 기반? UI 기반? 자연어 기반?

4. **Knowledge Base / RAG 관리**
   - 문서 기반 지식(RAG)이 "데이터" 하위인가 "스킬/도구" 하위인가 별도 메뉴인가?
   - Knowledge Base가 스킬의 일종인가 데이터 소스의 일종인가? (Dify의 Knowledge vs Dust.tt의 Connections)
   - 문서 업로드, 인덱싱 상태, 검색 테스트 화면 구조는?

5. **시맨틱 레이어 / 온톨로지 관리**
   - 데이터 간 의미 관계(온톨로지, 시맨틱 레이어)를 관리하는 UI가 있는가?
   - OpenAI Frontier의 "Business Context"는 어떤 화면에서 설정/관리하는가?
   - 에이전트 스킬이 시맨틱 레이어를 거쳐 데이터를 탐색하는 경로를 시각화하는가?

### ⚠️ 시각 자료 수집 필수

모든 세션에서 **화면 구성을 확인할 수 있는 시각 자료**를 반드시 수집해야 한다.
IA 설계는 구조 분석만으로는 부족하고, 실제 화면이 어떻게 구성되어 있는지 시각적으로 확인해야 판단 근거가 된다.

**수집 대상:**
- 공식 제품 스크린샷 (문서, 블로그, 프레스 릴리즈)

- 제품 투어 / 인터랙티브 데모 링크
- 서드파티 리뷰 영상/스크린샷 (G2, 제품 리뷰 블로그 등)

**각 세션 결론 시 포함할 것:**
- 서비스별 핵심 화면 스크린샷 또는 스크린샷 출처 URL

### 리서치 결과 파일 구조

리서치 결과는 별도 파일로 관리한다. 이 문서에 병합하지 않는다.

```
│   ├── 05-admin.md                  ← v3 완료
│   └── 06-gnb.md                    ← v3 완료
├── research-v4/                      ← v4 리서치 결과 (스킬 기반 에이전트 서비스 대상)
│   ├── 01-dashboard.md              ← 대시보드 (스킬 관점)

│   ├── 05-admin.md                  ← 관리자 (스킬 거버넌스 관점)
│   └── 06-gnb.md                    ← GNB (스킬 위치 검증)

    ├── cross-menu-connections.md     ← Layer 1: 메뉴 간 연결성 종합
    ├── menu-structure.md             ← Layer 1: 메뉴 구조 결정
    └── ...                           ← Layer 2~3 결과물
```

### IA 설계 단계 (리서치 완료 후)

**Layer 1: 구조 결정** (1세션)
- 입력: v3 + v4 리서치 결과 종합. 특히 v4의 스킬 관점 인사이트 우선 반영
- 작업: 메뉴 간 연결성 종합 → 최종 메뉴 목록, 계층, 배치 순서, 역할별 분기 원칙 결정
- 출력: `ia-design/cross-menu-connections.md`, `ia-design/menu-structure.md`
- ⚠️ 형진님 + 제품 팀장 확인 후 다음 단계 진행

**Layer 2: 메뉴별 상세 IA** (병렬, 메뉴당 1세션)
- 입력: Layer 1 확정 메뉴 구조 + 해당 메뉴의 v3+v4 리서치 파일 전문
- 작업: 각 메뉴의 하위 구조, 화면 구성, 주요 인터랙션 설계
- 출력: 메뉴별 IA 상세 문서

**Layer 3: 유스케이스 검증** (1세션)
- 입력: Layer 2 전체 결과물
- 작업: 킬러 유스케이스 3개를 메뉴를 가로질러 워크스루
  - 유스케이스 1 (자연어 분석): 채팅 → 데이터 스킬 실행 → 결과 대시보드 저장
  - 유스케이스 2 (문서 생성): 채팅 → 문서 생성 스킬 실행 → Artifact 표시 → 예약 반복 실행
  - 유스케이스 3 (거버넌스): 관리자가 스킬 사용 권한 설정 → 사용자가 스킬 실행 시 접근 제어 적용
- 출력: 수정사항 + 최종 IA

**Layer 4: GAP 분석**
- 새 IA vs 현재 구현의 차이점
- 마이그레이션 우선순위
