## 현재 상태 (Current State)

| 항목 | 값 |
|------|-----|
| 라우트 | `/admin` 내 탭 (AdminView 내 임베드) |
| 메인 컴포넌트 | `src/components/SkillManagementView.tsx` (253줄) |
| 서브 컴포넌트 | `src/components/SkillUploadModal.tsx` (107줄) |

**현재 구현된 기능:**
- 검색 바 + 탭 필터 (전체 / 내 스킬 / 스킬 탐색)
- 토글 리스트 (on/off Switch)
- ZIP/.skill 파일 드래그앤드롭 업로드 모달
- 9개 하드코딩 목 스킬 (내 스킬 3개, 스킬 탐색 6개)

**핵심 한계점:**
1. 스킬이 하드코딩 — 실제 카탈로그/마켓플레이스 없음
2. 카테고리·태그 없음 — 스킬 수 증가 시 탐색 불가
3. 품질 메타데이터 없음 — Eval 통과율, 벤치마크 점수 표시 불가
4. 출처 구분 미흡 — '내 스킬' vs '스킬 탐색' 2분류만 존재, 배지 시스템 없음
5. 버전 관리 없음 — 스킬 버전 이력 및 롤백 불가
6. 팀·조직 공유 없음 — 개인 스코프에 갇혀 있음
7. 3계층 권한 모델 없음 — 플랫폼/테넌트/개인 정책 구분 없음

## 목표 상태 (Target State)

현재의 단순 토글 리스트를 **업무 시나리오 중심 스킬 카탈로그**로 확장한다.
비개발자도 스킬을 발견·설치·관리할 수 있는 그리드 카드 UI를 제공하고,
Eval 품질 배지와 3계층 출처 배지를 통해 "어떤 스킬이 얼마나 좋은가"와
"누가 만들었는가"를 직관적으로 전달한다. Phase 1에서는 20~50개 스킬 규모를 목표로
카탈로그 UI + 출처 배지 + Eval 품질 배지를 구현한다.

## 네비게이션 플로우

### Primary Journey: 비개발자가 스킬을 발견하고 활성화

1. 사용자 → `/admin` > 스킬 탭 → **스킬 카탈로그** 진입
2. 카테고리 탭(예: "📄 문서 작성")을 클릭하거나 검색바에 키워드 입력
3. 스킬 카드 그리드 표시 — 각 카드에 이름, 설명, 출처 배지, Eval 통과율 배지
4. 카드 클릭 → **스킬 상세 패널** 슬라이드오버
5. 상세 패널에서 설명·요구사항·Eval 결과 확인 후 "활성화" 토글 클릭
6. **활성 스킬** 탭으로 자동 이동 또는 카탈로그 유지 (토글이 ON으로 전환)

### Secondary Journey: 개인 스킬 업로드 (검증 포함)

1. 사용자 → 스킬 카탈로그 화면 우상단 "스킬 추가" 버튼 클릭
2. **SkillUploadWizard** 모달 진입 — ZIP/.skill 드래그앤드롭
3. **Step 1: 유효성 검증** — SKILL.md 존재 확인 → 프론트매터(name, description) 파싱
   - 실패 시: 구체적 오류 메시지 ("SKILL.md에 name 필드가 없습니다") + 수정 가이드 링크
4. **Step 2: 미리보기** — 파싱된 이름, 설명, 추정 카테고리 표시 → 사용자가 확인/수정
5. **Step 3: 공개 범위 선택** — "개인 전용" (기본값) / "조직 배포 요청" (관리자 승인 필요)
6. 확인 → "내 스킬"에 추가 (개인) 또는 승인 큐로 이동 (조직 배포 요청)

### Admin Journey 1: 조직 스킬 배포

1. 관리자 → 스킬 탭 > "관리" 탭 진입
2. "조직 스킬 등록" 버튼 클릭 → SkillUploadWizard (관리자 모드)
3. 업로드 + 검증 후 → 배포 정책 설정 (강제/추천/허용/차단)
4. 대상 선택: 전체 사용자 / 특정 팀·부서
5. 배포 → 대상 사용자의 카탈로그에 출처 배지(⭐ 조직)와 함께 즉시 표시
6. 강제 배포(mandatory) 스킬은 사용자가 끌 수 없으며 🔒 배지 표시

### Admin Journey 2: 승인 요청 처리

1. 관리자 → 스킬 탭 > "관리" 탭 > 승인 요청 목록
2. 사용자가 "조직 배포 요청"한 스킬 목록 확인
3. 각 요청: 스킬 미리보기 → 승인(배포 정책 설정) / 거절(사유 입력)
4. 승인 → 카탈로그에 조직 스킬로 등록 + 요청자에게 알림
5. 거절 → 요청자에게 사유와 함께 알림

### Admin Journey 3: 스킬 정책 관리

1. 관리자 → 스킬 탭 > "관리" 탭 > 정책 설정
2. 스킬 목록에서 각 스킬의 배포 정책 변경 (강제 / 추천 / 허용 / 차단)
3. "차단" 설정 시 → 해당 스킬 활성화한 사용자에게 비활성화 알림 발송

### Version Journey: 스킬 롤백

1. 스킬 상세 패널 → "버전 이력" 탭 진입
2. 버전 목록에서 이전 버전의 Eval 통과율 확인
3. "이 버전으로 롤백" 버튼 클릭 → 영향 범위 표시 ("이 스킬 활성화 사용자: N명")
4. 확인 모달 → 롤백 실행 → Eval 자동 재실행 트리거
5. 결과 반영 후 카드의 Eval 배지 업데이트

## 카테고리 체계

업무 시나리오 중심 4개 카테고리. 카테고리 수를 최소화하여 탐색 혼란을 방지한다.

| 카테고리 | 코드 | 이모지 | 설명 | 예시 스킬 |
|---------|------|--------|------|----------|
| 문서 작성 | `document` | 📄 | 보고서, 기획서, 제안서, 이메일 등 텍스트 중심 | 비즈니스 리포트 생성기, 이메일 교정 도구, 문서 공동 작성 가이드 |
| 데이터 분석 | `data` | 📊 | 데이터 정리, 시각화, 인사이트 도출 | 차트 생성, CSV 분석, 대시보드 |
| 콘텐츠 제작 | `content` | 🎨 | 프레젠테이션, 디자인, 미디어 등 비주얼 중심 | PPT 생성, 이미지 생성, 알고리즘 아트, 캔버스 디자인 |
| 업무 자동화 | `automation` | ⚙️ | 반복 작업 자동화, 코드 생성, 워크플로 | 이메일 자동화, React 코드 최적화, 양식 처리 |

**분류 기준:**
- "문서 작성"과 "콘텐츠 제작"의 경계: 텍스트 산출물 → 문서 작성, 비주얼 산출물 → 콘텐츠 제작
- 코드/개발 관련 스킬: "업무 자동화"에 포함 (코드 생성도 업무 자동화의 일종)
- 20~50개 스킬 규모에서 카테고리당 5~12개로 적절한 밀도 유지

## 출처 배지 시스템

출처별 시각 구분으로 "신뢰도"를 직관적으로 전달한다.

| 배지 | 출처 | 색상/아이콘 | 의미 |
|------|------|-----------|------|
| 플랫폼 | `source: 'platform'` | 파란색 방패 🛡️ | KonaI-Agent 기본 제공, 보안 검증 완료 |
| 조직 배포 | `source: 'org'` + `deployPolicy: 'mandatory' \| 'recommended'` | 주황색 별 ⭐ | 조직 관리자가 배포·추천 |
| 내가 추가 | `source: 'personal'` | 회색 사용자 👤 | 개인이 직접 업로드 |

현재 `type: 'my' | 'example'` 구분은 위 3분류로 교체한다.

## Eval 품질 배지 시스템

Anthropic skill-creator의 Eval 데이터(`grading.json → summary.pass_rate`,
`benchmark.json → delta.pass_rate`)를 기반으로 한다.

| 통과율 범위 | 색상 | 레이블 | 의미 |
|------------|------|--------|------|
| 90~100% | 초록 | ✅ 양호 | 안정적 사용 가능 |
| 70~89% | 파랑 | ℹ️ 보통 | 대부분의 케이스에서 정상 |
| 50~69% | 주황 | ⚠️ 주의 | 일부 케이스에서 실패 |
| 0~49% | 빨강 | ❌ 개선 필요 | 검증 실패 다수 |
| 없음 | 회색 | — 미검증 | Eval 미실행 |

**카드 표시 규칙:**
- 기본: 통과율 숫자(예: "85%")와 색상만 표시
- 변동성 높은 경우(`evalStdDev > 0.1`): "85% ± 12%" 표기 + ⚠️ "결과 불안정" 경고 아이콘
- 상세 패널 진입 시: with_skill vs without_skill delta, 시나리오별 결과, 벤치마크 실행별 산점도를 펼쳐 보여준다

## 오픈 이슈

1. **Eval 데이터 연동 시점**: mock 데이터로 Phase 1을 구현하되, 실제 `grading.json` / `benchmark.json`과의 연동은 백엔드 준비 후 결정. stddev 데이터 수집 방식도 확인 필요.

2. **슬라이드오버 vs 별도 페이지**: 스킬 상세를 슬라이드오버(패널)로 처리할지 별도 라우트(`/admin/skills/{id}`)로 분리할지 결정 필요. 딥링크 필요 시 라우트 분리 고려.

3. **카드 그리드 열 수**: 3열 기준이나 화면 너비에 따라 2열·4열 전환 여부 확인 필요 (현재 AdminView max-width 제약).

4. **관리자 탭 노출 조건**: "관리" 탭을 관리자 역할 기반으로만 보여줄지, 일반 사용자에게도 읽기 전용으로 보여줄지 결정 필요.

5. **조직 스킬 배포 대상 세분화**: "전체 사용자" 외에 "특정 팀·부서"를 선택할 수 있도록 했는데, 현재 사용자 데이터에 팀/부서 구분이 충분한지 확인 필요. `admin.types.ts`의 `EnhancedUser.department` / `division` 필드를 활용할 수 있는지 검토.

6. **롤백 시 Eval 재실행 트리거**: 롤백 후 자동 Eval 재실행이 프론트엔드에서 트리거할 수 있는 API가 있는지 확인 필요. 없으면 "재실행 권장" 안내만 표시하고 수동 트리거로 처리.

7. **설명 최적화(Description Optimization) 구현 범위**: Anthropic의 설명 최적화 기능이 API로 노출되는지 확인 필요. 안 되면 프론트엔드에서 자체 분석 로직을 구현해야 하므로 공수 재평가 필요.

8. **업데이트 알림 전달 채널**: 인앱 배지만으로 충분한지, 이메일/Slack 알림도 필요한지 팀 확인. 강제 배포 스킬의 자동 업데이트 시 사전 알림 타이밍(즉시 vs 24시간 유예)도 결정 필요.
