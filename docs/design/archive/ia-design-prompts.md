## Step 1: 리서치 결과 통합 프롬프트

### 목적
6개 세션의 관찰 사실을 **구조적으로 통합**하여, 이후 설계 단계에서 참조할 수 있는 단일 문서를 만든다.

### 프롬프트

```
[컨텍스트로 첨부: ia-research-plan.md + 6개 세션 결과물]

아래 6개 리서치 세션 결과를 하나의 통합 문서로 정리해줘.
이 문서는 KonaI-Agent의 IA 설계 의사결정에 직접 사용할 참조 자료야.

[전제 — 반드시 숙지]
- 프로토타입 목적: 제품 구조의 타당성 검증 (데모 임팩트 아님)
- 핵심 차별점: ① 엔터프라이즈 데이터 거버넌스 ② 올인원 AI 워크스페이스
- 데이터 구조: ERP DB → 뷰 테이블 + Neo4j 온톨로지 → 에이전트가 온톨로지를 거쳐 데이터 접근
- 현재 메뉴 후보 (7개): 홈/대시보드, AI 채팅(확정), 데이터, 스킬, 예약 작업, 관리자, 플랫폼 관리
- Chat은 이미 개발 중이므로 다른 메뉴와의 연결점만 확인

[정리 방식]

### Part A: 서비스별 종합 프로필

각 리서치 대상 서비스별로 다음을 1페이지 이내로 요약:

| 항목 | 내용 |
|------|------|
| 서비스명 | |
| 카테고리 | (Tier 1 직접 경쟁 / Tier 2 영역별) |
| GNB 구조 | 최상위 메뉴 항목 전체 나열 + 유형(사이드바/상단) |
| 우리와의 관련성 | 어떤 메뉴/영역에서 참고할 수 있는가 |
| 핵심 관찰 | 가장 인상적인 IA 패턴 2~3가지 |

### Part B: 영역별 관찰 사실 통합

6개 리서치 영역별로 정리. 각 영역에서 다음 구조를 따를 것:

#### 영역 {N}: {영역명}

**1. 공통 패턴** (3개 이상 서비스에서 관찰된 것)
- 패턴 설명 + 해당 서비스 나열

**2. 차별화된 접근** (1~2개 서비스만의 독특한 방식)
- 접근 설명 + 해당 서비스 + 왜 독특한지

**3. 미결정 사항에 대한 관찰**
ia-research-plan.md 섹션 1의 "리서치에서 검증할 것" 4가지 질문에 대해:
- 스킬의 최적 위치 → 관찰된 사실 정리
- 예약 작업의 최적 위치 → 관찰된 사실 정리
- 관리자 vs 플랫폼 관리 분리 → 관찰된 사실 정리
- 빠진 필수 메뉴 → 관찰된 사실 정리

**4. Chat 연결점** (모든 영역에서 확인)
Chat은 이미 개발 중이므로 별도 영역으로 다루지 않지만, 각 영역에서 Chat과의 연결점을 명시적으로 정리:
- Chat → {이 영역}: 채팅에서 이 영역의 기능을 호출/참조하는 경로
- {이 영역} → Chat: 이 영역에서 생성한 결과가 채팅에 반영되는 경로
- 특히 확인할 것: Chat→대시보드(분석 결과 저장), Chat→스킬(스킬 선택/실행), Chat→데이터(자연어 질문→접근 제어)

**5. 시각 자료 핵심 선별**
각 영역에서 가장 참고 가치가 높은 스크린샷/영상 URL 상위 3~5개를 선별하고, 선별 이유를 한 줄로 명시

### Part C: 데이터 팩트 시트

서비스 간 비교를 위한 팩트 시트를 다음 항목별로 테이블로 만들어줘.
(관찰된 사실만 기입, 정보가 없으면 "미확인"으로 표시)

**테이블 1: GNB 비교**
| 서비스 | GNB 유형 | 최상위 메뉴 수 | 스킬/도구 위치 | 예약/자동화 위치 | Admin 분리 |

**테이블 2: 대시보드 비교**
| 서비스 | 홈=대시보드? | 커스텀 대시보드 수 | AI 인사이트 통합 | 위젯 유형 수 | 모니터링 위치 |

**테이블 3: 데이터 거버넌스 비교**
| 서비스 | 데이터 메뉴 위치 | 접근 제어 수준 | 시맨틱 레이어 | KB/RAG 위치 | 카탈로그 vs 파이프라인 |

**테이블 4: 스킬/도구 비교**
| 서비스 | 스킬 메뉴 위치 | 생성 방식 | 마켓 분리 | 에이전트-스킬 연결 | 버전 관리 |

**테이블 5: 예약/자동화 비교**
| 서비스 | 메뉴 위치 | 트리거 유형 | 스케줄 설정 방식 | 실행 이력 위치 | 수동 실행 |

**테이블 6: 관리자 비교**
| 서비스 | 테넌트 Admin 하위 | 플랫폼 Admin 하위 | AI 거버넌스 위치 | 감사 로그 | 역할별 가시성 |

**테이블 7: 역할별 메뉴 가시성 비교**
| 서비스 | 역할 구분 방식 | Admin 메뉴 처리(비관리자) | 역할별 분기 시점 | 기능 제한 방식(숨김/읽기전용/비활성) |

[출력 규칙]
- 관찰된 사실만 기록할 것. 결론, 권장안, 의견을 절대 포함하지 말 것
- "~해야 한다", "~가 좋다" 같은 당위 표현 금지
- "~로 보인다", "~인 것으로 관찰된다" 같은 관찰 표현만 사용
- 원본 리서치에서 근거를 찾을 수 없는 내용은 포함하지 말 것
- 각 사실에 출처 세션 번호를 표기 (예: [세션3])
```

## Step 2: 메뉴 간 연결성 종합 프롬프트

### 목적
영역별로 분리 리서치한 정보를 **제품 흐름 관점**으로 재조립한다.
메뉴 간 교차점과 데이터 흐름을 파악하여, Step 3에서 메뉴 구조를 확정할 때 "메뉴 간 관계"를 근거로 사용할 수 있게 한다.

### 프롬프트

```
[컨텍스트: Step 1의 출력물(통합 리서치 문서) + ia-research-plan.md]

Step 1에서 정리한 통합 리서치 문서를 바탕으로, 메뉴 간 연결성을 종합 분석해줘.
이 결과는 KonaI-Agent의 메뉴 구조를 확정하는 데 직접 사용할 근거야.

[전제]
- KonaI-Agent 현재 메뉴 후보 7개: 홈/대시보드, AI 채팅, 데이터, 스킬, 예약 작업, 관리자, 플랫폼 관리
- Chat은 이미 개발 중. 다른 메뉴와의 연결점만 확인 대상
- 데이터 구조: ERP DB → 뷰 테이블 + Neo4j 온톨로지 → 에이전트 접근

[정리 방식]

### Part A: 서비스별 메뉴 간 연결 맵

리서치 대상 서비스 중 Tier 1 전체(6개)와 Tier 2에서 연결성이 풍부한 서비스를 선별하여,
각 서비스의 메뉴 간 연결 경로를 전수 나열해줘.

#### {서비스명}

**연결 맵:**
```
{메뉴A} ──(연결 유형)──> {메뉴B}
  설명: 사용자가 A에서 B로 이동하는 구체적 경로/트리거
```

연결 유형 분류:
- **내비게이션**: 메뉴 A에서 B로 직접 이동하는 링크/버튼
- **데이터 흐름**: A에서 생성/설정한 데이터가 B에서 사용되는 관계
- **권한 흐름**: A에서 설정한 권한/정책이 B의 동작에 영향
- **결과 반영**: A에서의 실행 결과가 B에 표시되는 관계
- **컨텍스트 전달**: A에서의 작업 컨텍스트가 B로 전달되는 관계

### Part B: 공통 연결 패턴

3개 이상 서비스에서 공통으로 나타나는 메뉴 간 연결 패턴을 식별해줘.

각 패턴별로:
- **패턴명**: 한 줄 요약
- **연결 경로**: {출발} → {도착}
- **연결 유형**: 위 5가지 중 선택
- **관찰 서비스**: 해당 패턴이 나타난 서비스 나열
- **구현 방식**: 각 서비스가 이 연결을 어떻게 UI로 구현했는지 (버튼? 링크? 자동? 드래그?)

### Part C: KonaI-Agent 메뉴 후보 7개 기준 연결성 매핑

우리 메뉴 후보 7개를 행/열로 놓은 7×7 매트릭스를 만들어줘.
각 셀에 리서치에서 관찰된 연결 패턴을 매핑.

| → | 홈/대시보드 | AI 채팅 | 데이터 | 스킬 | 예약 작업 | 관리자 | 플랫폼 관리 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| **홈/대시보드** | - | | | | | | |
| **AI 채팅** | | - | | | | | |
| **데이터** | | | - | | | | |
| **스킬** | | | | - | | | |
| **예약 작업** | | | | | - | | |
| **관리자** | | | | | | - | |
| **플랫폼 관리** | | | | | | | - |

각 셀의 형식:
- 연결이 관찰된 경우: "[패턴명] (관찰 서비스 수/전체)" + 한 줄 설명
- 연결이 관찰되지 않은 경우: "미관찰"
- 해당 없는 경우: "—"

### Part D: 연결 밀도 분석

메뉴 후보별 연결 밀도를 정리:
- 각 메뉴의 **발신 연결 수** (이 메뉴에서 다른 메뉴로 나가는 연결)
- 각 메뉴의 **수신 연결 수** (다른 메뉴에서 이 메뉴로 들어오는 연결)
- 가장 연결이 밀집된 메뉴 쌍(pair) 상위 3개
- 연결이 거의 없는 메뉴 식별 (독립성이 높은 메뉴 → 하위 메뉴로 통합 가능성 시사)

### Part E: 스킬·예약 작업 위치 결정을 위한 연결 근거

리서치 계획서의 미결정 사항 중 "스킬의 최적 위치"와 "예약 작업의 최적 위치"에 대해,
연결성 관점에서 관찰된 근거를 정리:

**스킬 위치 관련:**
- 스킬이 독립 최상위 메뉴인 서비스에서 스킬↔다른 메뉴 연결 패턴
- 스킬이 설정 하위인 서비스에서 스킬↔다른 메뉴 연결 패턴
- 스킬이 에이전트 빌더 내부인 서비스에서 스킬↔다른 메뉴 연결 패턴

**예약 작업 위치 관련:**
- 예약이 독립 메뉴인 서비스에서의 연결 패턴
- 예약이 다른 메뉴 하위인 서비스에서의 연결 패턴

[출력 규칙]
- 관찰된 사실만 기록. 권장안/결론은 절대 포함하지 말 것
- 연결이 "있을 것 같다"는 추측 금지. 리서치에서 실제 관찰된 것만 기록
- 각 사실에 출처를 명시 (서비스명 + 세션 번호)
```

## Step 3: 메뉴 확정 프롬프트

### 목적
Step 1~2의 관찰 사실을 근거로, **메뉴 구조를 확정**한다.
이 단계에서는 의견과 판단이 포함된다 (Step 1~2와 다르게).

### 프롬프트

```
[컨텍스트: Step 1 출력(통합 리서치), Step 2 출력(연결성 맵), ia-research-plan.md]

지금까지 정리한 리서치 결과(통합 문서)와 연결성 분석을 바탕으로,
KonaI-Agent의 메뉴 구조를 확정하는 작업을 해줘.

이 단계에서는 관찰 사실에 기반한 **판단과 근거**를 함께 제시해야 해.

[전제 — 최우선 원칙]
1. 프로토타입 목적: 제품 구조의 타당성 검증 (데모 임팩트 아님)
2. 핵심 차별점: ① 엔터프라이즈 데이터 거버넌스 ② 올인원 AI 워크스페이스
3. 설계 원칙: 미니멀(핵심만) + 직관적(메뉴명으로 목적 전달) + 구조적 타당성(검증된 패턴 기반)
4. 데이터 구조: ERP DB → 뷰 테이블 + Neo4j 온톨로지 → 에이전트 접근
5. Chat은 이미 확정·개발 중

[작업 내용]

### Task 1: 미결정 사항 해결

리서치 계획서에서 "리서치로 결정"으로 남겨둔 4가지를 해결해줘.
각각에 대해 반드시 아래 형식을 따를 것:

#### {미결정 사항}

**결정**: {결론}
**근거 (관찰 사실)**:
1. {관찰 사실 1} — 출처: {서비스명}
2. {관찰 사실 2} — 출처: {서비스명}
3. ...

**반론 검토**:
- 반대 선택지: {대안}
```

## 프롬프트 사용 시 주의사항

### 1. 컨텍스트 관리

Deep Research 결과물이 6개 세션 × 수천 단어로 매우 길 수 있다.
Claude Web의 컨텍스트 윈도우에 모두 넣기 어려운 경우:

- **방법 A**: Step 1에서 요약을 먼저 만들고, Step 2~3에서는 요약본만 사용
- **방법 B**: Step 1의 Part C (팩트 시트 테이블)를 Step 2~3의 핵심 입력으로 사용
- **방법 C**: 영역별로 분할 실행 후 통합 (비추천 — 일관성 저하)

### 2. 결과 검토 체크포인트

각 Step 완료 후 다음을 확인:

**Step 1 완료 후:**
- [ ] 리서치 대상 서비스가 모두 포함되었는가
- [ ] 팩트 시트 테이블에 "미확인"이 과도하게 많지 않은가 (30% 이상이면 해당 영역 리서치 보충 고려)
- [ ] 원본 리서치에 없는 내용이 추가되지 않았는가

**Step 2 완료 후:**
- [ ] 7×7 매트릭스가 완성되었는가
- [ ] 연결 밀도 분석에서 극단적으로 고립된 메뉴가 있는가 (있으면 해당 메뉴 독립성 재검토)
- [ ] 스킬·예약 작업 위치 결정 근거가 충분한가

**Step 3 완료 후:**
- [ ] 미결정 사항 4가지가 모두 결정되었는가
- [ ] 각 결정에 반론 검토가 포함되었는가
- [ ] 하위 구조가 2단계 이상 깊어지는 메뉴가 없는가 (프로토타입에서는 2단계가 최대)
- [ ] 역할별 가시성 매트릭스에 모순이 없는가
- [ ] 자기 검증 4개 항목을 모두 통과하는가

### 3. 리서치 부족 시 대응

Step 1에서 정리할 때 특정 영역의 관찰 사실이 부족한 경우:
- 해당 영역에 "⚠️ 관찰 부족" 태그를 붙일 것
- Step 3에서 해당 영역의 결정은 "잠정 결정 — 추가 리서치 후 재검토 필요"로 표기
- 추가로 필요한 리서치 질문을 별도 섹션에 정리
