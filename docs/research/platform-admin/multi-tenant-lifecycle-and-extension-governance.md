## 개요

본 문서는 두 가지 핵심 주제를 통합한다:

1. **멀티테넌트 확장기능 관리 패턴** — 테넌트가 애드온 또는 확장기능을 발견, 활성화, 사용하는 방식
2. **테넌트 라이프사이클 UX 패턴** — 테넌트 생성부터 해지까지의 온보딩, 활성 운영, 위험 관리 전체 여정

두 주제는 긴밀히 연결되어 있다. 확장기능은 테넌트 구매 경험의 일부이며, 생성 후 초기 설정 단계에서 권장되기도 하고, 활성 운영 중 업그레이드/다운그레이드 의사결정에 영향을 미친다.

## 종합: 테넌트 생성부터 확장기능 배포까지 통합 여정

### 여정 맵

```
┌─────────────────────────────────────────────────────────────────┐
│ STAGE 1: 테넌트 생성 (Onboarding)                                  │
│ ├─ 위저드 단계 1-3 (필수 정보 수집)                                │
│ ├─ 위저드 단계 4 (선택: 샘플 확장기능 활성화)  ← 확장기능 진입점 #1  │
│ └─ 생성 완료 + 환영 이메일                                        │
├─────────────────────────────────────────────────────────────────┤
│ STAGE 2: 초기 설정 (Post-Creation Setup)                         │
│ ├─ 온보딩 체크리스트 제시                                         │
│ ├─ 샘플 에이전트 배포 (옵션)                                       │
│ ├─ 확장기능 권장 상품 노출  ← 확장기능 진입점 #2                   │
│ │  (테넌트 플랜 + 산업군 기반 AI 큐레이션)                         │
│ └─ 첫 성공 경험까지의 가이드                                      │
├─────────────────────────────────────────────────────────────────┤
│ STAGE 3: 활성 운영 (Active Lifecycle)                             │
│ ├─ 사용 추적 대시보드 (에이전트, 스킬, 확장기능)                    │
│ ├─ 플랜 변경 (업/다운그레이드)                                    │
│ ├─ 리소스 한도 조정                                              │
│ ├─ 추가 확장기능 발견/구매 UI  ← 확장기능 진입점 #3                │
│ │  (장터/마켓플레이스 통합)                                       │
│ └─ 건강 점수 기반 CS 추천                                        │
├─────────────────────────────────────────────────────────────────┤
│ STAGE 4: 위험 관리 (Risk Management)                              │
│ ├─ 일시정지/미결제 알림                                          │
│ ├─ 데이터 내보내기 지원                                          │
│ └─ 재활성화 경로                                                │
├─────────────────────────────────────────────────────────────────┤
│ STAGE 5: 해지 (Churn Defense)                                    │
│ ├─ 가치 리마인더 (활용 중인 확장기능 수 등)                        │
│ ├─ 대안 제시 (다운그레이드/일시정지)                               │
│ ├─ 이탈 설문 + 맞춤형 제안                                        │
│ └─ 데이터 보존 & 내보내기                                        │
└─────────────────────────────────────────────────────────────────┘
```

### 확장기능 거버넌스 관점 통합

테넌트 라이프사이클의 각 단계에서 **확장기능 권리(entitlement)** 정책이 다르게 적용된다.

| 단계 | 확장기능 권리 정책 | 거버넌스 관점 |
|------|-----------------|-------------|
| **테넌트 생성** | Trial: 기본 확장기능 3개만 허용 | 신규 가입자 보호, 학습곡선 완화 |
| | Standard: 구독 확장기능 최대 10개 | 스스로 선택, 자율 학습 유도 |
| | Enterprise: 무제한 (계약 협의) | 맞춤형 고객 지원 |
| **초기 설정** | 권장 확장기능 자동 활성화 가능 | 첫 성공 경험 가속 |
| | (테넌트 동의 하에) | 명시적 승인 필수 |
| **활성 운영** | 플랜 변경 시 권리 재조정 | Soft migration (기존 확장기능 유지, 신규 미활성) |
| | 비활용 확장기능 휴면 권장 | 낭비 방지, 관리 간소화 |
| **일시정지** | 모든 확장기능 차단 (프로비저닝만 유지) | 재활성화 시 복구 가능 상태 유지 |
| **해지** | 90일 보존 기간 동안 읽기만 허용 | 재가입 진입장벽 제거 |

## 1. 온보딩 — 신규 테넌트 생성

### 1.1 플랫폼별 온보딩 위저드 비교

#### Stripe Atlas (테넌트 = 사업체)

Stripe Atlas는 법인 설립이라는 복잡한 프로세스를 4단계 위저드로 압축했다. 첫 번째 단계에서 회사 정보(사업체 이름, 유형 C-Corp/LLC, 주소)를 수집하고, 두 번째 단계에서 공동창업자 정보와 지분 구조를 입력받는다. 세 번째 단계에서 법적 문서를 자동 생성하여 전자 서명을 받으며, 마지막 단계에서 결제를 처리한다. 법인 설립 완료 후에는 "Post-Incorporation Checklist"를 제공하여 은행 계좌 개설, EIN 취득, 83(b) 선거 파일링 등 후속 조치를 안내한다.

핵심 패턴으로는, 자동 문서 생성을 통해 수동 작업을 극적으로 줄이는 것, 그리고 법률 파트너(Cooley LLP)의 검증된 템플릿을 활용하여 사용자에게 신뢰감을 부여하는 것이 있다. 생성 후 즉시 사용 가능하지 않으며 Delaware 주 정부의 법인 등록 승인(약 2 영업일)이 필요하다.

#### Shopify (테넌트 = 스토어)

Shopify의 스토어 생성은 극도로 간소한 3단계로 구성된다. 이메일 주소 입력과 인증 코드 확인만으로 계정이 생성되고, 스토어 이름을 입력하면 바로 무료 체험이 시작된다. 유료 플랜 선택과 결제 수단 등록은 체험 기간 중 또는 종료 시점까지 지연된다.

이 접근법에서 주목할 점은 "결제 없는 진입"이다. 어떤 결제 정보도 요구하지 않고 즉시 관리자 대시보드에 접근할 수 있게 한다. 무료 체험 기간 동안 상품 등록, 테마 설정, 결제 게이트웨이 연결 등 핵심 기능을 체험하게 하여 "첫 성공 경험"까지의 거리를 최소화했다.

#### Slack (테넌트 = 워크스페이스)

Slack의 워크스페이스 생성은 3개의 핵심 질문으로 구성된다. 첫째, 팀/회사 이름(워크스페이스 이름으로 사용). 둘째, Slack을 주로 어떤 용도로 사용할 것인지(첫 번째 채널 이름으로 반영). 셋째, 팀원 초대(이메일 입력). 비밀번호 설정은 가입 시점이 아니라 6자리 인증 코드로 먼저 진입한 뒤 나중에 진행하도록 지연시킨다.

온보딩 완료 직후에는 Slackbot이 직접 메시지를 보내 첫 메시지 전송, 채널 탐색, 프로필 설정 등을 순차적으로 안내한다. 이 "제품 내에서 제품을 배우는" 접근법이 Slack 온보딩의 핵심이다. 성공 메시지와 함께 "Teach me something else" 버튼으로 추가 학습을 유도하여 도파민 히트를 활용한다.

#### Supabase (테넌트 = 프로젝트)

Supabase의 프로젝트 생성은 매우 개발자 친화적이다. Organization 선택(또는 생성) 후 프로젝트 이름, 데이터베이스 비밀번호, 리전 선택의 3가지 필드만 입력하면 프로비저닝이 시작된다. 무료 티어에서는 최대 2개의 활성 프로젝트를 허용하며, 초과 시 기존 프로젝트를 일시정지하거나 삭제해야 한다.

프로비저닝 후 대시보드에서 API 키, 연결 문자열, 클라이언트 라이브러리 설치 코드를 즉시 확인할 수 있어 "첫 쿼리 실행"까지의 시간이 매우 짧다.

#### Vercel (테넌트 = 팀)

Vercel의 팀 생성은 Git 제공자 연결을 출발점으로 한다. GitHub/GitLab/Bitbucket 계정을 연결하면 자동으로 레포지토리 목록을 가져오고, 템플릿 선택 또는 기존 레포 임포트로 첫 프로젝트를 즉시 배포한다. 팀 생성 시에는 팀 이름(slug)만 필수이고, 멤버 초대는 선택 사항이다. Pro 플랜은 14일 무료 체험을 제공하며, 체험 기간 중 결제 수단을 등록하지 않으면 자동으로 Hobby 플랜으로 다운그레이드된다.

#### Salesforce (테넌트 = Org)

Salesforce의 Org 프로비저닝은 엔터프라이즈 특성상 가장 복잡하다. 영업팀과의 상담을 거쳐 라이선스 유형(Sales Cloud, Service Cloud 등)을 결정하고, 계약 체결 후 Org가 프로비저닝된다. 관리자 계정 설정, SSO/SAML 구성, 사용자 프로비저닝(SCIM 연동 포함), 커스텀 프로필 및 권한 설정이 초기 설정의 주요 단계이다. 셀프서비스 생성이 아닌 영업 주도형 온보딩으로, Developer Edition이나 Sandbox를 통한 무료 평가판은 별도로 제공된다.

### 1.2 3계층 권한 모델 비교 (Slack / Teams / Salesforce)

코나체인이 멀티테넌트 거버넌스를 설계할 때 가장 직접 적용할 수 있는 권한 모델 비교.

#### Slack의 워크스페이스 권한 (간단)

Slack은 3계층 권한 모델로 설계되었다.

| 역할 | 권한 | 수량 제한 | 사용 사례 |
|------|------|----------|----------|
| **Workspace Owner** (소유자) | 모든 설정, 멤버 추가/제거, 앱 설치, 결제 관리, 워크스페이스 삭제 | 1명 또는 다중 (Slack for Enterprise) | 회사 대표, 관리자 |
| **Workspace Admin** (관리자) | 멤버 관리, 채널 설정, 일부 앱 설치, 감사 로그 조회 (결제/삭제는 불가) | 제한 없음 | 팀 리더, IT 담당자 |
| **Member** (멤버) | 메시지 전송, 채널 참여, 앱 사용 | 제한 없음 | 일반 사용자 |

권한의 특징:
- **계층이 단순**: 역할이 3가지로 제한되어 학습 곡선이 낮음
- **수직적 명확성**: Owner > Admin > Member 계층이 명확함
- **권한 위임 유연성**: Admin은 제한된 범위에서 자주 위임되는 작업 수행 가능. 하지만 Owner만이 최상위 결정(결제, 삭제)을 내림

#### Microsoft Teams의 Org/Team 2계층 권한 (복잡)

Teams는 조직(Organization) 차원의 권한과 팀(Team) 차원의 권한을 분리한다.

**조직 차원**:
- **전역 관리자 (Global Admin)**: Azure AD에서 관리하는 Microsoft 365 전사 관리자. Teams뿐 아니라 모든 Microsoft 365 서비스 제어.
- **Teams 서비스 관리자 (Teams Administrator)**: Teams 정책(통화, 모임, 메시징), 조직 차원의 앱 관리, 라이선스 할당

**팀 차원**:
- **팀 소유자 (Team Owner)**: 해당 팀의 모든 설정, 멤버 추가/제거, 채널 관리, 부분적 앱 설치
- **팀 멤버 (Team Member)**: 채널 접근, 파일 공유, 메시지 송수신

권한의 특징:
- **2계층 분리**: 조직 차원(IT) ↔ 팀 차원(비즈니스 사용자) 분리로 엔터프라이즈 거버넌스와 팀 자율성 균형
- **정책 기반 제어**: 각 팀이 같은 정책(예: 기본 탭 집합, 허용 앱) 내에서만 자율성 행사
- **계정 연동**: Azure AD와 깊게 통합되어 사용자 온보딩/오프보딩이 자동화됨

#### Salesforce의 계층적 역할 모델 (매우 복잡)

Salesforce는 **커스텀 프로필 + 권한 집합(Permission Set)** 이중 구조로 세밀한 제어를 제공한다.

**기본 역할 계층**:
```
System Administrator (최상위)
├─ Custom Profiles 파생 (프로필별 객체/필드 접근)
│  ├─ Sales Manager
│  ├─ Sales User
│  ├─ Support Agent
│  └─ Custom Role A
├─ Permission Sets (프로필 위의 추가 권한)
│  └─ "Can Edit Contract"
│  └─ "Can Approve Expense"
└─ Role Hierarchy (부서/팀별 데이터 공유)
```

권한의 특징:
- **매우 세밀한 제어**: 객체별(Account, Opportunity, Case 등), 레코드별, 필드별 접근 제어
- **조합 가능한 설계**: 프로필(기본 껍질) + 권한 집합(선택적 추가) + 역할 계층(데이터 공유) 3가지를 조합하여 복잡한 조직 구조를 표현
- **높은 학습 곡선**: Admin은 "권한 계산" 로직을 정확히 이해해야 함. 다른 시스템의 3배 이상 복잡함
- **용도**: 보험사, 은행, 제약 등 규제 엄격한 산업. 감사(Audit) 추적 필수

### 1.3 코나체인에 권장하는 권한 모델 (Slack 단순성 + Salesforce 유연성)

**3계층 기본 모델** (Slack 참고):

| 역할 | 권한 | 수량 |
|------|------|------|
| **테넌트 관리자** | 모든 설정, 사용자 추가/제거, 에이전트 배포, 확장기능 구매, 결제 | 1명 이상 |
| **팀 리더** | 할당된 에이전트의 설정, 팀 사용자 관리, 확장기능 활성화 | 제한 없음 |
| **일반 사용자** | 에이전트 실행, 스킬 사용, 대화 조회 | 제한 없음 |

**선택적 세부 권한** (Salesforce 참고):

- **확장기능 구매 권한**: 별도의 권한 집합으로 관리. 팀 리더 중 특정인만 활성화 가능
- **감사 로그 조회**: 규제 요구사항 대응용 (별도 권한 집합)
- **데이터 내보내기**: 기본값은 테넌트 관리자만, 팀 리더에게 위임 가능

### 1.4 온보딩 필수 vs 선택 정보 패턴

| 구분 | 필수 (위저드 내) | 선택/지연 (나중에 설정) |
|------|-----------------|----------------------|
| **공통** | 이메일, 테넌트명 | 로고, 브랜딩, 상세 프로필 |
| **Stripe Atlas** | 사업체 이름, 유형, 창업자 정보, 결제 | 은행 계좌, 세금 설정 |
| **Shopify** | 이메일, 스토어 이름 | 결제 수단, 상품, 플랜 선택 |
| **Slack** | 이메일, 팀 이름, 용도 | 비밀번호, 프로필 사진, 앱 연동 |
| **Supabase** | Org, 프로젝트명, DB 비밀번호, 리전 | 커스텀 도메인, RLS 정책 |
| **Vercel** | Git 제공자 연결, 팀명 | 멤버 초대, 도메인, 환경변수 |
| **Salesforce** | 관리자 계정, 라이선스 유형 | SSO, SCIM, 커스텀 객체 |

### 1.5 생성 후 "첫 성공 경험" 패턴

모든 플랫폼이 공유하는 핵심 원칙은 "가치 실현까지의 시간(Time-to-Value) 최소화"이다.

**체크리스트 패턴**: Stripe Atlas의 Post-Incorporation Checklist, Shopify의 스토어 설정 가이드가 대표적이다. 진행률 표시(Progress Bar)와 함께 완료된 항목에 체크마크를 보여주어 성취감을 자극한다.

**인터랙티브 투어 패턴**: Slack의 Slackbot 대화형 튜토리얼이 가장 정교하다. 사용자가 실제 기능을 조작하며 배우도록 유도하고, 각 단계 완료 시 즉각적 보상(성공 메시지, 칭찬)을 제공한다. 스킵 가능하게 만드는 것이 중요하다.

**샘플 데이터 패턴**: Supabase의 SQL 에디터에서 샘플 쿼리를 즉시 실행할 수 있게 하거나, Vercel의 템플릿 프로젝트로 첫 배포를 30초 내에 완료하게 하는 접근이 이에 해당한다.

### 1.6 코나체인 적용 권장안: 테넌트 생성 위저드 (4단계)

**Step 1 — 기본 정보** (필수)
- 회사명 (텍스트 입력)
- 도메인 (자동 제안 + 수동 입력, 중복 검증 인라인)
- 산업군 드롭다운 (AI 에이전트 활용 용도 파악용)
- 담당자 이름 / 이메일 / 전화번호

**Step 2 — 플랜 & 계약** (필수)
- 플랜 선택 카드 UI (Trial / Standard / Enterprise)
- 계약 기간 선택 (월간 / 연간)
- Trial 선택 시 → 계약 기간 자동 설정, 결제 스킵
- 리소스 한도 프리뷰 (선택한 플랜의 API 키 수, 사용자 수, 스토리지)

**Step 3 — 관리자 계정** (필수)
- 테넌트 관리자 이메일 (기본 정보에서 자동 채움)
- 초기 비밀번호 설정 또는 초대 링크 발송 선택
- SSO 연동 여부 토글 (활성화 시 → IdP 설정 안내로 분기)

**Step 4 — 초기 설정** (선택, 스킵 가능)
- 태그 추가 (자유 입력, 관리 편의용)
- 메모 입력 (영업/CS 메모)
- **샘플 확장기능 자동 활성화 토글** (플랜별 기본값, 테넌트 동의 필수)
  - Trial: "기본 분석 대시보드" + "에이전트 모니터링" 2개만
  - Standard: "기본 분석 대시보드" + "에이전트 모니터링" + "팀 협업 도구" 3개
  - Enterprise: 맞춤형 선택 (영업과 협의)
- API 키 자동 생성 토글 (기본값: 활성)

**생성 후 즉시 동작**
- 상태: Trial 또는 Active로 자동 설정
- 테넌트 관리자에게 환영 이메일 + 온보딩 체크리스트 링크 발송
- 관리자(우리 팀) 대시보드에 새 테넌트 카드 즉시 반영
- 건강 점수 초기값 자동 산정

## 2. 활성 운영

### 2.1 플랜 업/다운그레이드 패턴

#### 업그레이드

대부분의 SaaS 플랫폼은 **인라인 업그레이드**를 선호한다. Vercel은 대시보드 내 Settings → Billing에서 업그레이드 버튼을 제공하며, 결제 수단 입력 후 즉시 적용된다. Shopify 역시 Settings → Plan에서 플랜 변경이 가능하고, 변경 시 남은 기간에 대한 비례 정산(proration)을 자동 처리한다.

핵심 패턴은 "즉시 적용 + 비례 정산"이다. 업그레이드 시점부터 새로운 기능과 한도가 즉시 활성화되고, 현재 빌링 사이클의 남은 기간만큼 차액을 청구한다.

#### 다운그레이드

다운그레이드는 더 복잡한 UX를 요구한다. Vercel에서 Pro → Hobby 다운그레이드 시 모든 팀 멤버(원래 소유자 제외)가 제거되고, 연결된 Store 및 Domain을 사전에 이전해야 한다. Shopify도 다운그레이드 전 현재 플랜 전용 기능을 사용 중인 경우 경고를 표시한다.

핵심 패턴은 "사이클 종료 시 적용 + 영향 범위 사전 안내"이다. 다운그레이드는 현재 빌링 사이클 종료 시 적용되며, 상실되는 기능과 데이터에 대한 명확한 안내를 제공한다.

#### 계약 갱신

엔터프라이즈 SaaS에서 계약 갱신은 보통 만료 90일 전부터 알림을 시작한다. 자동 갱신이 기본인 경우 만료 30일 전에 변경/취소 가능 기간을 안내하고, 수동 갱신인 경우 갱신 링크와 함께 플랜 변경 옵션을 제시한다.

### 2.2 리소스 한도 변경 패턴

Vercel의 Spend Management가 좋은 모델이다. 월간 크레딧의 75% 소진 시 자동 알림을 발송하고, 100% 초과 시 on-demand 과금으로 전환되거나 Hard Limit 설정에 따라 프로젝트를 자동 일시정지한다. 사용자는 대시보드에서 지출 한도를 자유롭게 조정할 수 있다.

Supabase는 Organization 기반 과금으로, 프로젝트별 리소스(DB 크기, 스토리지, 대역폭)가 자동으로 스케일되되 Free 티어에서는 엄격한 상한을 적용한다.

### 2.3 확장기능과 플랜 변경의 상호작용

**업그레이드 시**: 새 플랜에서 허용되는 추가 확장기능을 활성화 제안한다.

예: Standard → Enterprise로 업그레이드 시, 기존에 차단되었던 "고급 분석 모듈"을 자동 활성화할지 묻는 모달.

**다운그레이드 시**: 현재 활성화된 확장기능이 다운그레이드 후 지원되지 않는 경우, 사전 경고를 제시한다.

예: Enterprise → Standard로 다운그레이드 시, "고급 분석 모듈" 3개가 비활성화될 예정이라는 경고.

이를 **Soft migration** 원칙이라 한다. 즉, 비활성화할 확장기능이 있다면:
1. **비활성화 예정일** 명시
2. **데이터 내보내기** 옵션 제공 (비활성화 전)
3. **복구 경로** 안내 (향후 업그레이드 시 복구 가능)

### 2.4 코나체인 적용 권장안: 활성 운영 관리

**플랜 변경 플로우 (테넌트 상세 패널 내 인라인)**
- 현재 플랜 카드 옆에 "플랜 변경" 버튼 배치
- 클릭 시 슬라이드 패널로 플랜 비교 테이블 표시
- 업그레이드: 즉시 적용, 비례 정산 금액 실시간 미리보기
- 다운그레이드: "다음 갱신일(YYYY-MM-DD)부터 적용됩니다" 안내
- 다운그레이드 시 초과 리소스 경고 (예: "현재 API 키 15개 사용 중 → Standard 플랜 한도 10개")
- **확장기능 영향 표시**: 다운그레이드로 비활성화될 확장기능 목록

**리소스 한도 변경 (테넌트 상세 패널 → 리소스 탭)**
- 슬라이더 또는 숫자 입력으로 개별 한도 조정 (API 키 수, 사용자 수, 스토리지)
- 플랜별 기본값 vs 커스텀 오버라이드 명확히 구분
- 변경 이력 타임라인 표시

**계약 갱신 알림 (자동화)**
- 만료 90일 전: 대시보드 배너 + 이메일
- 만료 30일 전: 갱신/변경/해지 옵션 모달
- 만료 7일 전: 긴급 알림 (건강 점수에 반영)

**확장기능 관리 (테넌트 상세 패널 → 확장기능 탭)** (신규)
- 현재 활성 확장기능 목록 (플랜별 색상 구분)
- 플랜 업그레이드 시 "추천 확장기능 3개" 카드 표시
- 비활용 확장기능 휴면 권장 (비용 절감 기회)

## 3. 위험 관리 — 일시정지와 재활성화

### 3.1 플랫폼별 일시정지 패턴

#### Supabase의 자동 일시정지

Supabase 무료 티어에서는 7일간 활동이 없는 프로젝트가 자동으로 일시정지된다. 일시정지 전에 경고 이메일을 발송하며, 일시정지된 프로젝트는 대시보드에서 "Paused" 뱃지로 표시된다. 재활성화는 대시보드에서 "Restore" 버튼 클릭으로 가능하지만, 최신 버전의 API 서버와 Postgres로 업데이트될 수 있어 호환성 문제 가능성을 안내한다.

주목할 점은, 유료(Pro) 프로젝트는 일시정지할 수 없다는 제한이다. 이 정책은 사용자들의 상당한 불만을 야기했으며, 이는 일시정지 정책 설계 시 유료/무료 테넌트 간 형평성을 고려해야 한다는 교훈을 준다.

#### Shopify의 "Pause and Build"

Shopify는 완전 해지 대신 "Pause and Build" 옵션을 제공한다. 월 $9의 최소 요금으로 관리자 대시보드 접근은 유지되지만, 고객의 구매는 불가능해진다(상품 열람만 가능). 이는 일시적으로 판매를 중단하되 스토어 데이터를 보존하려는 사용자를 위한 중간 단계이다.

#### Vercel의 사용량 초과 일시정지

Vercel은 Hobby 플랜에서 사용량 한도를 초과하면 팀과 프로젝트를 자동으로 일시정지한다. Pro 플랜으로 업그레이드하면 일시정지가 즉시 해제되며, 비활성 기간에 대한 과금은 없다. Spend Management의 Hard Limit을 설정한 Pro 사용자도 지출 한도 도달 시 자동 일시정지를 선택할 수 있다.

### 3.2 일시정지 상태의 테넌트 경험

일시정지 상태에서 테넌트에게 보여줘야 하는 핵심 요소들은 다음과 같다.

**명확한 상태 표시**: "귀사의 계정이 [사유]로 인해 일시정지되었습니다"라는 전체 화면 또는 상단 배너 메시지. 일시정지 사유(미결제/관리자 수동/사용량 초과)별로 메시지를 분기한다.

**데이터 접근 범위**: 읽기 전용 접근을 허용할 것인지(대시보드 조회, 데이터 내보내기), 완전 차단할 것인지는 플랫폼마다 다르다. Shopify의 Pause and Build는 관리자 접근을 유지하는 반면, Vercel의 일시정지는 배포를 완전 중단한다.

**해결 경로 안내**: 미결제의 경우 결제 수단 업데이트 버튼, 사용량 초과의 경우 플랜 업그레이드 버튼을 즉각적으로 제공하여 자력 복구가 가능하게 한다.

### 3.3 재활성화 플로우

업계 표준으로 두 가지 모델이 존재한다.

**자동 재활성화**: 결제 완료 즉시 서비스가 복원된다. Vercel이 이 모델을 사용하며, Pro 업그레이드 시 일시정지 상태가 자동으로 해제된다. 사용자 경험이 가장 빠르고 매끄럽다.

**수동 승인 재활성화**: 결제 완료 후 관리자(플랫폼 운영팀)의 확인을 거쳐 복원된다. 엔터프라이즈 고객이나 보안 이슈로 일시정지된 경우에 적합하다.

### 3.4 확장기능 일시정지 정책

일시정지된 테넌트의 확장기능 처리 정책:

- **활성 확장기능은 비활성화** (제공 서버의 리소스 보호)
- **재활성화 시 복구**: 일시정지 전 활성 확장기능 목록을 메타데이터로 보존했다가, 재활성화 시 원래 상태로 복구
- **데이터 보존**: 90일 동안 확장기능 데이터 유지 (재활성화 시 손실 없음)

### 3.5 코나체인 적용 권장안: 일시정지/재활성화

**일시정지 트리거 (2경로)**

경로 A — 관리자 수동 일시정지:
- 테넌트 상세 패널 → 상태 드롭다운에서 "Suspended" 선택
- 확인 모달: 사유 선택(계약 위반 / 보안 이슈 / 기타) + 메모
- 테넌트 관리자에게 자동 이메일 발송 (사유 + 문의 안내)

경로 B — 자동 일시정지 (미결제):
- 결제 실패 시 → 3일 후 1차 알림 → 7일 후 2차 알림 → 14일 후 자동 Suspended
- 각 단계에서 테넌트 관리자와 우리 팀 양쪽에 알림

**일시정지 상태 테넌트 화면**
- 로그인 시 전체 화면 오버레이: "계정이 일시정지되었습니다"
- 사유별 분기 메시지:
  - 미결제: "결제 수단을 업데이트하면 즉시 재활성화됩니다" + 결제 버튼
  - 관리자 수동: "관리자에 의해 일시정지되었습니다. 문의: [연락처]"
- 데이터 내보내기 버튼은 항상 접근 가능 (데이터 인질 방지)
- **확장기능 상태**: "다음 확장기능이 일시정지 중입니다: [목록]"

**재활성화 플로우**
- 미결제 해소 → 자동 재활성화 (Active 상태 복원, 모든 기능 즉시 복구)
- 관리자 수동 일시정지 → 관리자가 상태를 Active로 변경해야 복원
- 재활성화 시 테넌트 관리자에게 "서비스가 복원되었습니다" 이메일 발송
- **확장기능 복구**: 일시정지 전 활성이었던 확장기능을 사전 동의 하에 자동 재활성화

## 4. 해지

### 4.1 플랫폼별 해지 플로우 비교

#### Shopify — 셀프서비스 + 다단계 확인

Shopify의 해지는 Settings → Plan → "Cancel plan"에서 시작된다. 해지 전 "Pause and Build" 대안을 먼저 제안하고, 사용자가 계속 진행하면 해지 사유를 드롭다운에서 선택하게 한다. 최종 확인으로 비밀번호를 입력해야 해지가 완료된다. 해지는 현재 빌링 사이클 종료 시 효력이 발생하며, 스토어 데이터는 2년간 보존되어 이 기간 내에는 재개설이 가능하다. Shopify Plus 고객은 셀프서비스 해지가 불가하고 지원팀에 연락해야 한다.

#### Vercel — 다운그레이드 우선 제안

Vercel은 팀 삭제보다 Hobby 플랜으로의 다운그레이드를 우선 제안한다. 결제를 중단하면서도 프로젝트에 대한 접근은 유지할 수 있게 하여 완전 해지를 방지한다. 팀 삭제를 원할 경우 Account Management에서 진행 가능하다.

#### 업계 공통 해지 방지 전략

SaaS 업계 전반의 조사 결과, 효과적인 해지 방지 전략은 다음과 같은 요소를 포함한다.

**가치 리마인더**: Zoom은 해지 시도 시 "475개 클라우드 녹화에 대한 접근을 잃게 됩니다"처럼 사용자 계정의 실제 사용 데이터를 보여주어 상실감을 구체화한다. Asana는 미활용 기능을 하이라이트하여 아직 발견하지 못한 가치를 알린다.

**대안 제시**: 해지 대신 (1) 플랜 다운그레이드, (2) 일시정지(Pause), (3) 기간 한정 할인을 순차적으로 제안하는 것이 표준이다. 업계 데이터에 따르면 일시정지를 선택한 구독자의 60~80%가 재활성화하며, 다운그레이드 구독자는 평균 7~8개월 더 유지된다. 잘 설계된 해지 플로우는 전체 해지 시도의 20~40%를 방어한다.

**이탈 설문**: 해지 사유 수집은 모든 플랫폼에서 필수 단계이다. 평균 6개 정도의 사전 정의된 사유를 제공하고 "기타" 옵션으로 자유 서술을 허용한다. 핵심은 설문이 너무 길어지지 않도록 하는 것이다. 추가 질문 하나가 이탈 방어율을 약 6.7%씩 낮춘다는 데이터가 있다.

**법적 고려사항**: 캘리포니아의 2025년 자동 갱신법(AB 2863)은 해지 흐름 내에서 단 하나의 보유 제안만 허용하고, "클릭으로 해지" 버튼을 반드시 제공하도록 요구한다. 다크 패턴(해지를 의도적으로 어렵게 만드는 UX)은 규제 위험을 수반한다. Amazon은 다크 패턴 사용에 대해 $25억 합의금을 지불한 사례가 있다.

### 4.3 확장기능 해지 정책

테넌트가 완전히 해지될 때 확장기능 처리:

- **즉시 비활성화**: 모든 활성 확장기능의 프로비저닝 중단

### 4.4 코나체인 적용 권장안: 해지 플로우

**해지 요청 경로 (2트랙)**

트랙 A — 셀프서비스 (Trial / Standard):
- 테넌트 관리자가 설정에서 "서비스 해지" 요청
- 4단계 해지 플로우:
  1. **가치 리마인더**: "현재 에이전트 N개가 활성 상태이며, 이번 달 M건의 대화를 처리했습니다. 활성 확장기능 X개를 사용 중입니다."
  2. **대안 제시**: 다운그레이드 / 일시정지 / 기간 한정 할인(건강 점수 기반 동적 제안)
  3. **이탈 설문**: 사유 선택 (가격 / 기능 부족 / 다른 솔루션 / 사용 안 함 / 기타) + 자유 서술
  4. **최종 확인**: "해지는 [현재 사이클 종료일]에 효력이 발생합니다" + 비밀번호 재입력
- 해지 요청 시 우리 팀에 자동 알림 (Slack/이메일) → CS 개입 기회

트랙 B — 관리자 처리 (Enterprise):
- 테넌트 관리자가 해지 의사를 전달
- 우리 팀 관리자가 테넌트 상세 패널에서 해지 프로세스 시작
- 데이터 내보내기 완료 확인 후 해지 실행

**데이터 보존 정책**
- 해지 후 90일간 데이터 보존 (읽기 전용 접근 가능)
- 보존 기간 중 재활성화 가능 (결제 재개 시 즉시 복원)
- 90일 경과 후 영구 삭제 (삭제 30일 전 최종 알림)

**데이터 내보내기**
- 해지 확정 전 "데이터 내보내기" 단계를 필수 안내
- 내보내기 형식: JSON (에이전트 설정, 대화 이력, 분석 데이터) + CSV (사용자 목록, 연락처)
- 내보내기 완료 확인 체크박스 (해지 진행 전)

**확장기능 해지 안내**
- "다음 확장기능을 사용 중입니다: [목록]" 명시
- "해지 시 90일 보존 기간 내에 재가입하면 복구 가능합니다" 안내

## 5. 관리자 뷰 vs 테넌트 관리자 뷰

### 5.1 화면 구성 원칙

**우리 팀 관리자 뷰 (슈퍼 어드민)**

모든 테넌트를 일괄 관리하는 관점이다. 테넌트 목록 테이블에서 상태별 필터링(Active/Trial/Suspended/Inactive), 건강 점수 정렬, 계약 만료일 기준 정렬이 가능해야 한다. 각 테넌트 행에서 원클릭으로 상세 패널 진입, 상태 변경, 메모 추가가 가능해야 한다.

핵심 대시보드 위젯: 상태별 테넌트 분포, 이번 달 만료 예정 계약, 건강 점수 하위 10% 테넌트 리스트, 최근 생성/해지 테넌트 타임라인.

**테넌트 관리자 뷰 (고객사 어드민)**

자사 테넌트 범위 내에서 사용자 관리, 설정 변경, 사용량 모니터링을 수행하는 관점이다. 자기 테넌트의 플랜, 리소스 한도, 사용량 현황, 결제 내역에 접근할 수 있어야 한다. 플랜 변경 요청, 해지 요청 등 라이프사이클 액션의 시작점은 여기에 위치한다.

### 5.2 자동화 가능 영역

| 영역 | 자동화 방식 | 수동 필요 시점 |
|------|-----------|--------------|
| 테넌트 생성 | 위저드 완료 시 자동 프로비저닝 | Enterprise 플랜은 관리자 승인 |
| SSO 프로비저닝 | SCIM 연동 시 사용자 자동 생성/삭제 | IdP 초기 설정 |
| 확장기능 프로비저닝 | 플랜 선택 시 기본 확장기능 자동 활성화 | 추가 확장기능은 테넌트 수동 선택 |
| 리소스 스케일링 | 사용량 기반 자동 확장 (플랜 한도 내) | 한도 초과 시 플랜 변경 |
| 결제 실패 처리 | 자동 재시도 (3회) → 자동 일시정지 | 장기 미결제 시 수동 해지 |
| 계약 갱신 | 자동 갱신 + 사전 알림 | 조건 변경 시 수동 협의 |
| 건강 점수 | 사용량/로그인 빈도/에이전트 활성도 기반 자동 산정 | CS 개입 트리거 임계값 수동 설정 |
| 해지 방어 | 건강 점수 기반 동적 제안 자동 생성 | 고가치 고객 수동 CS 대응 |

## 6. 멀티테넌트 확장기능 관리 패턴 (심화)

### 6.1 3가지 권한 모델 비교: Slack vs Teams vs Salesforce

이전 섹션 1.2에서 기술한 권한 모델을 확장기능 관리 관점에서 재검토한다.

#### 확장기능 설치 권한 (3가지 모델)

**모델 1: Slack (간단, 단일 소유자 제어)**

```
workspace owner
  └─ 모든 앱/통합 설치 권한
     └─ admin은 '승인된 앱'만 설치 가능
        └─ member는 read-only
```

**모델 2: Teams (계층적, 정책 기반)**

```
전역 관리자(IT)
  └─ 테넌트 전체 정책 설정 (허용 앱 목록 + 블록리스트)
     └─ 팀 소유자
        └─ 정책 범위 내에서 앱 설치/제거
           └─ 팀 멤버 (read-only)
```

**모델 3: Salesforce (아주 복잡, 객체 기반)**

```
시스템 관리자
  ├─ 모든 AppExchange 앱 설치 + 승인
  ├─ 앱별 설치 권한 프로필 정의
  │  └─ "예: Sales Cloud Admin만 설치 가능"
  └─ 앱 버전 관리 + 자동 업데이트 정책
```

#### 확장기능 거버넌스 복잡도 비교

| 관점 | Slack | Teams | Salesforce |
|------|-------|-------|-----------|
| **학습 곡선** | 매우 낮음 (3역할) | 중간 (2계층 + 정책) | 높음 (프로필 + 권한 집합 + 역할 계층) |
| **정책 표현력** | 낮음 | 중간 (정책 기반) | 높음 (프로필 + AppExchange 설치 권한) |
| **감사(Audit)** | 기본 로그 | 상세 감사 로그 | 매우 상세 (필드 레벨) |
| **적합한 산업** | 스타트업, 창의 조직 | 중견기업 (폴리시 중시) | 규제 산업 (금융, 보험, 의료) |

### 6.2 확장기능 발견 경로 (Entrypoints)

사용자가 확장기능을 발견하고 설치하는 경로는 일반적으로 5가지이다.

**Entry Point 1: 온보딩 (위저드 Step 4)**
- "권장 확장기능 자동 활성화"
- 테넌트 플랜 + 산업군 기반 AI 큐레이션
- 테넌트 관리자 명시적 동의 필수
- 예: "귀사는 고객상담 업체인 것 같습니다. '고객 대화 분석' 확장기능을 활성화하시겠습니까?"

**Entry Point 2: 초기 설정 대시보드 ("첫 성공" 체크리스트)**
- 온보딩 완료 후 테넌트 관리자에게 제시되는 체크리스트
- "권장 확장기능 N개" 섹션
- "지금 추가" 버튼으로 마켓플레이스로 유도
- 체크리스트 완료율 게이미피케이션 (프로그레시 바)

**Entry Point 3: 활성 운영 대시보드 (마켓플레이스 탭)**
- 테넌트 관리자 대시보드 좌측 네비게이션에 "마켓플레이스" 탭
- 필터: 업종별, 가격대별(Free/Paid), 별점, 추천
- "내 플랜에 맞는 확장기능" 배지로 구매 가능 여부 표시
- 무료 확장기능은 "지금 설치" 버튼 → 즉시 활성화
- 유료 확장기능은 "구매하기" → 결제 프로세스

**Entry Point 4: 플랜 업그레이드 직후**
- 플랜 변경 완료 후 "축하합니다! 이제 X개의 추가 확장기능을 사용할 수 있습니다"
- 업그레이드로 새로 가능해진 확장기능 카드 표시
- "추천 확장기능 3개" 미니 마켓플레이스

**Entry Point 5: 우리 팀 관리자 (고객사 추천)**
- 우리 팀이 건강 점수/사용량 분석 후, "이 고객이 이 확장기능을 쓰면 좋을 것 같음" → CS 이메일 발송
- 이메일에 마켓플레이스 링크 포함
- 테넌트 관리자가 링크 클릭 → 마켓플레이스 해당 확장기능으로 자동 스크롤
- 개인화 큐레이션 효과

```

```

## 7. 종합 구현 로드맵

### Phase 1 — 테넌트 생성 위저드 + 기본 확장기능 (최우선)

Step 4에 확장기능 선택 항목 추가. Trial/Standard/Enterprise별 기본 확장기능 세트 정의.

### Phase 2 — 상태 전환 플로우 + 확장기능 일시정지

일시정지 시 모든 확장기능 자동 비활성화 + 재활성화 시 복구.

### Phase 3 — 플랜 변경 & 확장기능 Soft Migration

업그레이드 시 새 확장기능 권리 노출, 다운그레이드 시 영향 범위 경고.

### Phase 4 — 마켓플레이스 (확장기능 발견)

마켓플레이스 UI 구현. 필터, 검색, 카드, 상세 모달. 무료 설치 자동화.

### Phase 5 — 해지 플로우 & 확장기능 보존

가치 리마인더에 "활성 확장기능 X개" 포함. 90일 보존 정책 구현.

### Phase 6 — 고급: 테넌트 관리자 포털 & 마켓플레이스 API

고객사가 직접 접근하는 포털. 마켓플레이스 API로 3rd-party 개발자 확장기능 공급 가능.

## 8. 핵심 UX 원칙 요약

1. **마찰 최소화, 가치 최대화**: 생성 위저드의 필수 필드를 최소화하고, 선택 정보는 나중에 수집한다. Slack의 3질문 온보딩이 모범 사례이다.

2. **투명한 상태 커뮤니케이션**: 테넌트 현재 상태, 변경 영향, 복구 방법을 항상 명확하게 전달한다. Supabase의 일시정지 이메일 시퀀스가 참고할 만하다.

3. **가역적 전환 우선**: 완전 해지보다 다운그레이드/일시정지를 먼저 제안한다. Shopify의 "Pause and Build"가 좋은 사례이며, 일시정지 선택자의 60~80%가 재활성화한다.

4. **데이터 인질 금지**: 일시정지/해지 상태에서도 데이터 내보내기는 항상 가능해야 한다. 이는 신뢰를 구축하고 규제 요건을 충족한다. 확장기능도 마찬가지: 제거 시에도 데이터 내보내기 옵션을 제공한다.

5. **이중 관점 설계**: 모든 라이프사이클 화면을 "우리 팀 관리자"와 "테넌트 관리자" 양쪽 관점에서 설계한다. 같은 데이터라도 접근 범위와 수행 가능한 액션이 다르다.

6. **자동화 + 인간 개입 균형**: 정형적 전환(결제 실패 → 알림 → 일시정지)은 자동화하되, 고가치 고객의 이탈 위험이나 보안 이슈는 반드시 인간 판단을 거치도록 한다.

7. **다크 패턴 회피**: 해지를 의도적으로 어렵게 만들지 않는다. 캘리포니아 AB 2863과 같은 규제를 준수하고, 윤리적 설계로 장기적 신뢰를 구축한다.

8. **확장기능 거버넌스의 단순성**: 확장기능 설치 권한은 Slack의 3계층 모델처럼 단순하게 시작하되, 필요시 Salesforce식 권한 집합으로 확장 가능하도록 설계한다. 초기에는 과도하게 복잡하면 안 된다.

9. **다중 발견 경로**: 확장기능 발견을 온보딩, 초기 설정, 플랜 업그레이드, 활성 운영, 우리 팀 추천 등 5가지 경로로 제공한다. 단일 마켓플레이스 입구에만 의존하면 발견이 낮다.

10. **보존을 통한 이탈 방지**: 해지 또는 확장기능 제거 시에도 90일 보존 기간을 두어 재가입/복구 경로를 제공한다. 데이터 손실 공포가 이탈의 큰 이유이다.
