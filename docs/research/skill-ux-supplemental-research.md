## 3. 갭별 조사 계획

### G1. 아바타 스택 — 협업 도구에서의 "사용자 존재" 표현 패턴

**배경**: 1차 R3 리서치에서는 마켓플레이스/카탈로그(npm, Chrome, VS Code 등)를 조사했고, 아바타 스택을 쓰는 서비스가 없었다. 그러나 v7의 "활성 멤버"는 마켓플레이스 맥락이 아니라 **팀 협업** 맥락이다. 협업 도구에서 "누가 이 리소스를 사용/참여하고 있는가"를 아바타로 표현하는 패턴은 별도로 존재한다.

**조사 대상** (마켓플레이스가 아닌 협업 도구):

| 서비스 | 관찰 포인트 |
|--------|-------------|
| Figma (에디터 상단바) | 현재 접속 중인 협업자 아바타 스택. 표시 개수, 오버플로, 클릭 동작 |
| Google Docs (상단바) | 현재 편집 중인 사용자 아바타. 실시간 vs 비동기 표시 차이 |
| Notion (페이지 상단) | 페이지 멤버/편집자 아바타. 공유 설정과의 관계 |
| Linear (이슈 리스트) | Assignee/Subscriber 아바타 표시. 테이블 컬럼 내 배치 |
| GitHub (PR 리뷰어) | Reviewer 아바타 스택. 겹침 오프셋, 최대 표시 수 |

**핵심 질문**:
1. "실시간 접속자" 아바타 스택 vs "이 리소스를 구독/활성화한 사람" 아바타 스택 — 어떤 맥락에서 각각 사용되는가?
2. 테이블 셀 내(좁은 공간)에서 아바타 스택을 쓰는 실제 서비스가 있는가? 있다면 최대 표시 수, 겹침 px, 오버플로 처리는?
3. v7의 "활성 멤버 아바타 스택"은 위 패턴 중 어디에 해당하며, 설계 타당성은?

**기대 산출물**: v7 아바타 스택의 설계 유형 분류 + 유사 패턴 2~3개 + 차이점 및 조정 권장사항

### G2. 트렌드 임계값 — 소규모 데이터셋의 변동 감지 기준

**배경**: 1차 R3 리서치에서 "7일 50% 증가 시 ↑ 표시" 기준을 권장했지만, 근거가 불충분하다. 특히 팀 규모(주간 0~200 호출)에서는 1→2 호출만으로 100% 증가가 되는 등 소규모 데이터의 노이즈 문제가 있다.

**조사 대상**:

| 서비스/도구 | 관찰 포인트 |
|-------------|-------------|
| Datadog | Alert threshold 기본값, anomaly detection 감도 설정 |
| Grafana | Alert conditions, evaluation period, threshold 타입 |
| Google Analytics | "Insights" 자동 알림의 변동 감지 기준 |
| Amplitude | "Anomaly detection" 임계값, 최소 샘플 사이즈 |
| VS Code Marketplace | "Trending" 배지 부여 조건 (공개된 범위 내) |

**핵심 질문**:
1. 소규모 데이터셋(일 0~30건)에서 의미 있는 변동을 감지하려면 최소 기간과 최소 절대값 기준은?
2. "노이즈 필터링"을 위한 최소 호출 수 하한선(예: "주 5회 이상일 때만 트렌드 표시")을 적용하는 서비스가 있는가?
3. 퍼센트 변동(%) vs 절대 변동(+N건) — 소규모에서 어느 지표가 더 유의미한가?

**기대 산출물**: 팀 규모(0~200 호출) 맥락의 트렌드 표시 조건 수정안 (최소 호출 수 하한, 감지 기간, 임계값)

### G3. 복사 확산 방지 — 팀 카탈로그의 복사본 관리 가드레일

**배경**: 1차 R5에서 복사 시 이름 규칙, 배치 위치, 원본 관계 표시는 잘 다뤘다. 그러나 시간이 지나 팀 카탈로그에 복사본이 과다 누적되는 시나리오의 관리 전략이 부족하다. v7은 승인 절차 없이 자유 복사를 허용하므로, 장기적으로 카탈로그 품질 저하 위험이 있다.

**조사 대상**:

| 서비스 | 관찰 포인트 |
|--------|-------------|
| Google Drive (공유 드라이브) | 파일 복사 제한 정책, 관리자 권한, 스토리지 쿼터 |
| Notion (팀 워크스페이스) | 페이지 복제 제한, 아카이브/정리 기능, 템플릿 vs 일반 페이지 |
| Figma (팀 라이브러리) | 컴포넌트 publish 권한, 중복 감지, 라이브러리 정리 도구 |
| Slack (워크플로우 빌더) | 워크플로우 복사 권한, 비활성 워크플로우 자동 아카이브 |
| GitHub (Organization) | Fork 관리, archived repository 정책, repository template 제한 |

**핵심 질문**:
1. "자유 복사 + 사후 정리" vs "복사 시 승인/제한" — 어떤 모델이 팀 규모에서 더 효과적인가?
2. 복사본 과다 시 "같은 원본에서 파생된 복사본 그룹핑" 또는 "중복 힌트"를 제공하는 서비스가 있는가?
3. 비활성 복사본 자동 아카이브/정리 패턴이 있는가? 있다면 비활성 기준(기간, 호출 수)은?

**기대 산출물**: v7 복사 모델의 장기 관리 전략 권장안 (즉시 적용 vs v8 이후 검토 항목 분류)

### G4. 패널 내 파일 탐색기 폭 — 실측 기반 최소 폭 검증

**배경**: 1차 R6에서 "400px 패널 내 파일 목록 + 콘텐츠 동시 표시"를 전제로 설계했고, 적응형 패턴(1파일=숨김, 2~4=플랫, 5+=트리)을 권장했다. 그러나 400px이라는 수치의 적합성이 실제 서비스 측정 없이 제시되었다.

**조사 대상**:

| 서비스 | 측정 항목 |
|--------|-----------|
| GitHub | 파일 트리 사이드바 기본 폭, 최소 리사이즈 폭 |
| VS Code | Explorer 사이드바 기본 폭, 최소 폭, 에디터 최소 폭 |
| Linear | 이슈 상세 패널 기본 폭, 최소 폭 |
| Jira | 이슈 패널 기본 폭 |
| Notion | 사이드 peek 패널 기본 폭 |

**핵심 질문**:
1. "콘텐츠 패널" 유형의 슬라이드 패널 기본 폭은 업계에서 몇 px인가?
2. 파일 목록(세로) + 콘텐츠(아래)를 세로 배치할 때 최소 가독 폭은?
3. v7의 400~500px 범위가 적절한지, 조정이 필요한지?

**기대 산출물**: 실측 기반 패널 폭 비교표 + v7 권장 폭 확정 또는 수정

## G1. 아바타 스택 — 협업 도구에서의 "사용자 존재" 표현 패턴

### 배경
1차 리서치에서 마켓플레이스/카탈로그 6개 서비스를 조사한 결과, **아바타 스택을 사용하는 서비스가 없었습니다**. 그러나 v7의 "활성 멤버"는 마켓플레이스가 아니라 **팀 협업** 맥락이므로, 협업 도구의 아바타 패턴을 별도로 조사해야 합니다.

### 조사 대상 (협업 도구 5개)
1. **Figma** (에디터 상단바) — 현재 접속 중 협업자 아바타 스택
2. **Google Docs** (상단바) — 현재 편집자 아바타
3. **Notion** (페이지/데이터베이스) — 멤버 프로퍼티, People 컬럼
4. **Linear** (이슈 리스트) — Assignee/Subscriber 아바타, 테이블 셀 내 배치
5. **GitHub** (PR 리뷰어, Collaborators) — 아바타 스택 겹침 패턴

### 조사 항목
1. 각 서비스에서 아바타 스택이 사용되는 **맥락** 분류: (a) 실시간 접속자 (b) 리소스 참여자/구독자 (c) 할당된 담당자
2. **테이블 셀 내**(좁은 공간) 아바타 스택의 실제 사례: 최대 표시 수, 아바타 크기(px), 겹침 오프셋(px), "+N" 오버플로 처리
3. v7의 "활성 멤버 아바타 스택"이 위 분류 중 어디에 해당하는지 분석 + 설계 타당성 평가

### 출력 형식
서비스별 분석 → 맥락 유형 분류표 → v7 설계 타당성 판정 + 조정 권장사항

## G2. 트렌드 임계값 — 소규모 데이터셋의 변동 감지 기준

### 배경
1차 리서치에서 "최근 7일 호출 수가 이전 7일 대비 50% 이상 증가 시 ↑ 아이콘 표시"를 권장했으나, 근거가 불충분합니다. 특히 **팀 규모(주간 0~200 호출)**에서는 절대값이 작아서:
- 1회→2회 = 100% 증가 (의미 없는 노이즈)
- 5회→8회 = 60% 증가 (약간의 관심 증가?)
- 20회→35회 = 75% 증가 (실질적 트렌드)

이처럼 퍼센트 기반 임계값만으로는 소규모 데이터의 노이즈를 걸러낼 수 없습니다.

### 조사 대상
1. **Datadog** — Alert threshold 기본값, anomaly detection 최소 데이터 포인트 요건
2. **Grafana** — Alert conditions, evaluation period, "for" duration 설정
3. **Google Analytics 4** — Insights 자동 알림의 변동 감지 기준, anomaly detection 알고리즘 공개 정보
4. **Amplitude** — Anomaly detection 임계값, 최소 이벤트 수 요건
5. **VS Code Marketplace** — "Trending" 배지 부여 조건 (공개된 범위)

### 조사 항목
1. 소규모 데이터셋(일 0~30건)에서 의미 있는 변동을 감지하기 위한 **최소 기간**과 **최소 절대값** 기준
2. 노이즈 필터링을 위한 **최소 하한선**(예: "주 5회 이상일 때만 트렌드 표시")을 적용하는 사례
3. 퍼센트 변동(%) vs 절대 변동(+N건) — 소규모에서 어느 지표가 더 의미 있는지, 또는 두 가지를 조합하는 사례

### 출력 형식
서비스별 감지 기준 비교표 → 소규모 데이터 적용 시 문제점 분석 → v7 트렌드 표시 조건 수정안 (최소 호출 수 하한, 감지 기간, 임계값 구체적 숫자 포함)

## G3. 복사 확산 방지 — 팀 카탈로그의 복사본 관리 가드레일

### 배경
v7은 "모든 스킬을 자유롭게 복사, 복사본은 독립적, 승인 절차 없음" 모델입니다. 1차 리서치(R5)에서 복사 시 이름 규칙·배치 위치·원본 관계 표시는 잘 다뤘으나, **시간 경과 후 팀 카탈로그에 복사본이 과다 누적되는 시나리오**의 관리 전략이 부족합니다.

시나리오 예시:
- 팀원 10명이 각각 "매출 분석" 스킬을 복사 → 10개의 유사 스킬이 카탈로그에 존재
- 3개월 후 사용되지 않는 복사본이 20개 이상 누적 → 카탈로그 탐색 효율 저하

### 조사 대상 (팀 공유 도구 5개)
1. **Google Drive** (공유 드라이브) — 파일 복사 제한 정책, 스토리지 쿼터, 관리자 권한
2. **Notion** (팀 워크스페이스) — 페이지 복제 제한 여부, 아카이브/휴지통 정리 기능, 템플릿 vs 일반 페이지 구분
3. **Figma** (팀 라이브러리) — 컴포넌트 publish 권한, 라이브러리 정리 도구, 중복 감지
4. **Slack** (워크플로우 빌더) — 워크플로우 복사 권한, 비활성 워크플로우 관리
5. **GitHub** (Organization) — Fork 관리 정책, archived repository, template repository 제한

### 조사 항목
1. "자유 복사 + 사후 정리" vs "복사 시 승인/제한" — 각 서비스의 모델과 그 이유
2. 복사본 과다 시 관리 도구: (a) 동일 원본 파생 그룹핑 (b) 중복 감지/힌트 (c) 사용되지 않는 항목 자동 아카이브
3. 비활성 항목 아카이브 기준: 기간(예: 90일 미사용), 호출 수(예: 0회), 소유자 퇴사 등

### 출력 형식
서비스별 복사 관리 모델 비교표 → v7에 즉시 적용할 가드레일(v7 scope) + 장기 검토 항목(v8+) 분류 → 구체적 UX 권장사항

## G4. 패널 폭 실측 — 슬라이드 패널과 파일 탐색기의 최소 폭 검증

### 배경
v7 슬라이드 패널 내에서 파일 목록 + 콘텐츠를 세로로 배치합니다. 1차 리서치에서 "400~500px" 범위를 권장했으나, 실측 데이터가 부족합니다.

### 조사 대상
1. **Linear** — 이슈 상세 패널 기본 폭, 최소 리사이즈 폭
2. **Jira** — 이슈 상세 패널 기본 폭, 전체 확장 전환 기준 폭
3. **Notion** — 사이드 peek 패널 기본 폭, 리사이즈 범위
4. **GitHub** — 코드 뷰 파일 트리 사이드바 기본 폭, 최소 폭
5. **VS Code** — Explorer 사이드바 기본 폭, 에디터 최소 폭

### 조사 항목
1. 각 서비스의 콘텐츠 패널/사이드 패널 **기본 폭**(px)과 **최소 폭**(px) — 공식 문서 또는 DevTools 측정 기반
2. 파일 목록(세로) + 콘텐츠(아래) 세로 배치 시 **최소 가독 폭** — 마크다운 렌더링, 코드 하이라이팅이 깨지지 않는 최소 폭
3. 패널 폭별 콘텐츠 적응 전략: (a) 줄바꿈 (b) 가로 스크롤 (c) 레이아웃 전환

### 출력 형식
서비스별 폭 측정 비교표(px 단위) → v7 패널 폭 400~500px 범위의 적합성 판정 → 확정 권장 폭 또는 수정안
