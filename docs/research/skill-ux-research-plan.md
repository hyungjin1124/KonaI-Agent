## 2. 기존 리서치에서 즉시 벤치마킹 가능한 항목

추가 리서치 없이 기존 문서에서 v7 설계에 바로 적용할 수 있는 인사이트를 정리한다.

### 2.1 버전 이력 + AI 변경 인사이트 (영역 D) — 즉시 적용 가능

**출처**: `ai-summary-block-ui-patterns.md`, `skill-versioning-with-eval-results.md`

기존 리서치에서 도출된 5가지 AI 요약 배치 패턴(diff 위 인라인, 에디터 인라인, 타임라인 봇 코멘트, 접을 수 있는 패널, 콘텐츠 하단 자동 요약) 중, v7이 채택한 "타임라인 내 인라인 블록" 패턴(Distill.io 참조)은 이미 리서치 기반으로 설계되었다. 추가로 벤치마킹할 수 있는 세부 패턴:

- **Distill.io**: 파란 배경 + 좌측 보더로 AI 콘텐츠를 시각 구분 → v7의 accent 보더 + 배경색 설계에 직접 반영 가능
- **gpt-commit-summarizer**: 변경 유형별 계층(파일 수준 → 전체 요약) 패턴 → v7의 태그 리스트 구조와 유사
- **Slack AI 스레드 요약**: 접힘/펼침 + "외 N건" 패턴 → v7의 이전 버전 접힘 규칙에 반영 가능
- **Anthropic eval 시스템**: iteration별 통과율/시간/토큰 스냅샷 → 향후 스킬 품질 지표로 확장 가능

### 2.2 채팅 기반 스킬 생성 워크플로우 (영역 H) — 즉시 적용 가능

**출처**: `skill-creator-ux-workflow-patterns.md`, `anthropic-skill-creator-2026-march-update.md`

- **Intent Capture → Interview → Write → Test → Iterate** 5단계 루프가 v7의 "채팅에서 생성" 설계와 직접 대응
- **4가지 핵심 질문** (목표, 트리거 조건, 출력 형식, 테스트 여부)을 채팅 내 스킬 생성 가이드로 활용 가능
- **Manus의 conversation-to-skill 패키징**: 성공적인 대화를 스킬로 변환하는 UX → v7에서 이미 참조
- **Relevance AI의 "Invent"**: 설명만으로 자동 생성하는 UX → 비개발자 대상 스킬 생성 가이드에 참조

### 2.3 스킬 분류 및 탐색 (영역 G 일부) — 부분 적용 가능

**출처**: `03-skill.md`, `03-skill-more.md`

- **ChatGPT GPT Store**: 카드 기반 + 카테고리 필터 + 리더보드 → 대규모 탐색에 적합하나, v7의 팀 규모(10~50개)에는 과도
- **ChatGPT Enterprise 관리 뷰**: 테이블 기반 + 사용 통계 컬럼 + 접근 권한 필터 → **v7 테이블 설계에 직접 참조 가능** (가장 유사한 패턴)
- **Dify Marketplace**: 카드 + 태그 필터 + 타입 필터 → 카테고리 필터 UX에 참조 가능
- **Copilot Studio 통합 Tools 탭**: 다양한 도구 유형을 하나의 뷰에서 관리 → 통합 관리 관점에서 참조

### 2.4 스킬 배포 채널 (장기 로드맵용)

**출처**: `skill-discovery-and-distribution-patterns.md`

개인→팀→조직→공개 4단계 여정 아키텍처가 정리되어 있다. v7은 "팀" 단계에 집중하지만, 후순위 항목인 "교차 팀 스킬 탐색"과 "스킬 벤치마크 테스트"의 로드맵 설계 시 즉시 참조 가능하다.

## 3. 추가 리서치 계획

기존 리서치에서 커버되지 않았거나 깊이가 부족한 영역에 대한 조사 계획이다.

### R1. 테이블 + 슬라이드 패널 레이아웃 패턴

**목적**: v7의 핵심 화면 구조인 "테이블 + 우측 슬라이드 패널"의 UX 모범 사례를 조사하여 테이블 축약 규칙, 패널 전환 애니메이션, 전체 확장 패턴 등을 구체화한다.

**조사 대상**:
- Linear (이슈 리스트 + 상세 패널)
- Jira (보드/리스트 뷰 + 상세 패널)
- Notion (데이터베이스 뷰 + 사이드 peek)
- Airtable (테이블 + 확장된 행 패널)
- Salesforce (리스트 뷰 + 레코드 패널)

**조사 항목**:
1. 테이블→패널 전환 시 컬럼 축약 규칙 (어떤 컬럼을 숨기는가, 어떤 기준으로)
2. 패널 폭 비율 (고정/가변, 드래그 리사이즈 여부)
3. 패널 내 섹션 구성 순서 (헤더, 메타데이터, 본문, 액션)
4. 전체 확장(full-page) 전환 패턴 (모달 vs 라우트 변경 vs 인라인 확장)
5. 키보드 네비게이션 (↑↓로 행 이동, Enter로 패널 열기, Esc로 닫기)
6. 패널 열린 상태에서 다른 행 클릭 시 전환 애니메이션

**기대 산출물**: 각 서비스의 패널 구조 목업 비교 + v7 설계에 대한 구체적 권장사항

---

### R2. diff 뷰어 UX 패턴 심화

**목적**: v7의 원문 비교(unified inline diff) 설계를 구체화하기 위해, 텍스트 기반 diff 뷰어의 UX 패턴을 조사한다. 특히 비개발자가 마크다운/자연어 변경을 이해하는 맥락에 적합한 패턴을 찾는다.

**조사 대상**:
- GitHub (코드 diff — unified/split 토글)
- Google Docs (제안 모드 — 인라인 추적 변경)
- Notion (페이지 히스토리 — 변경 하이라이트)
- WordPress (포스트 리비전 비교)
- Confluence (페이지 비교)

**조사 항목**:
1. 삭제/추가/변경의 시각적 표현 방식 (색상, 취소선, 배경, 인라인 vs 블록)
2. 변경 없는 영역의 접힘/펼침 규칙 (전후 몇 줄 유지, 접힌 영역 표시 방식)
3. 비개발자 대상 diff에서의 단어 단위 vs 줄 단위 비교
4. 좁은 패널 폭(400~500px)에서의 diff 표시 전략
5. 변경 요약↔원문 비교 간 앵커 링크/스크롤 연동 사례
6. 마크다운 원문 diff vs 렌더링된 diff 비교 (어떤 것을 보여줄 것인가)

**기대 산출물**: 비개발자 대상 자연어 diff 뷰어 설계 권장안

---

### R3. 사용량 지표 및 소셜 프루프 표시 패턴

**목적**: v7 테이블의 "호출 수"와 "활성 멤버" 컬럼 설계를 고도화하기 위해, 제품 내 사용량 지표와 소셜 프루프를 표시하는 UX 패턴을 조사한다.

**조사 대상**:
- npm (주간 다운로드 수 표시)
- Chrome 웹 스토어 (사용자 수, 평점)
- VS Code 마켓플레이스 (설치 수, 평점, 트렌드)
- Figma Community (복사 수, 좋아요)
- Slack App Directory (설치 기업 수)
- ChatGPT Enterprise 관리 뷰 (채팅 수, 접근 권한)

**조사 항목**:
1. 숫자 표시 형식 (정확한 수 vs "1.2K" 축약 vs 상대 표현 "이번 주 인기")
2. 트렌드 표시 여부 (↑↓ 아이콘, 스파크라인 차트, "지난 주 대비 +30%")
3. 아바타 스택 패턴 (최대 표시 수, "+N" 오버플로, 클릭 시 전체 목록)
4. 사용량 지표의 테이블 컬럼 폭과 정렬 방향
5. "아무도 사용하지 않는" 스킬의 표시 전략 (0회 호출, 활성 멤버 없음)

**기대 산출물**: 호출 수·활성 멤버 컬럼의 구체적 렌더링 규격 + 빈 상태 처리 가이드

---

### R4. 팀 규모 스킬 탐색 효율성 패턴

**목적**: v7이 타겟하는 팀 규모(10~50개 스킬)에서의 탐색 효율성을 높이기 위한 패턴을 조사한다. 기존 리서치는 대규모 마켓플레이스(수백~수천) 위주라서 소규모 카탈로그에 맞는 패턴이 부족하다.

**조사 대상**:
- Slack 워크스페이스의 커스텀 이모지/워크플로우 관리
- Notion 팀 템플릿 갤러리
- Figma 팀 라이브러리 (컴포넌트/스타일)
- Google Workspace 확장 프로그램 (팀용)
- Retool 내부 앱 카탈로그

**조사 항목**:
1. 소규모(10~50개) 카탈로그에서 카테고리 필터 vs 자유 검색의 효율성
2. "활성화/비활성" 그룹 분리 vs 단일 리스트 + 정렬/필터의 장단점
3. "인기순" vs "최근 수정순" vs "내가 자주 쓰는 순" 기본 정렬의 사용자 선호
4. 팀원의 사용 패턴이 스킬 발견에 미치는 영향 (소셜 디스커버리)
5. 빈 상태 → 첫 스킬 추가까지의 온보딩 플로우

**기대 산출물**: 소규모 팀 카탈로그에 최적화된 탐색 UX 설계 권장안

---

### R5. 파일/에셋 복사 UX 패턴

**목적**: v7의 "복사" 모델(모든 스킬에서 복사, 자동 넘버링, 독립적)을 구체화하기 위해, 파일 및 에셋 복사의 UX 패턴을 조사한다.

**조사 대상**:
- Google Drive (파일 사본 만들기)
- Figma (컴포넌트/파일 Duplicate)
- GitHub (Repository Fork + Template Repository)
- Notion (페이지 복제)
- Canva (디자인 복사)

**조사 항목**:
1. 복사 시 이름 생성 규칙 (접미사 패턴: "Copy of X", "X (2)", "X — 복사본")
2. 복사 직후 사용자 행동 유도 (이름 편집 포커스, 즉시 편집 모드, 알림)
3. 원본과의 관계 표시 방식 (출처 링크, "포크됨" 뱃지, 관계 미표시)
4. 복사본의 목록 내 배치 위치 (원본 바로 아래, 목록 최상단, 자동 정렬 위치)
5. 대량 복사 방지 또는 중복 관리 전략

**기대 산출물**: 복사 인터랙션의 마이크로 UX 설계 (이름 규칙, 피드백, 후속 행동 유도)

### R6. 파일 탐색기 + 콘텐츠 뷰어 통합 패턴

**목적**: v7 슬라이드 패널의 "스킬 콘텐츠" 영역(파일 목록 + 읽기 전용 콘텐츠 뷰)의 구체적 UX를 설계하기 위해, 파일 탐색기와 콘텐츠 뷰어가 통합된 패턴을 조사한다.

**조사 대상**:
- GitHub 코드 뷰어 (파일 트리 + 코드 렌더링)
- VS Code 탐색기 + 에디터 (사이드바 + 탭 에디터)
- Notion 페이지 내 첨부 파일 뷰어
- GitBook (문서 사이드바 + 콘텐츠)
- Storybook (컴포넌트 트리 + 프리뷰)

**조사 항목**:
1. 파일 트리 vs 플랫 리스트 (깊이가 1~2단계일 때 어느 것이 적합한가)
2. 기본 선택 파일 규칙 (README 우선, 최근 수정 파일 우선 등)
3. 파일 타입별 렌더링 전략 (마크다운 렌더링, 코드 하이라이팅, 이미지 프리뷰, PDF 뷰어)
4. 패널 폭 제약(400~500px) 하에서의 파일 목록 + 콘텐츠 레이아웃
5. 코드/마크다운의 줄바꿈 + 가로 스크롤 처리

**기대 산출물**: 스킬 콘텐츠 뷰어의 레이아웃 및 렌더링 규격

## 5. 리서치 방법론

### 5.1 웹 리서치 (주요 방법)

각 조사 대상 서비스의 공식 문서, 블로그, 제품 화면을 직접 탐색하여 UI 패턴을 분석한다.

- **공식 문서/블로그**: 각 서비스의 디자인 시스템 문서, UX 블로그, 변경 로그
- **실제 화면 캡처**: 가능한 경우 실제 제품을 사용하여 화면 구성 확인 (Chrome 브라우저 활용)
- **디자인 시스템 참조**: Linear, Notion 등의 공개된 디자인 시스템에서 컴포넌트 패턴 참조

### 5.2 산출물 형식

각 리서치는 다음 구조의 마크다운 문서로 작성한다:

```
# {리서치 제목}
> 조사 기준일, 대상 서비스, 목적

## 1. 서비스별 분석
### 1-N. {서비스명}
- 화면 구조 (ASCII 목업 또는 스크린샷 링크)
- 인터랙션 패턴
- 장점/단점

## 2. 패턴 비교
(비교 표)

## 3. KonaI-Agent 적용 권장안
- 채택할 패턴 + 근거
- v7 설계 변경이 필요한 부분 (있다면)
- 구현 시 주의사항
```

### 5.3 기존 리서치와의 관계

- 각 리서치 문서는 `docs/research/skill-management/` 하위에 저장
- 기존 리서치 문서의 관련 섹션을 참조하되, 중복 작성하지 않음
- 리서치 완료 후 `03-skill-ia.md`에 반영할 설계 변경 사항이 있으면 별도 제안 문서로 정리
