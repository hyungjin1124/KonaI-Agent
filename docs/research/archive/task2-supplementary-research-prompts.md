## 보완이 필요한 2개 영역

### 영역 1: AI 에이전트 플랫폼 관리 대시보드 특화 패턴

기존 리서치는 Vercel/Supabase/Retool(배포/DB/내부 도구)의 범용 SaaS 패턴을 다뤘지만, AI 에이전트 플랫폼 고유의 모니터링 메트릭(토큰 사용량, 에이전트 실행 성공률, 모델별 비용, 프롬프트/스킬 사용 빈도)을 대시보드에 어떻게 표현하는지에 대한 참조가 없다.

### 영역 2: 테넌트 온보딩 및 라이프사이클 관리 UX

"테넌트 추가" 버튼 클릭부터 첫 에이전트 실행까지의 온보딩 플로우, 테넌트 일시정지/재활성화/해지 플로우, 계약 갱신/플랜 변경 플로우에 대한 단계별 UX 참조가 없다.

## Claude Web 리서치 프롬프트

### 프롬프트 1: AI 에이전트 플랫폼의 관리자 대시보드 — 테넌트별 에이전트 모니터링 및 비용 추적

```
AI 에이전트를 서비스로 제공하는 플랫폼(LLM-as-a-Service, Agent-as-a-Service)에서, 플랫폼 관리자가 테넌트별 에이전트 사용 현황을 모니터링하고 비용을 추적하는 대시보드 UX 패턴을 조사해줘.

조사 대상 (AI 에이전트 / LLM 플랫폼):

1. OpenAI Platform Dashboard (organization usage 페이지)
   - 테넌트(organization/project)별 토큰 사용량 시각화
   - 모델별(GPT-4, GPT-4o, o1 등) 비용 분리 추적
   - 일별/주별/월별 사용량 추세 차트
   - API 키별 사용량 브레이크다운
   - 비용 제한(Usage limits) 설정 UI

2. Anthropic Console (Admin Dashboard)
   - Workspace별 사용량 모니터링
   - 모델별 토큰 소비 및 비용 추적
   - Rate limit 모니터링
   - 멤버/API 키 관리

3. AWS Bedrock Console
   - 모델 호출 메트릭 (호출 수, 레이턴시, 에러율)
   - 프로비저닝된 처리량 모니터링
   - CloudWatch 통합 대시보드
   - 비용 탐색기 (모델별, 리전별)

4. LangSmith / LangFuse (에이전트 관찰 도구)
   - 에이전트 실행 트레이스 (입력→추론→도구 호출→출력 전체 경로)
   - 실행 성공/실패율, 평균 레이턴시, 토큰 효율
   - 프롬프트/스킬별 사용 빈도 및 성능 비교
   - 비용 추적 (실행당 비용 계산)

5. Helicone / PromptLayer (LLM 프록시/모니터링)
   - 요청별 비용 추적
   - 캐시 히트율
   - 사용자/세션별 분석

각 플랫폼에서 다음을 정리해줘:

핵심 메트릭:
- 어떤 지표를 KPI 카드로 보여주는가 (상단 요약)
- 어떤 차트 유형으로 추세를 시각화하는가
- 테넌트(조직/프로젝트)별 브레이크다운은 어떤 UI 패턴인가

비용 추적:
- 모델별 비용을 어떻게 분리 표시하는가
- 토큰 입력/출력 비용을 어떻게 구분하는가
- 비용 제한(budget/limit) 설정 UI는 어떻게 되어 있는가
- 비용 초과 시 어떤 액션이 가능한가 (알림, 차단, 자동 다운그레이드)

에이전트 특화:
- 에이전트 실행 트레이스를 어떻게 시각화하는가
- 실행 성공/실패/타임아웃 비율을 어떻게 보여주는가
- 어떤 도구/스킬이 가장 많이 호출되었는지 분석하는 뷰가 있는가

우리 시스템 컨텍스트:
- 멀티테넌트 AI 에이전트 플랫폼 (코나체인)
- 현재 PlatformAdminView의 "사용량 및 알림" 탭에 API 호출 수, 토큰 소비량, 에이전트 세션 수, 임계치 초과 테넌트 수를 KPI로 보여주고 있음
- 현재 차트: 30일 API 호출 추세(테넌트별 스택 면적 차트), 30일 토큰 소비 추세(입력/출력 스택 바 차트)
- 현재 테이블: 테넌트별 API 호출/토큰/에이전트 실행/제한% 테이블
- 5개 알림 규칙 (토큰 임계치, API Rate Limit, 비용 초과, 에러율 이상, 비활성 테넌트)
- 부족한 부분: 모델별 비용 분리, 에이전트 실행 트레이스, 스킬별 사용 빈도, 예측적 비용 알림

기존 구현의 강점을 유지하면서 어떤 메트릭과 UI를 추가하면 경쟁력 있는 플랫폼 관리 대시보드가 되는지 구체적으로 권장해줘.
파일명: ai-platform-admin-dashboard-patterns.md
```

### 프롬프트 2: SaaS 테넌트 온보딩 및 라이프사이클 관리 UX

```
멀티테넌트 SaaS 플랫폼에서 테넌트(고객사)의 전체 라이프사이클을 관리하는 UX 패턴을 조사해줘.

조사할 라이프사이클 단계:

1. 온보딩 (신규 테넌트 생성)
   - 테넌트 생성 위저드의 단계 구성 (회사 정보 → 플랜 선택 → 관리자 계정 → 초기 설정)
   - 어떤 정보를 필수로 수집하는가
   - 생성 후 즉시 사용 가능한가, 승인 절차가 있는가
   - "첫 성공 경험"까지의 가이드 (체크리스트, 투어, 샘플 데이터)

2. 활성 운영
   - 플랜 업/다운그레이드 플로우 (인라인 vs 별도 페이지, 즉시 적용 vs 사이클 종료 시)
   - 계약 갱신 알림 및 프로세스
   - 리소스 한도 변경 (API 키 추가, 사용자 수 증가, 스토리지 확장)

3. 위험 관리
   - 테넌트 일시정지 (관리자가 수동으로 / 미결제로 자동)
   - 일시정지 상태에서 테넌트에게 보이는 화면
   - 재활성화 플로우 (결제 완료 → 자동 재활성화 / 수동 승인)

4. 해지
   - 해지 요청 플로우 (셀프서비스 vs 관리자 처리)
   - 데이터 보존 기간 안내
   - 해지 후 데이터 내보내기 옵션
   - 해지 방지 전략 (할인 제안, 다운그레이드 제안)

조사 대상 플랫폼:
- Stripe Atlas (테넌트 = 사업체) 온보딩 위저드
- Salesforce (테넌트 = org) 프로비저닝
- Shopify (테넌트 = store) 생성 및 해지 플로우
- Slack (워크스페이스) 생성 및 라이프사이클
- Supabase (프로젝트) 생성 위저드와 일시정지/삭제 플로우
- Vercel (팀) 생성 및 해지

각 단계에서:
- 화면 구성 (위저드 스텝 수, 각 스텝의 입력 필드)
- 필수 vs 선택 정보 구분
- 자동화 가능한 부분 (기본값 자동 설정, SSO 연동 시 자동 프로비저닝)
- 관리자(우리 팀)와 테넌트 관리자(고객사) 각각이 보는 화면

우리 시스템 컨텍스트:
- 멀티테넌트 AI 에이전트 플랫폼 (코나체인)
- 현재 테넌트 관리 탭에 "테넌트 추가" 버튼이 있지만 생성 위저드가 미구현
- 현재 테넌트 상태: Active / Trial / Suspended / Inactive (4종)
- 테넌트별 데이터: 회사명, 도메인, 플랜, 건강 점수, 연락처, 계약 기간, API 키, 리소스 한도, 태그, 메모
- 현재 상세 패널에서 이 정보를 보여주지만, 생성/수정/상태 전환 플로우가 없음

테넌트 라이프사이클의 각 단계별로 우리 시스템에 적용할 수 있는 구체적 위저드/모달/페이지 구성을 권장해줘.
파일명: tenant-lifecycle-ux-patterns.md
```

## 참고: 추가 리서치가 불필요한 영역

기존 리서치에서 이미 충분히 다룬 부분:
- ✅ 테넌트 관리 구조 (Vercel 팀/Supabase 조직/Retool Spaces 비교)
- ✅ RBAC 패턴 (역할 세분화, 프로젝트 스코프, 권한 매트릭스)
- ✅ 사용량 알림 단계별 설계 (Vercel Spend Management 참조)
- ✅ 빌링 모델 비교 (크레딧/시간/시트 기반)
- ✅ 내비게이션 패턴 (사이드바, 커맨드 팔레트, 듀얼 사이드바)
- ✅ Best Practice 종합 (Progressive Disclosure, Empty State, 접근성)
