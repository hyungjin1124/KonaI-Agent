## G1. 아바타 스택 — 협업 도구에서의 "사용자 존재" 표현 패턴

### 1-1. 서비스별 분석

**Figma (에디터 상단바)**  
Figma는 실시간 접속자 아바타를 상단 툴바 우측에 원형으로 나란히 표시한다. 각 아바타에는 고유 색상이 배정되며, 해당 색상은 캔버스 위의 커서와 연동된다. 아바타를 클릭하면 해당 사용자의 뷰로 이동하는 "Follow Mode"가 활성화되고, 마우스오버 시 사용자 이름이 툴팁으로 표시된다. Figma의 아바타는 겹침(overlap) 없이 간격을 두고 배치되며, 접속자가 많을 경우 "+N" 카운터로 축약된다. 아바타 크기는 약 24~28px이다. 이 패턴은 순수하게 "실시간 접속자(presence)" 맥락에 해당하며, 파일을 닫으면 아바타가 즉시 사라진다. (출처: Figma Help Center — "Present to collaborators using spotlight")

**Google Docs (상단바)**  
Google Docs 역시 현재 문서를 열어둔 사용자를 상단 우측에 원형 아바타로 표시한다. 편집 중인 사용자에게는 색상 테두리가 부여되며, 이 색상은 문서 내 커서 위치와 연동된다. Google Docs는 접속자가 적을 때 아바타를 나란히 배치하고, 일정 수 이상이면 "+N" 카운터를 사용한다. 이 역시 "실시간 접속자" 패턴이며, 문서를 닫으면 표시에서 제거된다. 아바타 크기는 약 28~32px로 Figma보다 약간 크다. (출처: 업계 관례 기반, DevTools 추정치)

**Notion (데이터베이스 People 컬럼)**  
Notion은 두 가지 맥락에서 아바타를 사용한다. 첫째, 페이지 상단의 실시간 접속자 표시(Figma/Google Docs와 유사)이고, 둘째는 데이터베이스의 "Person" 프로퍼티 컬럼이다. 데이터베이스 테이블 셀 내에서 Person 프로퍼티는 단일 아바타(20~24px) 또는 다중 아바타 스택으로 표시된다. 테이블 셀 내 아바타는 겹침 오프셋 약 -6px~-8px로 스택되며, 셀 폭이 좁으면 최대 2~3개 표시 후 "+N"으로 처리한다. 이 맥락은 "리소스 참여자/담당자" 패턴에 해당한다. (출처: Notion 공식 릴리즈 2022-07-20, 업계 관례 기반)

**Linear (이슈 리스트)**  
Linear는 이슈 리스트 및 보드 뷰에서 각 이슈의 Assignee를 단일 원형 아바타로 표시한다. 아바타 크기는 약 20px이며, 리스트 뷰의 행 우측에 배치된다. Linear는 이슈당 단일 담당자 모델이므로 아바타 "스택"은 사용하지 않으나, Subscriber 목록에서는 다중 아바타를 보여준다. 이슈를 마우스오버하면 A 단축키로 담당자를 빠르게 변경할 수 있다. 이는 "할당된 담당자" 패턴이다. (출처: Linear Docs — "Assign and delegate issues")

**GitHub (PR 리뷰어, Collaborators)**  
GitHub는 Primer 디자인 시스템에서 AvatarStack 컴포넌트를 공식 제공한다. 이 컴포넌트는 최소 2개, 최대 4개 아바타를 겹쳐서 표시하며, 표준 아바타 크기는 20px이다. 마우스오버 시 아바타가 펼쳐지며(expand) 개별 사용자를 확인할 수 있다. PR 페이지의 Reviewers, Repository의 Contributors 섹션 등에서 사용된다. 4개를 초과하는 경우 "+N" 카운터가 표시된다. 겹침 방식은 우측 아바타가 좌측을 덮는 형태이며, 겹침 오프셋은 아바타 크기의 약 50~60%(즉 20px 아바타 기준 약 10~12px 겹침, 노출 영역 약 8~10px)이다. 이 패턴은 "리소스 참여자" 맥락에 해당한다. (출처: Primer Design System — "Avatar stack" 컴포넌트 문서)

### 1-2. 맥락 유형 분류표

| 맥락 유형 | 의미 | 대표 서비스 | 아바타 표시 방식 |
|---|---|---|---|
| (a) 실시간 접속자 | 현재 리소스를 열어둔 사용자 | Figma, Google Docs, Notion(페이지) | 상단바, 겹침 없음/최소 겹침, 색상 커서 연동 |
| (b) 리소스 참여자/구독자 | 리소스에 관여한/구독 중인 사용자 | GitHub(Contributors), Notion(People 컬럼) | 테이블 셀/카드 내, 겹침 스택, "+N" 오버플로 |
| (c) 할당된 담당자 | 특정 작업의 책임자 | Linear(Assignee) | 단일 아바타, 행 내 고정 위치 |

### 1-3. v7 설계 타당성 평가 및 조정 권장사항

v7의 "활성 멤버"는 **해당 스킬을 현재 사용 중인 팀원**을 의미하므로, 맥락 유형 (b) "리소스 참여자"에 가장 가깝다. 실시간 접속(a)과 달리 비동기적 사용 기록이며, 단일 담당자(c)와 달리 복수 사용자이다. 이 맥락에서 아바타 스택은 GitHub의 AvatarStack 패턴과 가장 유사하며, 설계 자체는 타당하다.

**구체적 스펙 권장사항**:

- **아바타 크기**: 20px (GitHub Primer 표준과 동일, 테이블 행 높이 36~40px 내에서 적합)
- **최대 표시 수**: 2개 (v7 현재 설계 유지 — 테이블 셀 폭 제약 고려)
- **겹침 오프셋**: -8px (20px 아바타 기준, 노출 영역 12px 확보)
- **"+N" 처리**: 3명 이상 시 "+N" 카운터 표시, 카운터는 동일 크기(20px)의 회색 원형 배경에 11px 폰트
- **인터랙션**: 마우스오버 시 전체 멤버 목록을 툴팁 또는 팝오버로 표시
- **이니셜 아바타**: 프로필 이미지 미설정 시 이름 이니셜 + 고유 배경색 (업계 표준 관례)
- **흰색 테두리**: 아바타 간 2px 흰색 테두리로 겹침 구분 (GitHub, MUI AvatarGroup 공통 패턴)

## G2. 트렌드 임계값 — 소규모 데이터셋의 변동 감지 기준

### 2-1. 서비스별 감지 기준 분석

**Datadog — Anomaly Detection**  
Datadog의 이상 탐지는 세 가지 알고리즘(Basic, Agile, Robust)을 제공한다. 핵심 파라미터는 "bounds"로, 표준편차에 해당하며 기본값 2~3을 권장한다. 주간 계절성(weekly seasonality)을 사용하려면 최소 3주 분량의 히스토리 데이터가 필요하고, 일간 계절성은 최소 3일이 필요하다. 모든 계절성 알고리즘은 최대 6주의 과거 데이터를 활용한다. Datadog은 트리거 윈도우(예: 15분 내 40% 이상 데이터 포인트가 이상일 때 알림)와 복구 윈도우를 분리하여 노이즈를 줄인다. 다만 Datadog은 대규모 인프라 메트릭을 전제하므로, 일 0~30건 수준의 소규모 이벤트 데이터에는 적합하지 않다. 특히 "count 메트릭을 gauge처럼 보간하지 않는" 정책을 명시하고 있어, 이산적(discrete) 이벤트 데이터의 한계를 인정하고 있다. (출처: Datadog 공식 문서 — "Anomaly Monitor", "Algorithms")

**Grafana — Alert Conditions**  
Grafana의 알림 조건은 "for" duration 파라미터를 통해 일정 기간 동안 조건이 지속될 때만 알림을 발생시킨다. 예를 들어 "값이 임계값을 5분 이상 초과할 때"로 설정하면 순간적 스파이크는 무시된다. 평가 주기(evaluation period)와 "pending period"를 조합하여 노이즈를 필터링한다. 그러나 Grafana 역시 절대 최소값 하한선 기능을 기본 제공하지는 않으며, 이를 위해서는 복합 쿼리(예: "값 > 5 AND 변동률 > 50%")를 수동 구성해야 한다. (출처: 업계 관례 기반)

**Google Analytics 4 — Insights 자동 알림**  
GA4의 Insights는 머신러닝 기반 자동 이상 탐지를 제공하며, 사용자에게 "비정상적 변동"을 자동으로 알린다. GA4는 내부적으로 Bayesian structural time series 모델을 사용하는 것으로 알려져 있으며, 최소 28일의 히스토리 데이터를 권장한다. GA4는 세션 수가 극히 적은 속성(property)에서는 Insights 알림을 생성하지 않는 것이 관찰된다. 공식적으로 명시된 최소 트래픽 요건은 없으나, 실무적으로 일 50회 이상의 이벤트가 있어야 의미 있는 탐지가 이루어지는 것으로 보고된다. (출처: 업계 관례 기반, 추정치)

**Amplitude — Anomaly Detection**  
Amplitude의 이상 탐지는 차트에 "Expected Range"를 오버레이하며, 실제 값이 예상 범위를 벗어나면 알림을 생성한다. Amplitude는 최소 30일 히스토리를 권장하며, 이벤트 수가 적은 경우 예상 범위의 신뢰 구간이 넓어져 사실상 대부분의 변동이 "정상" 범위에 포함된다. 이는 소규모 데이터에서 자연스러운 노이즈 필터링으로 작용한다. 그러나 역으로, 진정한 트렌드도 감지하지 못하는 문제가 있다. (출처: 업계 관례 기반, 추정치)

**VS Code Marketplace — Trending 메트릭**  
VS Code Marketplace API는 `trendingdaily`, `trendingweekly`, `trendingmonthly` 세 가지 트렌딩 지표를 제공한다. 이 값은 소수점을 포함하는 연속적 수치(예: trendingdaily=0.63, trendingweekly=63.9, trendingmonthly=107.0)로, 설치 수의 가속도 또는 가중 이동평균 기반으로 산출되는 것으로 추정된다. 마켓플레이스에서 "Trending" 배지가 부여되는 정확한 임계값은 공개되어 있지 않으나, 주간/월간 트렌딩 값이 일정 백분위(percentile) 이상인 확장이 선정되는 것으로 추정된다. 주목할 점은 일간 트렌딩 값이 상대적으로 낮은 확장(0.63)도 주간/월간에서는 높은 값을 가질 수 있어, **기간이 길수록 노이즈가 줄어드는** 효과를 확인할 수 있다. (출처: GitHub Shields.io 이슈 #2689, VS Code Marketplace API)

### 2-2. 소규모 데이터 적용 시 문제점

| 문제 유형 | 설명 | 예시 |
|---|---|---|
| 저빈도 노이즈 | 절대값이 작을 때 퍼센트 변동이 과장됨 | 1→2회 = 100% 증가, 그러나 무의미 |
| 신뢰 구간 팽창 | 데이터가 적을수록 통계적 신뢰 구간이 넓어져 대부분 "정상" 판정 | 주 5회일 때 ±5회 범위 → 0~10 모두 정상 |
| 계절성 부재 | 주 0~200건 수준에서는 요일별 패턴이 불명확 | 월요일 10건, 화요일 0건이 패턴인지 노이즈인지 구분 불가 |
| 지연 탐지 | 이상 탐지 알고리즘이 최소 3~4주 데이터를 요구 | 신규 스킬은 탐지 대상에서 사실상 제외 |

### 2-3. v7 트렌드 표시 조건 수정안

1차 리서치의 "50% 이상 증가 시 ↑ 표시" 규칙을 아래와 같이 수정할 것을 권장한다.

**이중 조건 방식 (절대값 하한 + 퍼센트 변동 조합)**:

```
트렌드 표시 조건 = (현재 주 호출 수 ≥ 최소 하한) AND (변동률 ≥ 임계값)
```

| 파라미터 | 권장 값 | 근거 |
|---|---|---|
| **감지 기간** | 7일 (주간 비교) | Datadog 기본 평가 윈도우, GA4 주간 비교 관례 |
| **최소 호출 수 하한** | 현재 주 ≥ 5회 | 일 1회 미만 수준의 노이즈 제거. 1→2회 같은 무의미한 변동 차단 |
| **상승 트렌드 (↑)** | 이전 주 대비 +100% 이상 증가 AND 절대 증가 ≥ 5건 | "5→11회"는 표시(+120%, +6건), "2→5회"는 미표시(+150%이나 +3건 미달) |
| **하강 트렌드 (↓)** | 이전 주 대비 -50% 이상 감소 AND 이전 주 ≥ 10회 | 10→4회는 표시(-60%), 3→1회는 미표시(이전 주 하한 미달) |
| **신규 스킬 예외** | 생성 후 2주 미만 스킬은 트렌드 표시 비활성 | 히스토리 부족으로 인한 허위 트렌드 방지 |

**UI 표현 권장**:

- **↑ 아이콘**: 녹색(#22C55E) 상승 화살표, 호출 수 옆에 인라인 배치
- **↓ 아이콘**: 주황색(#F59E0B) 하락 화살표 (빨간색은 "오류" 연상이므로 회피)
- **마우스오버 툴팁**: "지난주 12회 → 이번주 28회 (+133%)" 형태로 원시 데이터 제공
- **트렌드 없음**: 아이콘 미표시 (회색 대시 등 불필요한 표시 지양)

## G3. 복사 확산 방지 — 팀 카탈로그의 복사본 관리 가드레일

### 3-1. 서비스별 복사 관리 모델

**Google Drive (공유 드라이브)**  
Google Drive 공유 드라이브는 관리자가 "뷰어 및 댓글 작성자의 다운로드, 인쇄, 복사 차단" 옵션을 설정할 수 있다. 그러나 편집자 이상 권한이 있으면 자유롭게 복사 가능하다. 복사본은 사용자의 내 드라이브 또는 다른 공유 드라이브에 생성되며, 원본과의 연결은 유지되지 않는다. 스토리지 쿼터가 사실상 유일한 "확산 제어" 장치이며, 비활성 파일 자동 아카이브 기능은 Google Workspace Enterprise에서 보존 정책(retention policy)으로 제한적으로 제공된다. Google Drive의 모델은 **"자유 복사 + 쿼터 제한"**이다. (출처: 업계 관례 기반)

**Notion (팀 워크스페이스)**  
Notion은 워크스페이스 내 모든 페이지를 자유롭게 복제(Duplicate)할 수 있다. 복제본은 독립적이며 원본과의 링크가 유지되지 않는다. Notion은 "템플릿" 기능을 별도로 제공하여, 반복 사용되는 구조를 템플릿으로 등록하면 복제 대신 템플릿에서 새 인스턴스를 생성하도록 유도한다. 비활성 페이지 자동 아카이브 기능은 없으며, 수동으로 아카이브하거나 휴지통으로 이동해야 한다. 최근 Notion은 워크스페이스 검색 개선과 사이드바 정리(섹션 접기 등)로 탐색 효율을 보완하고 있다. 모델은 **"자유 복사 + 템플릿 유도 + 수동 정리"**이다. (출처: 업계 관례 기반)

**Figma (팀 라이브러리)**  
Figma는 팀 라이브러리에서 컴포넌트 publish 권한을 에디터(Editor) 이상으로 제한하며, 라이브러리를 구독하는 방식으로 중복을 줄인다. 개별 파일의 복제(Duplicate)는 자유이나, 복제된 파일의 컴포넌트는 원본 라이브러리와의 연결이 유지된다(detach하지 않는 한). 이 "연결 유지" 모델이 핵심 차별점이다. 라이브러리 정리 도구로는 사용되지 않는 컴포넌트를 검색하는 플러그인(예: Unused Components)이 있으나 공식 기능은 아니다. 모델은 **"자유 복사 + 원본 연결 유지 + publish 권한 제어"**이다. (출처: 업계 관례 기반)

**Slack (워크플로우 빌더)**  
Slack 워크플로우는 빌더 권한이 있는 사용자가 기존 워크플로우를 복제할 수 있다. 복제본은 독립적이며 원본과 연결되지 않는다. 비활성 워크플로우에 대해 Slack은 별도의 자동 아카이브 기능을 제공하지 않으나, 관리자가 워크플로우 목록에서 수동으로 비활성화(unpublish)할 수 있다. 워크플로우 수에 대한 명시적 제한은 Enterprise Grid에서 관리자 정책으로 설정 가능하다. 모델은 **"권한 기반 복사 + 수동 비활성화"**이다. (출처: 업계 관례 기반)

**GitHub (Organization)**  
GitHub은 Fork와 Template Repository를 구분한다. Fork는 원본과의 연결을 유지하여 upstream에서 변경 사항을 pull할 수 있고, PR을 통해 기여할 수 있다. Template Repository는 "Use this template" 버튼으로 독립적 사본을 생성하되, 원본과의 링크는 유지되지 않는다. Organization 레벨에서 Fork 정책을 제한할 수 있으며(private repo의 fork 금지 등), Archived Repository 기능으로 비활성 저장소를 읽기 전용으로 전환할 수 있다. 아카이브된 저장소는 목록에서 시각적으로 구분되며(흐린 표시 + "Archived" 배지), 검색에서 기본 제외된다. 모델은 **"Fork(연결 유지) + Template(독립 복사) + 아카이브 + 정책 제어"**이다. (출처: GitHub Docs, 업계 관례 기반)

### 3-2. 복사 관리 모델 비교표

| 서비스 | 복사 자유도 | 원본 연결 | 비활성 관리 | 확산 제어 장치 |
|---|---|---|---|---|
| Google Drive | 높음 (권한별) | 없음 | 보존 정책(Enterprise) | 스토리지 쿼터 |
| Notion | 높음 | 없음 | 수동 아카이브/삭제 | 템플릿 유도 |
| Figma | 높음 | 컴포넌트 링크 유지 | 없음 (플러그인 의존) | Publish 권한, 라이브러리 구독 |
| Slack | 중간 (권한 기반) | 없음 | 수동 비활성화 | 관리자 정책 |
| GitHub | 높음 | Fork=유지, Template=없음 | Archived Repository | Fork 정책, 아카이브 |

### 3-3. v7 가드레일 권장사항

**v7 즉시 적용 (v7 scope)**:

1. **"원본에서 복사됨" 메타데이터 표시**: 복사본 스킬 카드에 원본 스킬 이름과 링크를 표시한다. "매출 분석 (복사본 · 원본: @김팀장/매출 분석)" 형태로 카탈로그에서 원본 관계를 즉시 파악할 수 있게 한다. 이는 GitHub의 Fork 관계 표시와 유사하다.

2. **비활성 복사본 시각적 희석**: 최근 30일 간 호출 0회인 복사본은 테이블에서 텍스트 색상을 #9CA3AF(gray-400)로 희석하고, 행 우측에 "30일간 미사용" 배지를 표시한다. GitHub의 Archived Repository 시각 처리와 유사한 접근이다.

3. **복사 시 이름 규칙 강제**: 복사 시 기본 이름을 "{원본 이름} (사본)"으로 설정하고, 사용자가 변경할 수 있게 한다. 동일 이름의 스킬이 이미 존재하면 경고 메시지를 표시한다.

4. **"내 복사본만 보기" 필터**: 테이블 필터에 "내가 만든 복사본" 옵션을 추가하여, 자신의 복사본을 빠르게 관리할 수 있게 한다.

**장기 검토 (v8+ scope)**:

1. **자동 아카이브 제안**: 90일간 호출 0회 + 소유자 마지막 로그인 30일 이상 경과 시, 소유자에게 "이 스킬을 아카이브하시겠습니까?" 알림을 발송한다. 자동 삭제가 아닌 수동 확인 방식으로 안전성을 확보한다.

2. **동일 원본 파생 그룹핑 뷰**: 카탈로그에서 "원본별 그룹" 뷰를 제공하여, 동일 원본에서 파생된 복사본들을 묶어서 표시한다. "매출 분석 → 복사본 7개" 형태로 확산 정도를 한눈에 파악할 수 있다.

3. **복사 상한 경고**: 동일 원본에서 팀 내 복사본이 5개를 초과할 경우, 복사 시점에 "이 스킬은 이미 5명의 팀원이 복사했습니다. 기존 복사본을 확인해보시겠습니까?" 안내를 표시한다. 복사를 차단하지는 않되 인식(awareness)을 높인다.

4. **소유자 퇴사 시 처리 정책**: 소유자가 팀에서 제거되면, 해당 복사본을 팀 관리자에게 소유권 이전하거나 90일 후 자동 아카이브하는 정책을 설정한다.

## G4. 패널 폭 실측 — 슬라이드 패널과 파일 탐색기의 최소 폭 검증

### 4-1. 서비스별 폭 측정

**Linear — 이슈 상세 패널**  
Linear의 이슈 상세 뷰는 별도의 "사이드 패널"이 아닌 전체 페이지 레이아웃으로 구현된다. 콘텐츠 영역(좌측)과 프로퍼티 영역(우측)이 병렬 배치되며, 콘텐츠 영역의 최대 폭은 약 680~720px, 프로퍼티 패널은 약 280~320px로 DevTools에서 관찰된다. 리사이즈 기능은 공식적으로 지원되지 않으며, 브라우저 창 크기에 반응하여 콘텐츠 영역이 유동적으로 조절된다. Linear 개발팀은 가독성을 위해 콘텐츠 열 폭에 상한을 두었다고 밝힌 바 있다. (출처: Linear Changelog — "Issue view layout" 2021-06-03, DevTools 추정치)

**Jira — 이슈 상세 패널**  
Jira Cloud의 이슈 뷰는 좌측 메인 콘텐츠와 우측 디테일 패널로 구성된다. 우측 패널의 기본 비율은 `flex: 0 1 calc(35% + 12px)`로 설정되어 있으며, 이는 1920px 기준 약 685px에 해당한다. 커뮤니티에서 이 폭이 과도하다는 불만이 지속되었고, 최근에는 리사이즈 가능하도록 업데이트되었다. 보드 뷰의 이슈 디테일 패널(오른쪽 슬라이드)은 약 400~450px로 더 좁으며, 리사이즈 기능이 별도로 요청되어 왔다. 전체 이슈 뷰의 최대 폭 제한은 약 1400px로, 이를 초과하면 양측에 여백이 발생한다. (출처: Atlassian Community — "Set the width of the right side panel", "New Jira Experience - Max Width Issue View")

**Notion — Side Peek 패널**  
Notion의 Side Peek은 데이터베이스 항목을 우측 패널로 여는 기능이다. Side Peek 패널의 폭은 브라우저 창 크기에 비례하여 자동 조절되며, 일반적으로 전체 폭의 약 50~60%를 차지한다. 1920px 기준 약 900~1050px로 상당히 넓은 편이다. 리사이즈를 직접 드래그로 조절하는 기능은 제공되지 않으며, 대안으로 Center Peek(중앙 모달) 또는 Full Page로 전환할 수 있다. Notion의 Side Peek은 v7의 좁은 슬라이드 패널과는 성격이 다르다 — Notion은 페이지 전체 콘텐츠를 표시하는 반면, v7은 버전 이력과 콘텐츠 미리보기만 표시한다. (출처: Notion 공식 릴리즈 2022-07-20, 업계 관례 기반)

**GitHub — 코드 뷰 파일 트리 사이드바**  
GitHub의 코드 뷰와 PR 파일 뷰에서 좌측 파일 트리 사이드바는 약 260~300px의 고정 폭으로 표시된다. 현재까지 공식적인 리사이즈 기능은 제공되지 않으며, 이에 대한 커뮤니티 요청이 지속되고 있다. 파일 트리가 표시될 때 브라우저 폭이 약 1000px 이하로 줄어들면 파일 트리가 자동으로 숨겨진다. Split diff 뷰에서는 1200px 이하에서 숨김이 권장된다. GitHub Desktop 앱에서는 파일 리스트 폭이 350px로 설정되어 있다. (출처: GitHub Community Discussion #12341 — "Pull Request File Tree Beta Feedback", GitHub Desktop Issue #1588)

**VS Code — Explorer 사이드바**  
VS Code의 Primary Sidebar(Explorer 포함) 기본 폭은 약 300px이다. `window.sidebar.defaultPanelWidth` 설정을 통해 사용자가 기본 폭을 지정할 수 있으며, 일반적 권장 범위는 250~400px이다. 최소 폭은 약 170px까지 축소 가능하며, 이 이하에서는 파일명이 잘리고 아이콘만 표시된다. Activity Bar의 고정 폭은 약 48~55px이다. VS Code는 사이드바 폭을 세션 간 기억하며, 드래그로 자유롭게 조절할 수 있다. (출처: VS Code 공식 문서 — "Custom Layout", GitHub Issue #158603, codegenes.net 설정 가이드)

### 4-2. 폭 측정 비교표

| 서비스 | 패널 유형 | 기본 폭 (px) | 최소 폭 (px) | 리사이즈 | 비고 |
|---|---|---|---|---|---|
| Linear | 이슈 프로퍼티 패널 | 280~320 | 고정 | 불가 | 콘텐츠 영역 680~720px |
| Jira (보드 디테일) | 슬라이드 패널 | 400~450 | ~350 (추정) | 최근 지원 | 전체 뷰는 별도 |
| Jira (이슈 뷰 우측) | 인라인 패널 | ~685 (35%+12px) | ~400 (추정) | 최근 지원 | 1920px 기준 |
| Notion (Side Peek) | 오버레이 패널 | 900~1050 | 고정 | 불가 | 전체 폭 50~60% |
| GitHub (파일 트리) | 사이드바 | 260~300 | 260 (고정) | 불가 | <1000px 시 자동 숨김 |
| VS Code (Explorer) | 사이드바 | ~300 | ~170 | 드래그 가능 | 설정으로 기본값 조절 |

### 4-3. v7 패널 폭 적합성 판정 및 권장사항

v7 슬라이드 패널은 버전 이력(상단)과 콘텐츠 미리보기(하단)를 세로로 배치하는 구조이다. 이 용도에서 1차 리서치의 400~500px 권장은 **적절하며, 하한을 400px으로 확정**할 것을 권장한다.

**근거**:

- Jira 보드의 이슈 디테일 슬라이드 패널(400~450px)이 v7과 가장 유사한 용도이며, 이 폭에서 메타데이터 + 설명 텍스트가 가독성을 유지한다.
- VS Code Explorer의 최소 폭 170px은 파일명만 표시하는 극단적 케이스이며, 마크다운 렌더링이나 코드 하이라이팅에는 부적합하다.
- GitHub 파일 트리 사이드바(260~300px)는 파일명 목록에 특화되어 있어, 콘텐츠 미리보기를 포함하는 v7에는 좁다.

**확정 권장 스펙**:

| 파라미터 | 권장 값 | 근거 |
|---|---|---|
| **기본 폭** | 480px | Jira 디테일(450) + 마크다운 여유분. 1920px 화면에서 테이블에 약 1440px 확보 |
| **최소 폭** | 400px | 마크다운 렌더링 최소 가독 폭. 코드 블록은 가로 스크롤 허용 |
| **최대 폭** | 640px | 전체 폭의 1/3 상한. 테이블 영역이 지나치게 줄어드는 것 방지 |
| **리사이즈** | 드래그 가능 (sash 핸들) | VS Code, Jira 등 업계 표준. 사용자 선호에 따른 조절 필수 |
| **반응형 전환** | 브라우저 폭 < 1024px 시 패널을 전체 화면 오버레이로 전환 | 모바일/태블릿 대응 |

**콘텐츠 적응 전략**:

- **마크다운 텍스트**: 400px 이상에서 줄바꿈(word-wrap)으로 자연스럽게 흐르도록 처리. 별도 가로 스크롤 불필요.
- **코드 블록**: `overflow-x: auto`로 가로 스크롤 허용. 폭 400px에서 약 45~50자 표시 가능(13px monospace 기준).
- **파일 목록(버전 이력)**: 버전 번호, 날짜, 작성자를 한 행에 배치. 400px에서 충분히 표시 가능. 커밋 메시지는 단일 행에서 말줄임(...) 처리.
- **이미지/미디어**: 패널 폭에 맞춰 `max-width: 100%`로 축소 표시.
