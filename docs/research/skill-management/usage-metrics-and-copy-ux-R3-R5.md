# 사용량 지표 표시 + 복사 UX 벤치마크 리서치

> **조사 기준일**: 2026-03-25  
> **대상**: npm, Chrome 웹 스토어, VS Code Marketplace, Figma Community, Slack App Directory, ChatGPT Enterprise, Google Drive, GitHub, Notion, Canva  
> **목적**: 호출 수/활성 멤버 컬럼 렌더링 규격 + 복사 인터랙션 마이크로 UX 설계  
> **맥락**: 팀 내부 AI 에이전트 스킬 카탈로그 (0~200 호출 수 범위, 팀 규모 10~100명)

## Part 1: 사용량 지표 표시 패턴 (R3)

### 1-1. npm

**숫자 표시 형식**  
패키지 목록 및 상세 페이지에서 "Weekly Downloads"를 정확한 숫자로 표시하며, 천 단위 구분자(콤마)를 사용한다 (예: `23,522,794`). 검색 결과 리스트에서도 축약 없이 전체 숫자를 노출한다. 단, shields.io 배지에서는 `1.2M`, `500k` 등 SI 접미사 축약을 사용한다.

**트렌드 표시**  
패키지 상세 페이지에 주간 다운로드 수 추이를 보여주는 스파크라인 미니 차트를 제공한다. 별도의 ↑↓ 아이콘이나 "전주 대비 +N%" 같은 상대 표현은 기본 UI에 없으며, npmtrends.com이나 npmcharts.com 같은 외부 도구로 비교 차트를 제공한다.

**아바타 스택 패턴**  
해당 없음. npm은 사용자/설치자 아바타를 표시하지 않으며, collaborator 아바타만 패키지 상세 페이지 사이드바에 나열한다.

**빈 상태 처리**  
다운로드 수가 0인 경우 그대로 `0`을 표시한다. 신규 패키지도 예외 없이 동일한 형식을 사용하여, "아직 사용자가 없음"이라는 별도 메시지를 두지 않는다.

**장점**: 정확한 숫자는 기술적 신뢰감을 제공하며, 스파크라인은 추세를 직관적으로 전달한다.  
**단점**: 대규모 숫자(수백만~수천만)가 비전문가에게는 의미 파악이 어렵고, 팀 규모 카탈로그에서는 과도한 정밀도가 불필요하다.

### 1-2. Chrome 웹 스토어

**숫자 표시 형식**  
"사용자 수"를 상대적으로 큰 단위로 라운딩하여 표시한다. 1,000 이상부터는 가장 유효한 한 자릿수로 반올림한다 (예: `2,000+`, `10,000+`, `1,000,000+`). 최대 표시값은 `10,000,000+`이다. 평점은 ★ 5점 척도와 리뷰 수를 함께 표시한다.

**트렌드 표시**  
공개 스토어 페이지에서는 트렌드를 표시하지 않는다. 개발자 대시보드에서만 일별 설치/삭제 추이 차트와 주간 사용자 잔존율을 제공한다.

**아바타 스택 패턴**  
해당 없음. 사용자 아바타 표시 없이 집계된 숫자만 노출한다.

**빈 상태 처리**  
사용자 수가 없거나 숨겨진 경우 해당 메트릭 자체를 표시하지 않는다. 일부 Google 자체 확장 프로그램(예: Gmail)은 사용자 수를 비공개로 유지한다.

**장점**: 라운딩된 숫자는 정밀도보다 규모감을 빠르게 전달하며, 스캔이 용이하다.  
**단점**: 유효 숫자 1자리 라운딩으로 인해 `100,000+ → 200,000+` 사이 구간에서 성장을 감지할 수 없다. 팀 카탈로그에서는 0~200 범위이므로 이 라운딩 방식은 적합하지 않다.

### 1-3. VS Code Marketplace

**숫자 표시 형식**  
검색 결과 리스트와 확장 상세 페이지 모두에서 "installs" 수를 정확한 숫자로 표시하며, 대규모 숫자도 축약하지 않는다. 평점은 ★ 5점 척도이며, 리뷰 수와 함께 표시된다. API 내부적으로는 `install`, `updateCount`, `averagerating`, `ratingcount` 등 세분화된 통계를 제공한다.

**트렌드 표시**  
VS Code Marketplace API에는 `trendingdaily`, `trendingweekly`, `trendingmonthly` 통계가 존재하며, 이를 기반으로 "Trending" 배지를 상위 확장에 부여한다. 불꽃(🔥) 아이콘 또는 "Trending" 라벨로 표시되며, 구체적인 ↑↓ 퍼센트는 노출하지 않는다.  
VS Code 내부 확장 뷰에서는 Install Count, Rating, Name, Published Date, Updated Date 기준으로 정렬할 수 있으며, 기본 정렬은 Marketplace Installs(내림차순)이다.

**아바타 스택 패턴**  
해당 없음. Publisher 아이콘/로고는 표시되나 사용자 아바타는 없다.

**빈 상태 처리**  
설치 수 0인 확장도 `0` 또는 아주 작은 숫자를 그대로 노출한다. 별도의 빈 상태 메시지 없음.

**장점**: "Trending" 배지는 신규 및 급성장 확장을 쉽게 발견하게 해주며, 팀 카탈로그에서도 적용 가능한 패턴이다.  
**단점**: 트렌드 점수의 계산 방식이 불투명하여 사용자가 배지의 의미를 완전히 이해하기 어렵다.

### 1-4. Figma Community

**숫자 표시 형식**  
각 리소스(파일, 플러그인, 위젯) 페이지에 두 가지 주요 메트릭을 표시한다:
- **❤️ (좋아요 수)**: 하트 아이콘 옆에 정확한 숫자 또는 `1.2k` 축약 (1,000 이상 시)
- **복사/사용 수**: 사람 아이콘 옆에 해당 리소스를 복제한 횟수 또는 플러그인/위젯 사용자 수. 역시 `1k`, `10k` 형태로 축약한다.

Figma 공식 도움말에 따르면, "The number next to the heart icon indicates how many users have liked the resource. The other number indicates how many people have used the plugin or widget, duplicated the file, or authenticated the app."

**트렌드 표시**  
별도의 트렌드 표시 없음. 카테고리별 탐색 시 "Popular" 정렬이 존재하며, 이는 최근 기간의 좋아요/복사 수에 기반한 것으로 추정된다.

**아바타 스택 패턴**  
리소스 페이지에 Creator 프로필 아바타 1개가 표시되며, 사용자/복사자의 아바타 스택은 없다.

**빈 상태 처리**  
좋아요 0, 복사 0인 경우 숫자 `0`을 그대로 표시한다.

**장점**: 두 가지 보완적 메트릭(좋아요 = 관심도, 복사 = 실제 채택)이 에셋의 인기를 다각도로 보여준다. `k` 축약은 스캔성이 우수하다.  
**단점**: 좋아요와 복사 수의 구분이 초보 사용자에게 명확하지 않을 수 있다.

---

### 1-5. Slack App Directory

**숫자 표시 형식**  
Slack Marketplace의 앱 페이지에서는 **구체적인 설치 수를 공개하지 않는다**. 대신 앱의 카테고리, 설명, 호환 정보, 보안/컴플라이언스 정보, 개발자의 프라이버시 정책을 표시한다. 관리자 대시보드(Enterprise)에서는 앱별 설치된 워크스페이스 수, 활성 사용자 수 등을 테이블 형태로 볼 수 있으며 CSV 내보내기를 지원한다.

**트렌드 표시**  
공개 디렉토리에서는 트렌드 미표시. Enterprise 관리 대시보드에서 기간별 필터링으로 앱 사용 추이를 확인할 수 있다.

**아바타 스택 패턴**  
해당 없음. 앱 아이콘만 표시.

**빈 상태 처리**  
설치 수를 공개하지 않으므로 빈 상태 이슈가 없다. 관리 대시보드에서는 사용량 0인 앱도 테이블에 행으로 포함된다.

**장점**: 설치 수 비공개는 소규모 앱이 "인기 없어 보이는" 문제를 방지한다. 팀 내부 카탈로그에서도 이 접근을 참고할 수 있다.  
**단점**: 신뢰성 판단을 위한 사회적 증거(social proof)가 부재하여 앱 선택에 도움이 되지 않는다.

### 1-6. ChatGPT Enterprise 관리 뷰

**숫자 표시 형식**  
ChatGPT Enterprise의 Workspace Analytics는 다음 지표를 제공한다:
- **사용자 수 / 활성 사용자**: 기간별 활성 사용자 수, 총 메시지 수, 대화 수
- **GPT별 통계**: 각 커스텀 GPT의 대화 수, 메시지 수, 사용 사용자 수를 테이블로 표시
- **Task Insights**: 대화를 태스크 유형별로 분류 (영업, 엔지니어링 등)

숫자는 정확한 값으로 표시되며, CSV 내보내기가 가능하다. SCIM 그룹별 필터링을 지원하여 부서별 사용량 분석이 가능하다.

**트렌드 표시**  
Overview 대시보드에서 시계열 트렌드 차트를 제공한다. 기간 드롭다운(7일, 30일, 90일 등)으로 조절 가능하며, 채택률(adoption rate) 추이와 활성 사용자 추이를 라인 차트로 보여준다.

**아바타 스택 패턴**  
관리 뷰에서 사용자 목록은 이름/이메일 텍스트 기반이며, 아바타 스택은 사용하지 않는다.

**빈 상태 처리**  
사용량 0인 GPT도 테이블에 포함되며 `0`으로 표시된다. 아직 활성화되지 않은 사용자 수도 별도 메트릭으로 제공하여 채택 갭을 파악할 수 있게 한다.

**장점**: 팀/부서별 세그먼트 분석과 시계열 트렌드가 강점이며, 우리 제품과 가장 유사한 "팀 내부 도구 카탈로그" 맥락이다.  
**단점**: 관리자 전용 뷰이므로 일반 사용자에게는 사회적 증거로 활용되지 않는다.

## Part 2: 복사 UX 패턴 (R5)

### 2-1. Google Drive

**이름 생성 규칙**  
`"Copy of {원본 이름}"` — 접두사 방식. 동일 폴더에서 같은 파일을 반복 복사하면 `"Copy of Copy of {원본 이름}"` 형태로 중첩된다 (넘버링 없음). 로캘에 따라 한국어에서는 `"{원본 이름} 사본"`, 중국어에서는 `"{원본 이름} 的副本"` 등 접미사로 변경된다. 데스크톱 앱에서 폴더를 복제할 때는 폴더명에만 `copy`가 붙고, 내부 파일명은 변경되지 않는다.

**복사 직후 행동 유도**  
복사본이 동일 폴더에 생성된 후, 별도의 자동 네비게이션이나 이름 편집 포커스는 없다. 사용자가 직접 복사본을 찾아 열어야 한다. 에디터(File > Make a copy)에서 복사할 경우 새 탭에서 복사본이 열리며, 이 경우도 이름 편집 포커스는 제공되지 않는다. 별도 토스트 알림은 없다.

**원본 관계 표시**  
원본과의 관계를 표시하지 않는다. 복사본은 완전히 독립적인 파일이다.

**배치 위치**  
같은 폴더에 생성되며, 정렬 기준에 따라 자동 위치가 결정된다 (이름순이면 C 위치, 시간순이면 최상단).

**대량 복사 방지**  
별도 제한 없음. 이로 인해 `"Copy of Copy of Copy of..."` 문제가 빈번하게 발생하며, 커뮤니티에서 일괄 이름 변경 스크립트가 공유되는 등 실질적인 사용성 문제로 알려져 있다.

**장점**: 단순하고 예측 가능한 패턴.  
**단점**: 접두사 중첩이 가독성을 심각하게 저해하며, 복사 후 행동 유도가 전무하여 UX가 미완성적이다. 팀 카탈로그에서는 절대 채택하면 안 되는 반면교사.

### 2-2. Figma

**이름 생성 규칙**  
Figma Community에서 파일을 복제하면 원본 이름 뒤에 `"(Community)"` 접미사가 추가된다. 동일 파일 내 요소 복제(Cmd/Ctrl+D)는 동일 이름에 위치만 오프셋된 복제본을 생성한다. 파일 자체 Duplicate 시에는 이름 변경 규칙이 명시되지 않으나, 같은 프로젝트 내에서 `"{이름} (1)"`, `"{이름} (2)"` 형태의 넘버링이 붙는 것이 관찰된다.

**복사 직후 행동 유도**  
Community 파일 복제 시, "Open in Figma" 또는 "Open in FigJam" 클릭 후 계정 선택 → Drafts 폴더에 복사본이 생성되며 자동으로 해당 파일이 열린다. 복사본은 별도의 이름 편집 프롬프트 없이 바로 편집 가능한 상태로 열린다.

**원본 관계 표시**  
복사본은 원본의 버전 히스토리, 댓글, 권한을 포함하지 않는 완전히 새로운 파일이다. Figma 공식 문서에 따르면 "Changes made to the original file are not reflected in duplicated files." 원본 링크나 출처 표시는 없다.

**배치 위치**  
사용자의 Drafts 폴더 최상단에 배치된다.

**대량 복사 방지**  
별도 제한 없음. 유료 리소스의 경우 구매 확인 플로우가 자연스러운 게이트 역할을 한다.

**팀 카탈로그 특수성**  
Figma의 Team Libraries에서 컴포넌트를 복제하면 로컬 파일에 분리된 사본이 생기며, 팀 라이브러리 업데이트가 더 이상 반영되지 않는다. 이는 "포크 후 독립" 모델과 유사하다.

**장점**: Community 복사 시 자동으로 파일이 열리는 것은 즉각적인 행동 유도로 우수하다.  
**단점**: `"(Community)"` 접미사는 정보적이지만 이름이 길어질 수 있으며, 복사 후 원본 추적이 불가능하다.

---

### 2-3. GitHub

**이름 생성 규칙**  
- **Fork**: 원본과 동일한 리포지토리 이름을 사용하되, `username/repo-name` 네임스페이스로 구분한다. 이름 변경 가능하며, 변경 후에도 fork 관계가 유지된다.
- **Template Repository**: "Use this template" 클릭 시 모달에서 새 리포지토리 이름을 직접 입력하도록 유도한다. 자동 이름 생성 없이 사용자 입력을 강제한다.

**복사 직후 행동 유도**  
- **Fork**: Fork 생성 후 자동으로 새 리포지토리 페이지로 네비게이션된다. 상단에 "forked from original/repo" 링크가 영구적으로 표시된다.
- **Template**: 생성 후 새 리포지토리 페이지로 이동하며, "generated from template-name" 배지가 표시된다.

**원본 관계 표시**  
- **Fork**: 리포지토리명 바로 아래에 "forked from {owner/repo}" 링크가 영구 표시. Pull Request를 통한 upstream 동기화 UI 제공. 네트워크 그래프에서 fork 관계 시각화.
- **Template**: "generated from {template}" 텍스트가 표시되나, fork보다 약한 연결. 코드 동기화 기능 없음.

**배치 위치**  
사용자의 리포지토리 목록에 추가되며, 기본 정렬(최근 업데이트순)에 따라 최상단에 위치한다.

**대량 복사 방지**  
동일 네임스페이스에서 같은 이름의 fork를 중복 생성할 수 없다 (1 fork per user per repo 제한). Template은 매번 다른 이름을 입력해야 하므로 자연스러운 중복 방지.

**팀 카탈로그 특수성**  
GitHub Organizations에서는 fork가 Organization 내에 생성되어 팀원 모두에게 노출된다. 이때 "forked from" 배지가 맥락을 제공하여 원본과의 관계를 즉시 파악할 수 있다.

**장점**: Fork의 영구적 원본 관계 표시와 upstream 동기화는 "포크 후 독립" vs "포크 후 추적" 모델의 교과서적 구현이다. Template의 이름 입력 강제는 의미 있는 이름을 유도한다.  
**단점**: Fork 모델의 전체 동기화 기능은 스킬 카탈로그에서는 과도하다.

---

### 2-4. Notion

**이름 생성 규칙**  
페이지 Duplicate 시 원본 이름 뒤에 `"(1)"` 접미사가 추가된다. 동일 페이지를 반복 복제하면 `"(2)"`, `"(3)"` 순서로 증가한다. Community 템플릿 복제 시에는 원본 이름을 그대로 사용하며 별도 접미사가 없다 (Drafts/Private에 배치되므로 충돌 우려가 없음).

**복사 직후 행동 유도**  
- **페이지 Duplicate**: 즉시 같은 폴더에 복사본이 생성되며, 사이드바에서 확인 가능. 자동 네비게이션이나 이름 편집 포커스는 없다.
- **Community 템플릿**: 복제 후 Private 섹션 최상단에 나타나며, 사용자가 클릭하여 열 수 있다.
- **"Duplicate with content" vs "Duplicate without content"** 옵션을 제공하여 구조만 복사할지 전체 내용을 복사할지 선택할 수 있다 (2025년 업데이트).

**키보드 단축키**: Ctrl/Cmd + D로 즉시 복제. 메뉴 탐색 없이 한 번의 키 입력으로 완료.

**원본 관계 표시**  
없음. 복사본은 독립적이며 원본 변경사항이 반영되지 않는다.

**배치 위치**  
같은 폴더 내, 원본 바로 아래에 배치된다 (사이드바에서 원본 아이템 직하 위치).

**대량 복사 방지**  
별도 제한 없으나, `(1)`, `(2)` 자동 넘버링으로 중복을 시각적으로 구분한다.

**팀 카탈로그 특수성**  
Notion 팀 워크스페이스에서 페이지를 복제하면 팀 전체에 복사본이 노출될 수 있다. 이를 관리하기 위해 "Private" 섹션으로 먼저 복제한 후 필요시 팀 공간으로 이동하는 워크플로우가 일반적이다. "Allow duplicate as template" 토글을 통해 복제 가능 여부를 제어할 수 있다.

**장점**: `(1)`, `(2)` 넘버링은 간결하고 예측 가능하다. Cmd+D 단축키는 모달 없는 즉시 복사에 최적.  
**단점**: 복사 후 이름 편집 유도가 없어, 의미 없는 `"프로젝트 계획 (1)"`이 누적될 수 있다.

### 2-5. Canva

**이름 생성 규칙**  
`"Copy of {원본 이름}"` — Google Drive와 동일한 접두사 방식. 반복 복사 시 `"Copy of Copy of..."` 중첩이 발생한다. 에디터 내(File > Make a copy)와 프로젝트 목록(... > Make a copy) 모두 동일한 규칙을 적용한다.

**복사 직후 행동 유도**  
- **에디터 내 복사**: 복사본이 새 탭에서 자동으로 열린다. 상단 툴바의 디자인 이름 영역에서 즉시 이름을 변경할 수 있다 (인라인 편집 가능, 그러나 자동 포커스는 없음).
- **프로젝트 목록 복사**: 같은 폴더에 복사본이 나타나며, 썸네일 하단의 연필 아이콘으로 이름 변경 가능.

**원본 관계 표시**  
없음. 복사본은 완전히 독립적이다.

**배치 위치**  
같은 폴더 또는 프로젝트 페이지에 생성되며, 기본 정렬(최근 수정순)에 따라 최상단에 나타난다.

**대량 복사 방지**  
별도 제한 없음. Enterprise/Team 계정에서는 관리자가 "Who can send copies of their content outside the team?"와 "Who can accept copied content from another team?" 권한을 설정하여 팀 간 복사를 제어할 수 있다.

**팀 카탈로그 특수성**  
Canva Teams에서 Brand Templates를 복사하면 팀원에게 노출된다. 이를 관리하기 위해 Brand Templates 복사는 별도 프로세스로 분리되어 있으며, 관리자가 복사 권한을 역할/그룹별로 설정할 수 있다.

**장점**: 에디터 내 복사 시 새 탭 자동 열림은 즉각적 작업 시작을 가능하게 한다.  
**단점**: "Copy of" 접두사 중첩은 Google Drive와 동일한 문제를 공유하며, 팀 환경에서 "Copy of Copy of..." 이름이 프로젝트 목록을 오염시킬 수 있다.

## Part 3: KonaI-Agent 적용 권장안

### 3.1 호출 수 컬럼 렌더링 규격

**숫자 표시 형식 권장**

팀 카탈로그의 호출 수 범위(0~200)를 고려하면, **정확한 숫자 표시가 최적**이다. 축약이 의미를 갖는 임계점(1,000+)에 도달하지 않으므로 `47`처럼 그대로 표시한다.

| 범위 | 표시 형식 | 근거 |
|------|----------|------|
| 0~999 | 정확한 수 (`47`) | npm, VS Code 패턴. 팀 규모에서 정밀도가 의미 있음 |
| 1,000~9,999 | `1.2K` 축약 | 향후 스케일 대비. Figma 패턴 |
| 10,000+ | `12K` | 만 단위 축약 |

**구체적 렌더링 규격:**
- **폰트**: 시스템 모노스페이스 또는 tabular figures 폰트 (숫자 정렬을 위해)
- **색상**: `--text-secondary` (주요 컨텐츠보다 약간 낮은 위계)
- **정렬**: 우측 정렬 (숫자 컬럼 표준)
- **컬럼 폭**: 고정 `64px` (3자리 + 패딩). 4자리 이상 시 `80px`으로 확장

**트렌드 표시 권장**

VS Code의 "Trending" 배지 패턴을 채택하되, 팀 맥락에 맞게 간소화한다:

- **조건**: 최근 7일 호출 수가 이전 7일 대비 50% 이상 증가 시
- **표시**: 숫자 좌측에 `↑` 아이콘 (accent 색상, `12×12px`)
- **미표시 기준**: 감소 트렌드(`↓`)는 표시하지 않음 — 팀 내부에서 부정적 신호를 노출하는 것은 사용 의욕을 저해할 수 있음 (Slack이 설치 수를 비공개하는 것과 같은 논리)
- **대안**: 스파크라인은 팀 규모(0~200)에서 변동폭이 작아 시각적으로 평탄해질 수 있으므로, 간단한 아이콘이 더 효과적

**근거**: npm의 스파크라인은 수만 건 이상의 데이터에서 의미 있지만, 0~200 범위에서는 노이즈가 더 클 수 있다. VS Code의 배지 방식이 이 규모에 적합하다.

### 3.2 활성 멤버 컬럼 렌더링 규격

**아바타 스택 표시 규격**

벤치마크 대상 6개 서비스 중 아바타 스택을 사용하는 서비스는 없었으나, v7의 아바타 스택은 "팀 내부 카탈로그"라는 고유한 맥락에서 **강력한 소셜 프루프**로 작동한다. 이를 유지하되 다음 규격을 권장한다:

| 항목 | 규격 | 근거 |
|------|------|------|
| **아바타 크기** | `24×24px` (원형) | 테이블 행 높이(`40px`) 내 시각적 균형 |
| **최대 표시 수** | 2개 (v7 유지) | 3개 이상 시 컬럼 폭 과대. 2개는 "나 외에도 누군가 쓰고 있다"는 신호로 충분 |
| **겹침 오프셋** | `-6px` (우측 아바타가 좌측을 6px 겹침) | 업계 표준 아바타 스택 패턴 (GitHub PR reviewers, Figma collaborators) |
| **"+N" 오버플로** | `24×24px` 원형, 배경 `--bg-tertiary`, 폰트 `11px` bold | 아바타와 동일 사이즈로 시각적 일관성 |
| **"+N" 클릭 동작** | 전체 리스트 팝오버 (v7 유지) | 팝오버 내 각 멤버의 이름, 아바타, 활성화 일자 표시 권장 |
| **정렬** | 좌측 정렬 | 아바타 스택은 좌측 정렬이 자연스러움 |
| **컬럼 폭** | `88px` (아바타 24×2 - 겹침 6 + "+N" 24 + 패딩 22) | 패널 열림 시 숨김(v7 유지) |

**빈 상태 처리**

| 상태 | 표시 | 근거 |
|------|------|------|
| 활성 멤버 0명 | `—` (em dash) | v7 유지. Chrome 웹 스토어의 "메트릭 숨김"보다 명시적 |
| 본인만 활성 | 본인 아바타 1개 | 아바타가 1개여도 표시하여 "활성화 중"임을 확인 |

**추가 권장**: 아바타 호버 시 툴팁으로 멤버 이름 표시 (`150ms` 딜레이). 이는 이니셜 아바타의 식별성 한계를 보완한다.

### 3.3 복사 인터랙션 마이크로 UX

**이름 규칙 최종 권장**

v7의 `{원본 이름} (2)` 넘버링 방식은 **Notion 패턴과 일치**하며, Google Drive/Canva의 접두사 중첩 문제를 피하는 우수한 선택이다. 이를 유지하되 다음을 보강한다:

| 복사 횟수 | 이름 | 비고 |
|----------|------|------|
| 첫 번째 복사 | `{원본 이름} (2)` | v7 유지 |
| 두 번째 복사 | `{원본 이름} (3)` | v7 유지 |
| 이름 충돌 시 | 자동으로 사용 가능한 다음 번호 | v7 유지 |

**권장 보강**: 복사 직후 패널이 열리면서 **이름 필드에 자동 포커스 + 전체 선택** 상태를 제공한다. 이는 GitHub Template의 "이름 입력 강제"와 Notion의 "즉시 사이드바 반영"을 결합한 패턴으로, 사용자가 자연스럽게 의미 있는 이름을 부여하도록 유도한다.

**복사 직후 피드백 및 행동 유도**

v7의 토스트 + 자동 활성화를 유지하되, 다음 시퀀스를 권장한다:

| 단계 | 타이밍 | 동작 | 근거 |
|------|--------|------|------|
| 1. 복사 실행 | 0ms | 테이블에 새 행 삽입 + 하이라이트 애니메이션 (`background-color: --accent-bg`, `300ms ease-out → transparent`) | Notion의 사이드바 즉시 반영 패턴 |
| 2. 토스트 | 100ms | `"'{이름}' 스킬이 생성되었습니다"` (v7 유지) | 확인 피드백 |
| 3. 패널 열림 | 200ms | 우측 패널이 열리며, 이름 필드에 포커스 + 전체 선택 | Figma의 "파일 자동 열림" + GitHub Template의 "이름 입력 유도" 결합 |
| 4. 자동 활성화 | 즉시 | 채팅에서 자동 활성화 (v7 유지) | — |

**토스트 규격**: 
- 위치: 화면 하단 중앙 (또는 토스트 표준 위치)
- 지속 시간: `4000ms`, 자동 해제
- 액션 버튼: `"실행 취소"` (undo) — 실수 복사 시 즉시 삭제 가능 (8초 이내)

**원본 관계 표시 수준**

v7의 "복사 출처: 홍길동의 '매출 분석'" 패널 표시를 유지한다. 이는 GitHub Fork의 "forked from" 패턴을 팀 맥락에 맞게 간소화한 우수한 설계이다.

**추가 권장**:
- 출처 텍스트를 클릭 시 원본 스킬 패널로 네비게이션 (GitHub의 fork source 링크 패턴)
- 원본이 삭제/비활성화된 경우: `"복사 출처: (삭제됨)"` 또는 `"복사 출처: 홍길동의 '매출 분석' (비활성)"` — 링크 비활성화, 텍스트 `--text-disabled` 색상

**테이블 내 배치 위치**

| 현재 정렬 기준 | 배치 위치 | 근거 |
|--------------|----------|------|
| 호출 수 내림차순 (기본) | 활성 그룹 최하단 (호출 수 0이므로) | 정렬 일관성 유지 |
| 이름순 | 알파벳 순서에 따른 자연 위치 | — |
| 최근 생성순 | 최상단 | 가장 최근 아이템이므로 |

**권장**: 복사 직후 새 행에 `2초간 하이라이트 애니메이션`을 적용하여, 정렬 위치와 무관하게 사용자가 새 스킬을 즉시 식별할 수 있게 한다. 스크롤이 필요한 경우 자동 스크롤(`scrollIntoView({ behavior: 'smooth', block: 'center' })`)을 적용한다.

### 3.4 빈 상태 / 엣지 케이스 가이드

**호출 수 0, 활성 멤버 없음**

| 상태 | 호출 수 표시 | 활성 멤버 표시 | 추가 권장 |
|------|------------|--------------|---------|
| 신규 스킬 (아직 한 번도 호출되지 않음) | `0` (dimmed, `--text-tertiary`) | `—` | 호버 시 툴팁: "아직 사용된 적 없습니다" |
| 과거에 사용되었으나 현재 활성 멤버 없음 | `47` (정상 표시) | `—` | — |
| 활성 멤버는 있으나 호출 수 0 | `0` | 아바타 표시 | 스킬이 활성화되었으나 아직 채팅에서 호출되지 않은 상태 |

**근거**: `0`을 표시하는 것은 npm, VS Code, Figma의 일관된 패턴이며, Chrome 웹 스토어처럼 숨기면 "데이터 로딩 실패"로 오해할 수 있다. 단, `--text-tertiary` 색상으로 시각적 위계를 낮추어 "아직 사용되지 않음"을 부드럽게 전달한다.

**복사본이 많아질 때의 이름 관리**

| 시나리오 | 현재 v7 | 권장 보강 |
|---------|--------|---------|
| 같은 원본에서 5개 이상 복사 | `(2)`, `(3)`, ..., `(6)` | 자동 넘버링 유지, 패널 이름 편집 유도로 의미 있는 이름 부여를 촉진 |
| 팀 내 동일 스킬 복사본 과다 | 각각 독립 행으로 표시 | **그룹핑 힌트**: 동일 원본에서 파생된 복사본들을 시각적으로 묶어 표시하는 것을 v8 이후 검토 (예: "매출 분석" 그룹 아래 변형들을 접을 수 있는 UI) |
| 원본 삭제 후 복사본만 남음 | 독립 스킬로 유지 | 출처 표시에서 "(삭제됨)" 라벨 추가. 복사본 자체는 정상 동작 유지 |

**컬럼 축약 시 (패널 열림)**

v7의 현재 동작(호출 수 유지, 활성 멤버 숨김)을 유지한다. 이는 정보 밀도 우선순위(호출 수 > 활성 멤버)에 부합하며, VS Code의 목록 뷰에서 설치 수를 항상 표시하되 평점은 상세 페이지로 미루는 패턴과 일치한다.

## 부록: 조사 방법론 및 한계

**조사 방법**:  
각 서비스의 공식 문서, 헬프 센터, 개발자 문서, API 문서를 1차 소스로 활용하였다. 공식 문서로 확인할 수 없는 세부 사항(정확한 픽셀 값, 애니메이션 타이밍 등)은 업계 관례와 디자인 시스템 표준(Material Design 3, Apple HIG 2024, Radix Primitives)을 기반으로 권장하였으며, 해당 부분에는 "업계 관례 기반" 표기를 포함하였다.

**한계**:  
1. ChatGPT Enterprise 관리 뷰는 계정 접근이 필요하여, OpenAI 공식 헬프 센터 문서와 서드파티 분석 도구(GPTBoost 등)의 공개 정보에 의존하였다.
2. Slack App Directory의 내부 관리자 대시보드 상세 UI는 Enterprise Grid 접근이 필요하여 공식 문서 기반으로 조사하였다.
3. 각 서비스의 UI는 A/B 테스트, 점진적 롤아웃 등으로 사용자/지역별로 다를 수 있다.
4. 권장 규격의 구체적인 px, 색상, 타이밍 값은 실제 구현 시 디자인 시스템 토큰과 조율이 필요하다.
