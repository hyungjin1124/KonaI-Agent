## Part 1: 테이블 + 슬라이드 패널 (R1)

### 1-1. Linear

**화면 구조**

Linear는 이슈 리스트에서 "리스트 뷰"와 "보드 뷰"를 지원하며, 이슈 클릭 시 전체 페이지(full-page) 전환이 기본 동작이다. 별도로 **Split View**(Inbox, Triage에서 제공)와 **Space(Peek)** 기능이 존재한다.

```
┌─────────────────────────────────────────────────────┐
│ [사이드바]│  이슈 리스트 (리스트 뷰)                  │
│           │  Display: ID,Priority,Status,Labels,...   │
│  팀       │  ┌─────────────────────────────────────┐ │
│  프로젝트 │  │ ENG-123 │ High │ 로그인 버그   │김│ │
│  사이클   │  │ ENG-124 │ Med  │ API 리팩토링  │박│ │
│  뷰       │  │ ...                                 │ │
│           │  └─────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

**Split View (Inbox/Triage 전용)**
```
┌───────────────────────────────────────────────────────┐
│ [사이드바]│ 이슈 목록 (축약)  │ 이슈 상세 (우측 패널)  │
│           │ ENG-123 로그인..  │ 제목: 로그인 버그       │
│           │ ENG-124 API 리.. │ 설명: ...               │
│           │ ▸ENG-125 ...     │ 메타: Status, Priority  │
│           │                  │ 댓글, 활동 로그         │
└───────────────────────────────────────────────────────┘
```

- **컬럼 축약 규칙**: Split View에서는 왼쪽 목록이 이슈 제목(Summary) + 아이콘(상태, 우선순위)만 표시. Labels, Assignee, Estimate 등 기타 속성은 숨겨짐. Display Options에서 사용자가 어떤 프로퍼티를 표시할지 직접 선택 가능(ID, Priority, Status, Labels, Project, Cycle, Created, Updated, Assignee, Estimate 등)
- **패널 폭/리사이즈**: Split View 비율은 약 30:70(리스트:상세). 드래그 리사이즈 미지원(미확인). 이슈 상세 페이지에서는 콘텐츠 영역과 우측 Properties 패널이 나란히 배치되며, 화면이 커지면 비례적으로 확장됨
- **패널 내 섹션 구성**: 이슈 상세 페이지: 헤더(제목, 상태 배지) → 본문(설명, 마크다운 에디터) → 활동/댓글. 우측에 메타 Properties 패널(Status, Priority, Assignee, Labels, Project, Cycle 등)
- **전체 확장 패턴**: 이슈 클릭 시 기본적으로 URL 라우트가 변경되면서 전체 페이지로 전환(라우트 변경 방식). Peek: `Space` 키로 호버 중인 이슈를 빠르게 미리보기(오버레이 팝오버)
- **키보드 네비게이션**: 매우 충실. `↑↓`로 이슈 간 이동, `Enter`로 이슈 열기, `Esc`로 뒤로 가기. `Space`로 Peek. `J/K`로 이슈 이동, `X`로 선택. `Cmd+K`로 글로벌 커맨드 팔레트. G+I (Inbox), G+M (My Issues) 등 네비게이션 단축키
- **다른 행 클릭 시 전환**: Split View에서 다른 이슈 클릭 시 즉시 우측 패널 콘텐츠가 교체됨. 별도 애니메이션 없이 빠른 전환(스냅 전환)

**장점**: 키보드 중심 설계로 빠른 탐색. Display Options으로 속성 표시/숨김 세밀 제어. 전체 페이지 전환이 기본이라 상세 정보 접근성 우수  
**단점**: Split View가 Inbox/Triage에만 제한적으로 제공. 일반 이슈 리스트에서는 테이블+사이드 패널 패턴이 아닌 전체 페이지 전환만 가능

### 1-2. Jira

**화면 구조**

Jira는 보드(Kanban/Scrum)와 백로그(Backlog) 뷰에서 "Issue Detail View" 사이드 패널을 제공한다. 리스트(필터) 뷰에서도 "Detail View" 토글로 Split 레이아웃을 활성화할 수 있다.

```
┌──────────────────────────────────────────────────────────┐
│ [프로젝트 사이드바] │  백로그 리스트               │ 이슈  │
│                    │  Sprint 1 (3 issues)        │ 상세  │
│  보드              │  ┌─ KON-1 로그인 버그  High │ 패널  │
│  백로그            │  ├─ KON-2 API 개선     Med  │       │
│  타임라인          │  └─ KON-3 UI 수정     Low  │ 설명  │
│                    │  Backlog (12 issues)        │ 댓글  │
│                    │  ┌─ KON-4 ...              │ 필드  │
│                    │  ...                        │       │
└──────────────────────────────────────────────────────────┘
```

- **컬럼 축약 규칙**: 백로그/보드에서 이슈 상세 패널 열릴 때, 좌측 리스트는 축약됨. Summary(제목) + Issue Key + Assignee 아이콘만 표시. 카테고리, 스토리 포인트, 설명 등은 숨겨짐. Issue Detail View에서 표시할 필드는 Board Settings > Issue Detail View에서 관리자가 커스터마이즈 가능(우측 패널에 어떤 필드를 어떤 순서로 보여줄지)
- **패널 폭/리사이즈**: 우측 Issue Detail 패널은 화면의 약 40~50% 차지. 드래그 리사이즈 미지원(많은 사용자들이 우측 패널 숨기기/리사이즈 기능을 요청해왔으며, 커뮤니티에서 Chrome 확장으로 대응). 이슈 전체 페이지에서는 좌측 본문 + 우측 Properties 패널(약 30%) 구조이며, 이 우측 패널도 네이티브 숨김/리사이즈 불가
- **패널 내 섹션 구성**: 이슈 전체 페이지: 좌측(제목, 설명, 첨부파일, 하위 이슈, 링크, 활동/댓글) + 우측 패널(Status, Assignee, Reporter, Priority, Labels, Sprint, Epic 등 필드). 백로그 Side Panel: 유사하나 축약 버전
- **전체 확장 패턴**: 보드/백로그에서 이슈 클릭 시 기본적으로 사이드 패널이 열림. 이슈 키(예: KON-1) 링크 클릭 또는 '전체 화면' 아이콘 클릭 시 전체 페이지로 전환(URL 라우트 변경). 과거에는 모달(팝업) vs 사이드바 전환 옵션이 Labs에 있었으나, 현재 Cloud 버전에서는 기본 동작이 고정
- **키보드 네비게이션**: `J/K`로 이슈 간 이동(리스트 뷰). 보드에서는 방향키로 카드 이동 가능. `Enter`로 이슈 열기. 글로벌 단축키는 Linear 대비 제한적
- **다른 행 클릭 시 전환**: 사이드 패널이 열린 상태에서 다른 이슈 클릭 시 패널 콘텐츠가 즉시 교체됨. 전환 애니메이션 미미(스냅 전환)

**장점**: Board Settings에서 패널에 표시할 필드 커스터마이즈 가능. 보드/백로그와 사이드 패널 조합으로 컨텍스트 유지하며 상세 확인  
**단점**: 우측 패널 리사이즈/숨기기 네이티브 미지원(오랜 사용자 요청사항). 키보드 네비게이션이 Linear 대비 빈약. Cloud/Server 간 동작 차이 존재

### 1-3. Notion

**화면 구조**

Notion 데이터베이스는 Table, Board, List, Gallery, Calendar, Timeline 뷰를 제공하며, 행/카드 클릭 시 **Side Peek**, **Center Peek**, **Full Page** 세 가지 열기 모드를 뷰별로 설정할 수 있다.

```
Side Peek 모드:
┌───────────────────────────────────────────────────────┐
│  데이터베이스 테이블 (좌측)       │ 페이지 상세 (우측) │
│  ┌────────────────────────────┐  │ 제목: 매출 분석    │
│  │이름     │상태│담당│수정일  │  │ 프로퍼티 목록      │
│  │매출 분석│진행│홍 │03/20  │  │ ─────────────      │
│  │보고서   │완료│김 │03/18  │  │ 페이지 본문 콘텐츠 │
│  │회의록   │대기│박 │03/15  │  │ (마크다운 에디터)   │
│  └────────────────────────────┘  │                    │
└───────────────────────────────────────────────────────┘
```

- **컬럼 축약 규칙**: Side Peek 열릴 때 **테이블 컬럼은 축약되지 않음**. 좌측 테이블이 폭이 줄어들면서 스크롤이 필요해질 수 있으나, 컬럼 자체를 자동으로 숨기지는 않음. 사용자가 "Hide/Show properties" 또는 "Freeze up to column" 기능으로 수동 관리. Freeze 기능으로 특정 컬럼(보통 Name)을 고정해 스크롤해도 항상 보이게 할 수 있음
- **패널 폭/리사이즈**: Side Peek는 화면 우측 약 50% 차지. 드래그 리사이즈 미확인. Side Peek 상단 좌측의 아이콘으로 Center Peek, Full Page로 모드 전환 가능(⤡ 아이콘). 좌측 테이블은 Side Peek가 열려도 계속 인터랙티브(다른 행 클릭 가능)
- **패널 내 섹션 구성**: Side Peek 내부: 제목 → 프로퍼티 목록(데이터베이스 열 값들) → 구분선 → 페이지 본문(자유 콘텐츠 블록). Layout Builder(2024 도입)를 사용해 프로퍼티를 그룹(Header, Property Group, Panel)으로 배치 가능. Panel 그룹은 우측 사이드바처럼 보이는 별도 영역에 프로퍼티를 배치
- **전체 확장 패턴**: Side Peek → ⤡ 클릭 → Full Page(URL 라우트 변경). Center Peek는 모달 오버레이. 뷰 설정에서 기본 열기 모드를 Side Peek / Center Peek / Full Page 중 선택 가능. Table, Board, List, Timeline은 기본 Side Peek, Gallery, Calendar는 기본 Center Peek
- **키보드 네비게이션**: 데이터베이스 내 셀 간 이동은 방향키. `Space`로 레코드 확장(Expand). `Enter`로 셀 편집. `Esc`로 Peek 닫기. Linear/Jira 수준의 리스트 네비게이션 단축키는 미제공
- **다른 행 클릭 시 전환**: Side Peek가 열린 상태에서 좌측 테이블의 다른 행 클릭 시 우측 패널 콘텐츠가 교체됨. 테이블은 계속 인터랙티브 상태 유지

**장점**: Side Peek / Center Peek / Full Page 3가지 모드를 뷰별로 유연하게 설정. 좌측 테이블이 Peek 상태에서도 완전히 인터랙티브. Layout Builder로 프로퍼티 배치 커스터마이즈 가능  
**단점**: Side Peek 시 테이블 컬럼 자동 축약 없어 좁은 화면에서 스크롤 부담. 키보드 이슈 목록 네비게이션 부족

### 1-4. Airtable

**화면 구조**

Airtable Grid View에서 행(레코드) 클릭 시 **Expanded Record**(모달 오버레이)가 기본 동작이다. Interface Designer의 Record Detail 레이아웃에서는 **Sidesheet**(사이드 패널)과 **Full-screen** 두 가지 옵션이 제공된다.

```
Grid View + Expanded Record (모달):
┌────────────────────────────────────────────────────┐
│  Grid Table                                         │
│  ┌──────────────────────────────────────────────┐  │
│  │이름    │카테고리│담당│수정일 │호출수│활성  │  │
│  │매출분석│데이터  │홍 │03/20  │  47  │ON   │  │
│  │    ┌─────────────────────────┐               │  │
│  │    │ Expanded Record (모달)  │               │  │
│  │    │ 필드1: 값              │               │  │
│  │    │ 필드2: 값              │               │  │
│  │    │ [Activity] [Comments]  │               │  │
│  │    └─────────────────────────┘               │  │
│  └──────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────┘

Interface Sidesheet:
┌────────────────────────────────────────────────────┐
│  리스트/그리드 (좌측)        │ Record Detail (우측) │
│  ┌──────────────────────┐   │ 필드 그룹 (섹션)     │
│  │ Row 1               │   │ 필드1: 값            │
│  │ Row 2  (선택됨) →   │   │ 필드2: 값            │
│  │ Row 3               │   │ 댓글 / 이력          │
│  └──────────────────────┘   │ [◀ Prev] [Next ▶]   │
└────────────────────────────────────────────────────┘
```

- **컬럼 축약 규칙**: Grid View에서 Expanded Record는 모달 오버레이이므로 테이블 자체는 변경 없음. Interface Sidesheet 모드에서는 좌측 리스트가 축약되나, 축약 규칙은 Interface 빌더에서 설정한 레이아웃에 따름(Grid/List/Gallery 중 선택). Expanded Record에서는 "Show X hidden fields" 버튼으로 숨겨진 필드도 확인 가능
- **패널 폭/리사이즈**: Interface Sidesheet는 좌측 가장자리에 ↔ 아이콘이 나타나 **드래그 리사이즈 가능**. 커스텀 사이징은 브라우저별, 페이지별 저장됨. Expanded Record(모달)는 고정 폭(약 838px)이며 리사이즈 불가(사용자들이 넓히기를 요청해온 사안)
- **패널 내 섹션 구성**: Record Detail(Interface): 섹션별 필드 그룹(Collapsible Groups), 댓글, 이력(Revision History), 버튼(Action). Full-screen vs Sidesheet 선택 가능. Expanded Record(Base): 필드 목록 → Activity(Comments + Revision History) 사이드바. 2023년 레이아웃 개편으로 필드를 섹션/컬럼으로 그룹핑 가능해졌으나, 개별 필드 폭 조정은 제한
- **전체 확장 패턴**: Sidesheet에서 Full-screen으로 전환 가능(Interface). Base Grid에서는 Expanded Record 모달이 기본. Full Page 라우트 전환은 Interface에서만 제공
- **키보드 네비게이션**: Grid에서 `Space`로 레코드 확장. 방향키로 셀 이동. Interface Sidesheet에서 ◀/▶ 버튼(또는 키보드)으로 이전/다음 레코드 네비게이션 지원
- **다른 행 클릭 시 전환**: Sidesheet 열린 상태에서 다른 레코드 클릭 시 콘텐츠 교체. Prev/Next 네비게이션 버튼도 제공

**장점**: Interface Sidesheet에서 드래그 리사이즈 지원. Sidesheet/Full-screen 선택 가능. Collapsible Groups로 필드 정리. Prev/Next 레코드 네비게이션  
**단점**: Base Grid의 Expanded Record는 고정 폭 모달로 유연성 부족. 2023년 레이아웃 변경으로 기존 사용자들이 적응에 어려움을 겪음

### 1-5. Salesforce

**화면 구조**

Salesforce Lightning Experience에서 **Split View**는 리스트 뷰의 "Display As" 옵션 중 하나로, 좌측에 레코드 목록, 우측에 레코드 상세를 동시에 표시한다.

```
┌──────────────────────────────────────────────────────┐
│  Split View                                           │
│  ┌─────────────┐  ┌──────────────────────────────┐   │
│  │ Record List  │  │ Record Detail Page            │   │
│  │ (축약된 4필드)│  │ ┌──────────────────────────┐ │   │
│  │              │  │ │ Record Header             │ │   │
│  │ Acme Corp    │  │ │ Compact Layout Fields     │ │   │
│  │ 2026-03-20   │  │ ├──────────────────────────┤ │   │
│  │ John Smith   │  │ │ Details Tab               │ │   │
│  │ ─────────── │  │ │ Related Lists             │ │   │
│  │ Beta Inc     │  │ │ Activity Timeline         │ │   │
│  │ 2026-03-18   │  │ └──────────────────────────┘ │   │
```

- **컬럼 축약 규칙**: Split View 좌측 목록은 **Table View의 처음 4개 컬럼**만 표시. 이 4개 필드 순서를 바꾸려면 Table View에서 컬럼 순서를 조정해야 함. 리스트 뷰를 Clone하여 Split View 전용으로 컬럼 구성 가능(다른 사용자에게 영향 없음)
- **패널 폭/리사이즈**: 좌측 리스트 폭은 고정(약 25~30%). **접기/펼치기 토글**(화살표 아이콘)으로 리스트를 완전히 숨길 수 있음. 드래그 리사이즈는 미제공. 우측은 표준 Record Detail Page 전체가 렌더링됨
- **패널 내 섹션 구성**: 우측은 일반 레코드 상세 페이지 그대로. Record Header(Compact Layout 필드) → Highlights Panel → Tab(Details, Related, Activity 등). 관리자가 Lightning App Builder로 레이아웃 커스터마이즈 가능
- **전체 확장 패턴**: 좌측 리스트를 접으면 사실상 전체 페이지처럼 사용. 레코드 이름 클릭 시 Full Page 전환(URL 변경). Split View ↔ Table View ↔ Kanban View 간 자유 전환
- **키보드 네비게이션**: 키보드 네비게이션 지원은 하되 Linear 수준은 아님. Tab/Enter로 리스트 항목 이동 및 선택. 접근성 표준(WCAG) 준수
- **다른 행 클릭 시 전환**: 좌측 목록에서 다른 레코드 클릭 시 우측 상세가 교체됨. 별도 전환 애니메이션 없이 즉시 교체

**장점**: Table View의 첫 4개 필드를 자동으로 축약 표시하는 명확한 규칙. 리스트 접기/펼치기 토글. 기존 Record Page를 그대로 우측에 렌더링하여 일관성 유지. Compact Layout으로 중요 필드 관리  
**단점**: 축약 시 표시되는 필드가 4개로 고정. 드래그 리사이즈 미지원. Split View에서 필터/정렬 불가(Table View로 돌아가서 해야 함)

### 2-1. Slack (워크스페이스 커스텀 이모지/워크플로우 관리)

**카탈로그 구조**

Slack 커스텀 이모지 관리는 "Customize [workspace name]" 페이지에서 수행된다. 플랫 리스트 형태로, 검색 가능한 단일 목록이다.

- **카테고리 필터 vs 자유 검색**: 카테고리 필터 없음. 이름 기반 자유 검색(텍스트 필터링)만 제공. 이모지 수가 수백~수천 개까지 갈 수 있으나, 검색이 주요 탐색 수단. 이모지 피커에서는 카테고리별 그룹핑(Smileys, People, Custom 등)이 존재하나, 관리 화면에서는 단일 리스트
- **활성화/비활성 그룹 분리**: 없음. 모든 커스텀 이모지는 추가되면 바로 활성. 삭제만 가능(비활성화 개념 없음). Emoji Pack은 추가/제거로 관리
- **기본 정렬**: 이모지 관리 페이지에서 기본적으로 이름 알파벳순 또는 추가일 순(미확인). 이모지 피커에서는 "최근 사용" 섹션이 최상단에 표시
- **소셜 디스커버리**: 이모지 피커에서 "Frequently Used" 섹션 존재. 다른 팀원의 리액션(reactji)을 보고 해당 이모지를 발견하는 간접적 소셜 디스커버리. 채널에서 다른 조직의 커스텀 이모지를 우클릭하여 자신의 워크스페이스에 추가 가능
- **빈 상태 → 첫 추가**: 메시지 입력란의 스마일 아이콘 → "Add Emoji" → 이미지 업로드 + 이름 지정. 매우 단순한 플로우. Emoji Pack(테마별 사전 제작 이모지 세트)을 한 번에 추가하는 옵션도 제공하여 빈 상태에서 빠르게 채울 수 있음

**평가**: 50개 이하의 아이템에서는 검색만으로 충분히 탐색 가능한 사례. 카테고리 분류 없이 이름 검색 + 최근 사용 패턴으로 운영

### 2-2. Notion (팀 템플릿 갤러리)

**카탈로그 구조**

Notion 템플릿 갤러리는 공식 마켓플레이스(notion.com/templates)와 인앱 템플릿 픽커로 나뉜다. 팀 내부에서는 "템플릿 버튼"과 "데이터베이스 템플릿"으로 자체 템플릿을 관리한다.

- **카테고리 필터 vs 자유 검색**: 공식 갤러리: 카테고리 필터(Marketing, Engineering, HR, Design 등) + 자유 검색 병행. 카드 기반 레이아웃으로 시각적 브라우징 강조. 인앱 템플릿 픽커: 회원가입 시 선택한 직군에 맞는 5개 추천 템플릿 제공 → "Browse all templates"로 전체 접근. 팀 내부 템플릿: 데이터베이스 내 "New" 버튼 드롭다운에 템플릿 목록 표시
- **활성화/비활성 그룹 분리**: 없음. 템플릿은 "사용 가능" 상태만 존재. 팀 내부 DB 템플릿은 추가/삭제만 가능
- **기본 정렬**: 공식 갤러리: 추천순(Featured), 최신순, 인기순. 인앱: 개인화 추천(직군 기반)
- **소셜 디스커버리**: 공식 갤러리에서 "Made by [Creator]" 표시. 팀 내에서는 워크스페이스 내 페이지 공유를 통해 간접 발견. Notion은 온보딩 시 직군/용도 기반 개인화 추천으로 첫 탐색 부담을 줄임
- **빈 상태 → 첫 추가**: 온보딩 시 "Getting Started" 체크리스트 페이지 제공(learn-by-doing). 직군 기반 5개 추천 템플릿으로 빠른 시작. /template 슬래시 커맨드로 즉시 템플릿 생성 가능

**평가**: 개인화 추천 + 카테고리 필터 + 검색의 3중 구조가 다양한 탐색 맥락을 지원. 온보딩에서 빈 상태를 최소화하는 설계가 특히 강함

### 2-3. Figma (팀 라이브러리)

**카탈로그 구조**

Figma 팀 라이브러리는 컴포넌트, 스타일, 변수(Variables)를 파일 단위로 퍼블리시하여 팀/조직 전체에서 사용할 수 있게 하는 시스템이다.

- **카테고리 필터 vs 자유 검색**: Assets 패널에서 텍스트 검색으로 컴포넌트 탐색. 라이브러리별로 그룹핑되어 있으며, 컴포넌트 이름에 `/` 구분자를 사용한 계층 구조(예: Button/Primary/Large)가 사실상의 카테고리 역할. Admin 패널에서는 라이브러리 단위로 검색/관리
- **활성화/비활성 그룹 분리**: **라이브러리 단위로 Enable/Disable** 가능. 팀 관리자가 특정 라이브러리를 팀 기본(Default)으로 설정하거나, 특정 파일 유형(Design/FigJam)에만 활성화. "Approved Library" 마크(체크 아이콘)로 공식 라이브러리와 비공식 라이브러리를 구분
- **기본 정렬**: Assets 패널에서 라이브러리 이름순. Approved 라이브러리가 목록 최상단에 고정(Pin). 라이브러리 내 컴포넌트는 파일 내 페이지/프레임 구조에 따른 알파벳순
- **소셜 디스커버리**: 라이브러리 업데이트 알림 시스템이 소셜 디스커버리 역할. 누군가 라이브러리를 업데이트하면 사용 중인 모든 파일에서 알림 표시 → "Review changes" → Accept/Dismiss. Quick Insert(Shift+I)에서 팀 라이브러리 컴포넌트와 Sticker를 빠르게 삽입
- **빈 상태 → 첫 추가**: 라이브러리 파일 생성 → 컴포넌트/스타일 생성 → "Publish library" → 팀에서 Enable. UI Kit(Figma 제공 기본 컴포넌트 키트) 활용 가능. Admin에서 조직 전체 기본 라이브러리 설정으로 신규 팀원도 즉시 접근

**평가**: 10~50개 아이템에는 과도할 수 있는 시스템이지만, "Approved" 마크와 기본 활성화 설정이 팀 규모 카탈로그에서의 "신뢰할 수 있는 아이템 식별" 패턴으로 참고할 만함

### 2-4. Google Workspace (확장 프로그램 마켓플레이스, 팀용 관리)

**카탈로그 구조**

Google Workspace Marketplace는 대규모 퍼블릭 마켓플레이스이지만, 관리자가 팀용으로 제한하는 "Whitelist/Allowlist" 모드에서는 소규모 카탈로그가 된다.

- **카테고리 필터 vs 자유 검색**: 마켓플레이스: 카테고리 필터(Business Tools, Education, Productivity 등) + 검색 + "Works with" 필터(Gmail, Docs, Sheets 등). Admin Console(팀 관리): 앱 이름 검색 + 설치 상태 필터. Whitelist 모드에서는 관리자가 선별한 앱만 표시
- **활성화/비활성 그룹 분리**: 관리자 콘솔에서 앱별 **Install(설치됨)/Not Installed** 상태 분리. "Admin Managed" 앱은 관리자가 전체 조직에 푸시 설치. 3가지 정책: (1) 모든 앱 허용 (2) Whitelist만 허용 (3) 모두 차단
- **기본 정렬**: 마켓플레이스: 추천순(Featured), 인기순(설치 수), 별점순. Admin 콘솔: 이름순
- **소셜 디스커버리**: 마켓플레이스에서 설치 수(예: "4.5M+")와 별점이 인기도 시그널. Admin Managed 앱은 관리자가 큐레이션하므로 사실상 "팀에서 추천하는 앱" 역할. Gmail/Docs 우측 사이드바의 + 아이콘으로 인앱 발견
- **빈 상태 → 첫 추가**: 마켓플레이스 브라우징 → 설치 버튼 클릭. Admin Managed: 관리자가 앱 선택 → 조직 전체 또는 특정 OU에 자동 배포. 사용자 입장에서는 앱이 이미 설치되어 있는 상태로 시작

**평가**: "Admin Managed" 모드가 팀 규모 카탈로그의 "관리자 큐레이션 + 자동 배포" 패턴으로 참고할 만함. Whitelist 모드에서의 제한된 카탈로그 경험은 10~50개 스킬 관리와 유사

### 2-5. Retool (내부 앱 카탈로그)

**카탈로그 구조**

Retool은 내부 앱을 빌드하는 플랫폼으로, 빌드된 앱들의 목록이 "Home" 또는 "Apps" 페이지에 표시된다. 팀 내부 앱 카탈로그 역할을 한다.

- **카테고리 필터 vs 자유 검색**: 앱 목록에서 텍스트 검색 제공. Folder(폴더)로 앱을 카테고리별 분류 가능. Header/Sidebar 네비게이션으로 앱 간 이동. 소규모(10~50개)에서는 폴더 분류 + 검색으로 충분
- **활성화/비활성 그룹 분리**: 앱별 Published/Draft 상태. RBAC(역할 기반 접근 제어)로 특정 사용자/그룹에만 앱 노출. "Production" vs "Staging" 환경 구분
- **기본 정렬**: "Recently viewed" 또는 "Last modified" 기본. 폴더 구조 내에서는 이름순
- **소셜 디스커버리**: 팀원의 앱 사용 패턴은 직접적으로 노출되지 않음. 다만 앱별 접근 권한이 팀/역할 기반이므로, 자신이 볼 수 있는 앱 = 팀에서 관련된 앱이라는 간접적 큐레이션. Header/Sidebar 네비게이션에 pinned된 앱이 "자주 사용" 역할
- **빈 상태 → 첫 추가**: "Create new app" 버튼 + 템플릿 갤러리. AI App Generation(자연어로 앱 설명 → 자동 생성). 템플릿(Product Catalog, User Management 등)으로 빠른 시작

**평가**: 폴더 구조 + 검색 + "Recently viewed" 정렬이 10~50개 규모에서 효과적. Published/Draft 상태 구분은 활성/비활성과 유사한 패턴

## Part 3: KonaI-Agent 적용 권장안

### 3.1 테이블+패널 구조 권장안

**채택할 패턴 + 근거**

1. **컬럼 축약: Salesforce 방식 채택 (명시적 규칙 기반)**
   - v7 설계의 "이름 + 작성자 + 호출 수 + 활성화 토글만 유지"는 Salesforce의 "첫 4개 컬럼 표시" 원칙과 유사하며 적절함. 다만 Notion처럼 테이블을 아예 축약하지 않는 접근과 비교해보면, 10~50개 스킬 규모에서는 축약 규칙이 있는 편이 패널 콘텐츠에 더 많은 공간을 제공할 수 있으므로 v7의 축약 규칙을 유지하되, 어떤 컬럼을 남길지 사용자가 커스터마이즈할 수 있는 옵션도 검토할 만함

2. **패널 폭: Airtable Sidesheet 방식 (드래그 리사이즈) 권장**
   - 드래그 리사이즈를 지원하면 사용자가 자신의 워크플로우에 맞게 비율을 조정할 수 있음. Jira에서 패널 리사이즈 미지원이 장기간 사용자 불만 사항이었음을 참고. 기본 비율은 약 40:60(테이블:패널)으로 설정하되, 리사이즈 허용

3. **패널 열기 모드: Notion 방식 (Side Peek + Full Page 전환) 채택**
   - v7의 "[↗ 전체 확장] 버튼으로 전체 페이지 전환"은 Notion의 Side Peek → ⤡ → Full Page 패턴과 일치. 적절한 설계임. Airtable의 Sidesheet → Full-screen 전환도 동일 패턴

4. **패널 접기 토글: Salesforce 방식 채택**
   - 패널을 완전히 접어 테이블 전체 폭으로 복귀하는 토글 버튼 추가 권장. Salesforce의 ▸ 접기 화살표가 가장 직관적

5. **키보드 네비게이션: Linear 방식 참고**
   - `↑↓`로 행 이동, `Enter`로 패널 열기, `Esc`로 패널 닫기는 필수. 추가로 `Space`로 빠른 Peek(Airtable/Linear) 고려

**v7 설계에서 변경이 필요한 부분**

- 패널 접기/펼치기 토글 버튼 추가 (현재 설계에 명시 안 됨)
- 드래그 리사이즈 지원 여부 검토 (현재 설계에 명시 안 됨)
- 키보드 네비게이션 명세 추가 (↑↓ 행 이동, Enter 패널 열기, Esc 닫기, Space Peek)
- 패널 열린 상태에서 다른 행 클릭 시 즉시 교체(스냅 전환) 명시 — 5개 서비스 모두 이 패턴

**구현 시 주의사항**

- 축약 시 숨겨지는 컬럼(설명, 카테고리, 수정일, 버전, 활성 멤버)의 정보 손실이 탐색 효율에 미치는 영향을 사용성 테스트로 검증 필요
- 리사이즈 상태 저장: 브라우저별/사용자별로 패널 폭 기억(Airtable 방식)
- 패널 전환 시 포커스 관리: 패널이 열릴 때 패널 내부로 포커스 이동, Esc로 테이블로 복귀

### 3.2 팀 탐색 UX 권장안

**채택할 패턴 + 근거**

1. **탐색 수단: 검색 우선 + 카테고리 필터 보조**
   - 10~50개 규모에서 Slack처럼 검색만으로 충분히 운영 가능. 다만 v7에 이미 카테고리(4종) 필터가 있으므로 유지하되, 필터가 검색의 보조 수단임을 UI에서 명확히 해야 함(검색바를 필터 드롭다운보다 시각적으로 우선 배치)

2. **활성/비활성 그룹 분리: v7 방식 유지 (2그룹 분리)**
   - 조사한 서비스들 중 Figma(Enable/Disable)와 Retool(Published/Draft)이 유사한 2상태 분리를 제공. 10~50개에서 2그룹 분리는 "내가 쓸 수 있는 것"과 "꺼져 있는 것"을 빠르게 구분하는 데 효과적. 다만 비활성 그룹이 기본 접힌 상태(Collapsed)로 시작하면 활성 스킬에 집중하기 좋음

3. **기본 정렬: "호출 수 순" 유지 + "최근 사용" 옵션 추가**
   - v7의 활성 그룹 "호출 수 많은 순"은 Slack의 "Frequently Used" 패턴과 맞닿음. 추가로 "최근 내가 사용한 순" 정렬 옵션을 제공하면 개인화 탐색이 강화됨(Retool의 "Recently viewed"와 유사)

4. **소셜 디스커버리: "활성 멤버" 컬럼 활용 강화**
   - v7의 "활성 멤버" 컬럼([홍][김]+3)은 이미 소셜 시그널 역할을 함. 이를 더 강화하여, "팀에서 이번 주 가장 많이 사용된 스킬" 같은 하이라이트 배지를 추가하면 Figma의 "Approved" 마크처럼 신뢰/인기 시그널이 될 수 있음

5. **빈 상태 온보딩: Notion 방식 참고 (추천 + 빠른 시작)**
   - 0개 → 첫 스킬 추가까지: (1) "팀에 유용한 스킬 추천" 카드 3~5개 제시(Notion의 직군 기반 추천), (2) "스킬 만들기" CTA 버튼, (3) 예시 스킬을 "비활성" 상태로 미리 넣어두어 구조를 이해할 수 있게 함. Google Workspace의 "Admin 자동 배포" 처럼 팀 생성 시 기본 스킬 세트를 자동 추가하는 것도 검토

**v7 설계에서 변경이 필요한 부분**

- 비활성 그룹 기본 접힌(Collapsed) 상태 여부 명시 필요
- "최근 내가 사용한 순" 정렬 옵션 추가 검토
- 빈 상태(0개 스킬) 화면의 온보딩 플로우 설계 추가 필요
- "이번 주 인기" 등 소셜 시그널 배지 검토

### 3.3 두 영역의 교차점

**패널 열림 시 테이블 축약이 탐색 효율에 미치는 영향**

v7에서 패널이 열리면 "설명, 카테고리, 수정일, 버전, 활성 멤버" 5개 컬럼이 숨겨진다. 이는 탐색 관점에서 다음을 의미한다:

- **숨겨지는 정보 중 탐색에 중요한 것**: "카테고리"가 숨겨지면 필터링 결과를 시각적으로 확인하기 어려움. "활성 멤버"는 소셜 디스커버리의 핵심 시그널인데 숨겨짐
- **권장**: 카테고리를 컬러 태그 또는 아이콘으로 "이름" 컬럼 옆에 인라인 표시하여, 축약 상태에서도 카테고리 정보가 유지되게 하는 방안 검토. 활성 멤버 수(숫자만)를 호출 수 옆에 표시하는 것도 가능

**정렬/필터와 패널 전환 간 인터랙션**

- 패널이 열린 상태에서도 테이블의 필터/정렬을 변경할 수 있어야 함(Notion처럼 좌측 테이블이 계속 인터랙티브). Salesforce Split View에서 필터 변경 시 Table View로 돌아가야 하는 것은 워크플로우 단절을 유발하므로 피해야 함
- 필터/정렬 변경 시 현재 선택된 행이 필터 결과에 포함되지 않으면, 패널을 자동으로 닫거나 "해당 스킬이 현재 필터에 포함되지 않음" 안내 표시 검토
- 검색 입력 시 테이블이 실시간 필터링되면서 패널은 현재 선택된 스킬을 유지하는 것이 자연스러움(패널 콘텐츠까지 바뀌지 않도록)
