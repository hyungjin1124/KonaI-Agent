# 비개발자 대상 자연어 diff 뷰어 UX 리서치 (R2)

> **조사 기준일:** 2026-03-25  
> **대상:** GitHub, Google Docs, Notion, WordPress, Confluence  
> **목적:** 비개발자가 마크다운/자연어 변경을 직관적으로 이해할 수 있는 diff 뷰어 UX 패턴 도출  
> **맥락:** 엔터프라이즈 AI 에이전트 플랫폼의 스킬(SKILL.md) 버전 이력 관리용 diff 뷰어 설계

## 1. 서비스별 분석

### 1-1. GitHub

#### diff 표시 방식

GitHub은 코드 diff의 사실상 표준으로, **Unified(단일 컬럼)** 뷰와 **Split(좌우 병렬)** 뷰를 상단 우측 토글로 전환할 수 있다. 기본값은 Unified이며, 사용자가 마지막으로 선택한 모드가 기본값으로 기억된다.

```
┌─ Unified View ─────────────────────────────────┐
│  @@ -12,7 +12,8 @@ function getData() {          │
│    const url = '/api/data';                     │
│ -  const timeout = 5000;            ← 빨간 배경 │
│ +  const timeout = 30000;           ← 녹색 배경 │
│ +  const retries = 3;               ← 녹색 배경 │
│    return fetch(url);                           │
│  ⋯ (20줄 접힘, 클릭하여 펼치기) ⋯              │
│    export default getData;                      │
└─────────────────────────────────────────────────┘
```

#### 색상 체계

- **삭제 줄:** 연한 빨간 배경(#ffeef0) + 줄 전체 하이라이트
- **추가 줄:** 연한 녹색 배경(#e6ffec) + 줄 전체 하이라이트
- **단어 수준 변경:** 줄 내에서 실제 변경된 단어/문자를 더 진한 빨간/녹색으로 강조 (line-level diff 위에 word-level diff 중첩)
- **접두사:** 삭제는 `-`, 추가는 `+` 기호가 줄 번호 옆에 표시
- 색맹 대응은 색상만이 아닌 `+`/`-` 기호를 함께 사용하지만, 아직 색상 커스터마이징은 공식 미지원

#### 접힘/펼침 규칙

- 변경 지점 전후 **3줄** 맥락 유지 (기본값)
- 접힌 영역은 회색 배경의 "unfold" 버튼으로 표시 (↕ 아이콘)
- 클릭 시 **20줄씩 점진적으로 확장** (위쪽/아래쪽 방향 선택 가능)
- Alt+클릭으로 해당 파일의 모든 접힌 영역을 한 번에 펼칠 수 있음

#### 비개발자 관점에서의 장점과 한계

**장점:**
- Unified 뷰는 스캔이 빠르고 세로 공간 효율적
- 단어 수준 하이라이트가 줄 내 정확한 변경 위치를 보여줌
- PR의 "Files changed" 탭에서 변경 파일 목록 → 각 파일 diff로 연동

**한계:**
- 줄 번호, `@@` hunk 헤더 등 코드 전용 메타 정보가 비개발자에게 시각적 노이즈
- `+`/`-` 접두사는 자연어 맥락에서 의미가 직관적이지 않음
- 마크다운 원문(raw)으로만 diff를 보여줌 — 렌더링된 결과 비교 불가
- 변경 요약과 diff 간 자동 연동(앵커 스크롤 등) 없음

#### 좁은 폭 대응

- Unified 뷰는 좁은 폭에서도 잘 작동 (한 줄이 길면 줄바꿈)
- Split 뷰는 뷰포트 폭이 좁을 때 가로 스크롤 발생
- 모바일 GitHub에서는 Unified 뷰만 지원

### 1-2. Google Docs

#### diff 표시 방식

Google Docs는 두 가지 변경 추적 메커니즘을 제공한다:

**1) 제안 모드(Suggesting Mode) — 실시간 인라인 추적**

문서 편집 시 "제안(Suggesting)" 모드로 전환하면, 모든 편집이 제안 형태로 인라인 표시된다.

```
┌─ Google Docs 제안 모드 ───────────────────────────┐
│                                                    │
│  프로젝트 일정을 확인하고, ██표로 정리합니다██     │
│  ██차트로 시각화합니다██                           │
│                     ↗ 우측 댓글 풍선:              │
│                        "사용자A가 제안:            │
│                         '표로 정리합니다' →        │
│                         '차트로 시각화합니다'"      │
│                        [✓ 수락] [✗ 거절]           │
│                                                    │
└────────────────────────────────────────────────────┘
```

- 삭제된 텍스트: 본문 내 **취소선 + 색상(사용자별 고유색)**
- 추가된 텍스트: **색상 텍스트**로 인라인 삽입
- 우측 여백에 **제안 댓글 풍선** 표시 (제안자 이름, 수락/거절 버튼)
- 사용자별 다른 색상 자동 부여 (첫 번째 사용자 녹색, 두 번째 사용자 보라 등)

**2) 문서 비교(Compare Documents) — 두 문서 간 diff**

Tools > Compare Documents로 두 버전을 비교하면 **새 문서가 생성**되며, 차이점이 제안 모드의 형태로 표시된다.

**3) 버전 기록(Version History)**

- 사이드바에 타임라인 형태로 버전 목록 표시
- 선택한 버전의 변경 사항을 **색상 하이라이트**로 본문에 직접 표시
- 복수 사용자의 편집은 사용자별 색상으로 구분

#### 색상 체계

- 제안 모드: 사용자별 고유 색상 (녹색, 보라, 파랑 등)
- 삭제: 취소선 + 해당 사용자 색상
- 추가: 해당 사용자 색상의 텍스트
- 버전 기록: 변경 부분을 에디터별 색상으로 하이라이트 (토글로 끄기 가능)

#### 접힘/펼침 규칙

- **접힘 없음** — 제안 모드는 문서 전체를 WYSIWYG로 보여줌
- 변경 없는 영역도 그대로 표시되어 전체 맥락 유지
- 긴 문서에서는 스크롤이 길어질 수 있으나, 우측 댓글 풍선이 네비게이션 역할

#### 비개발자 관점에서의 장점과 한계

**장점:**
- WYSIWYG 환경에서 변경을 확인하므로 **가장 직관적**
- 취소선/컬러 텍스트는 종이 문서의 빨간펜 교정과 유사 → 비개발자 친화적
- 제안 단위로 개별 수락/거절이 가능하여 세밀한 제어
- "모두 수락/거절" 일괄 처리 가능

**한계:**
- diff 전용 뷰가 없음 — 변경이 많은 긴 문서에서 변경 지점만 빠르게 보기 어려움
- 접힘 기능 부재로 긴 문서의 변경 위치 파악에 스크롤 필요
- 비교 결과가 별도 문서로 생성되어 원본과의 참조가 불편
- 마크다운 원문 diff 불가 (WYSIWYG만)

#### 좁은 폭 대응

- 모바일 앱에서도 제안 모드 지원
- 댓글 풍선은 모바일에서 본문 하단 또는 탭으로 이동
- 반응형 설계가 잘 되어 있어 좁은 폭에서도 인라인 변경 가시성 유지

### 1-3. Notion

#### diff 표시 방식

Notion은 "페이지 히스토리(Page History)" 기능을 제공하며, 변경 비교는 상대적으로 단순하다.

- 우상단 `···` 메뉴 > Page History에서 **시간순 버전 목록** 표시
- 특정 버전 선택 시 해당 시점의 페이지를 **전체 렌더링** 상태로 보여줌
- 변경된 블록(텍스트, 이미지, 테이블 등)을 **하이라이트**로 표시
- 하이라이트 색상은 **연한 노란 또는 회색 배경** 형태

```
┌─ Notion Page History ─────────────────────────────┐
│  [← 돌아가기]        v3 · 2024-03-25 14:30       │
│                      by 사용자A                    │
│ ┌────────────────────────────────────────────────┐ │
│ │ ## 데이터 분석 프로세스                        │ │
│ │                                                │ │
│ │ ██ 1. 데이터를 수집합니다 ██      ← 하이라이트 │ │
│ │ ██ 2. 차트로 시각화합니다 ██                   │ │
│ │ 3. 결과를 리포트에 포함합니다                  │ │
│ └────────────────────────────────────────────────┘ │
│                        [이 버전 복원]              │
│                                                    │
│  버전 목록:                                        │
│  v3 · 3/25 14:30 · 사용자A                        │
│  v2 · 3/24 10:15 · 사용자B                        │
│  v1 · 3/23 09:00 · 사용자A                        │
└────────────────────────────────────────────────────┘
```

#### 색상 체계

- 변경된 블록: **연한 노란/베이지 배경** 하이라이트
- 삭제/추가 구분이 명확하지 않음 — "이 블록이 변경됨"만 표시
- 삭제된 텍스트와 추가된 텍스트의 시각적 구분 없음

#### 접힘/펼침 규칙

- **접힘 없음** — 페이지 전체를 렌더링된 상태로 보여줌
- 변경된 블록만 하이라이트되므로 스크롤하며 노란 영역을 찾는 방식

#### 비개발자 관점에서의 장점과 한계

**장점:**
- WYSIWYG 렌더링 상태로 변경을 확인 → 비개발자에게 자연스러움
- 블록 단위 하이라이트가 단순하고 이해하기 쉬움
- 10분 간격 자동 스냅샷으로 세밀한 버전 추적

**한계:**
- **진정한 diff 뷰가 없음** — 두 버전의 정확한 텍스트 차이를 보여주지 못함
- 삭제/추가/변경의 구분이 없어, "무엇이" 바뀌었는지 파악하려면 두 버전을 번갈아 봐야 함
- 공식적인 side-by-side 비교 기능 없음
- 커뮤니티에서 WordPress 스타일의 diff 기능 요청이 있으나 미구현
- Free 플랜은 7일, 유료 플랜은 무제한 이력 보관

#### 좁은 폭 대응

- 모바일 앱에서도 페이지 히스토리 접근 가능 (터치 최적화 레이아웃)
- 렌더링 기반이므로 반응형 처리에 무리 없음

### 1-4. WordPress

#### diff 표시 방식

WordPress의 리비전 비교는 5개 서비스 중 **유일하게 side-by-side를 기본값으로 사용하는 비개발자 도구**이다.

```
┌─ WordPress 리비전 비교 ─────────────────────────────────┐
│  ◀ 이전                 ━━━●━━━━━━━━━●━━ 슬라이더 ▶ 다음│
│  ☐ 임의의 두 리비전 비교                                 │
│                                                          │
│  제목                                                    │
│  ┌──── 삭제됨 ────────────┬──── 추가됨 ─────────────┐  │
│  │ 매출 분석 보고서       │ 매출 분석 보고서         │  │
│  └────────────────────────┴──────────────────────────┘  │
│                                                          │
│  본문                                                    │
│  ┌──── 삭제됨 ────────────┬──── 추가됨 ─────────────┐  │
│  │ 데이터를 ██표로██      │ 데이터를 ██차트로██     │  │
│  │ 정리합니다.            │ 시각화합니다.            │  │
│  │                        │ ██빈 셀 발견 시          │  │
│  │                        │ 기본값(0)으로 채움██     │  │
│  └────────────────────────┴──────────────────────────┘  │
│                                        [이 리비전 복원]  │
└──────────────────────────────────────────────────────────┘
```

#### 색상 체계

- **좌측 (이전 버전):**
  - 변경된 단락: 연한 빨간 배경 (#fce4e4 계열)
  - 실제 변경된 단어/구절: **진한 빨간 배경** (#ee7979 계열)
- **우측 (새 버전):**
  - 변경된 단락: 연한 녹색 배경 (#d8ffc1 계열)
  - 실제 변경된 단어/구절: **진한 녹색 배경** (#7ebb5e 계열)
- "삭제됨(Removed)" / "추가됨(Added)" 컬럼 헤더가 명시적으로 표시

#### 접힘/펼침 규칙

- **변경이 없는 필드(제목, 발췌 등)는 아예 표시하지 않는** 방식
- 본문 내에서는 **변경이 없는 단락도 그대로 표시** (접힘 없음)
- 단, 변경 없는 단락은 배경색 없이 일반 텍스트로 표시되어 시각적으로 구분됨

#### 특수 UX: 슬라이더 내비게이션

- 상단에 **타임라인 슬라이더**가 있어 드래그로 리비전 간 이동
- "임의의 두 리비전 비교" 체크박스를 켜면 슬라이더에 핸들 2개가 표시되어 비인접 버전 간 비교 가능
- Previous/Next 버튼으로 순차 탐색

#### 비개발자 관점에서의 장점과 한계

**장점:**
- Side-by-side 비교가 "이전 vs 이후"를 직관적으로 보여줌
- **단어 수준 하이라이트**가 단락 배경과 중첩되어 정확한 변경 위치 파악 가능
- 슬라이더가 시간 흐름에 따른 탐색을 시각적으로 지원
- "삭제됨/추가됨" 컬럼 헤더가 방향성을 명확히 함
- 비개발자 대상으로 설계됨 (코드 메타 정보 없음)

**한계:**
- **HTML 원문으로 diff를 보여줌** — `<p>`, `<a>` 태그가 노출되어 비개발자에게 혼란
- 접힘/펼침이 없어 긴 글에서 변경 위치까지 스크롤 필요
- 변경 요약 기능 없음 (diff만 존재)
- 반응형 처리 미흡 — 좁은 폭에서 side-by-side가 깨질 수 있음

#### 좁은 폭 대응

- 기본적으로 관리자 화면(Dashboard) 전용이라 모바일 최적화 약함
- 좁은 폭에서 side-by-side 테이블이 가로 스크롤되거나 레이아웃 깨질 수 있음
- 코드에서 `show_split_view` 옵션으로 단일 컬럼 전환 가능 (API 수준, UI 토글 미제공)

### 1-5. Confluence

#### diff 표시 방식

Confluence의 페이지 비교는 **렌더링된 WYSIWYG 상태에서 인라인 diff**를 보여준다. 이것이 5개 서비스 중 자연어 문서 diff에 가장 가까운 패턴이다.

```
┌─ Confluence 페이지 비교: v3 → v4 ─────────────────┐
│  << v2→v3 변경 보기    v4→v5 변경 보기 >>          │
│                                                     │
│  데이터 분석 프로세스                               │
│                                                     │
│  1. 데이터를 수집합니다                             │
│  ██ 표로 정리합니다 ██          ← 삭제 (분홍 배경) │
│  ██ 차트로 시각화합니다 ██      ← 추가 (녹색 배경) │
│  2. 결과를 리포트에 포함합니다                      │
│                                                     │
│  . . .   (변경 없는 대량 텍스트 생략)               │
│                                                     │
│  트리거: '매출 분석', '매출 보고서'                 │
│  ██ , '분기 보고서' ██              ← 추가 (녹색)  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 색상 체계

Confluence 공식 문서에 따르면 변경 사항은 다음과 같이 하이라이트된다:
- **추가된 콘텐츠:** 녹색 배경 하이라이트
- **삭제된 콘텐츠:** 분홍/빨간 배경 하이라이트 + 취소선
- **서식 변경:** 파란 하이라이트 (일부 버전)
- 변경은 **렌더링된 상태** 위에 표시되므로, 표·목록·이미지 등도 정상 렌더링

#### 접힘/펼침 규칙

- **변경 없는 대량 텍스트는 자동으로 말줄임표(. . .)로 축약**
- 이 방식은 GitHub의 접힘과 유사하나, WYSIWYG 렌더링 상태에서 적용된다는 차이
- `<<` / `>>` 링크로 인접 버전 간 비교로 빠르게 이동 가능

#### 특수 기능: 에디터 내 변경 보기

- 편집기 안에서 `More options > View changes`로 마지막 게시 이후의 변경 사항을 바로 확인 가능
- 이 경우 변경은 개별 작성자에게 귀속되지 않음

#### 비개발자 관점에서의 장점과 한계

**장점:**
- **렌더링된 상태에서 diff를 보여주는** 유일한 전통적 위키 도구
- 표, 목록, 이미지 등 리치 콘텐츠 변경도 시각적으로 확인 가능
- 변경 없는 영역 자동 축약으로 **변경 지점만 빠르게 파악 가능**
- `<<` `>>` 네비게이션으로 인접 버전 간 빠른 이동
- 비개발자 (PM, 기획자)가 주 사용층이므로 자연어에 최적화

**한계:**
- Side-by-side 비교 미지원 (인라인만)
- 변경 요약 기능 없음 (어떤 유형의 변경이 몇 건인지 모름)
- 단어 수준 diff가 아닌 **블록/문단 수준** 하이라이트인 경우가 있음
- 세밀한 단어 수준 변경이 긴 단락 전체를 하이라이트할 때 정확한 변경 위치 파악 어려움
- 서드파티 앱(Scroll Documents 등) 없이는 다중 페이지 문서의 버전 비교 불가

#### 좁은 폭 대응

- Confluence Cloud는 반응형 설계가 되어 있으나, 비교 뷰의 좁은 폭 최적화는 제한적
- 인라인 방식이므로 기본적으로 좁은 폭에서도 큰 문제 없음
- 표가 포함된 비교는 좁은 폭에서 레이아웃이 깨질 수 있음

## 3. KonaI-Agent 적용 권장안

### 3.1 패널(400~500px) diff 권장안

#### 채택할 시각 표현 패턴: "Confluence + Google Docs 하이브리드"

현재 v7 설계(빨간 배경+취소선 / 녹색 배경)는 **적절한 선택**이며, 리서치 결과 다음 세부 조정을 권장한다:

**① 색상 체계 — 현행 유지 + 단어 수준 강조 추가**

```
삭제: 연한 빨간 배경(#ffeef0) + 취소선
   └ 변경된 단어: 진한 빨간 배경(#fdb8c0)
추가: 연한 녹색 배경(#e6ffec)
   └ 변경된 단어: 진한 녹색 배경(#acf2bd)
```

- **2단계 하이라이트**(GitHub/WordPress 패턴): 줄/블록 수준의 연한 배경 + 단어 수준의 진한 배경을 중첩
- 이유: 단락 전체가 하이라이트되면 정확한 변경 위치를 놓칠 수 있음 (Confluence의 약점)
- 비개발자에게 "이 단락이 변경됨" → "이 단어가 변경됨"의 계층적 인지 제공

**② 비교 단위: 단어 수준 (Word-level diff)**

- 줄 단위(line-level)는 코드에 최적화 → 자연어 문서에는 단어 단위가 적합
- 리서치에서 확인된 베스트 프랙티스: "Use word-level diff for prose"
- 한국어 특성상 문장 내 조사·어미 변경도 단어 단위로 포착해야 함

**③ 취소선은 유지하되, `+`/`-` 접두사는 제거**

- GitHub의 `+`/`-` 접두사는 코드 diff 관례 → 비개발자에게 불필요한 시각 노이즈
- Google Docs/Confluence 방식의 "취소선 = 삭제, 색상 텍스트 = 추가"가 더 직관적
- 현행 v7 설계가 이미 이 방식이므로 유지

#### 접힘/펼침 규칙 구체화

현행 "전후 2줄 맥락, 나머지 접힘" 설계를 다음과 같이 보완:

| 규칙 | 값 | 근거 |
|------|----|------|
| 맥락 유지 줄 수 | 전후 **2줄** (현행 유지) | GitHub 3줄 대비 좁은 패널에서 공간 효율 우선 |
| 접힌 영역 텍스트 | `··· (변경 없음, N줄) ···` (현행 유지) | Confluence 말줄임표 패턴과 일치 |
| 접힌 영역 상호작용 | **클릭 시 전체 확장** | 20줄 점진 확장(GitHub)은 좁은 패널에서 불필요한 복잡성 |
| 인접 변경 병합 | 두 변경 사이가 **4줄 이하**이면 접지 않음 | 너무 짧은 접힘은 오히려 가독성 저하 |

```
권장 접힘/펼침 예시:

  1. 데이터를 수집합니다                    ← 맥락 (위 2줄 중 1줄)
  ██ 1-1. 빈 셀 발견 시 기본값(0)으로 ██   ← 추가
  ██      자동 채움                    ██
  2. 표로 정리합니다                        ← 맥락 (아래 2줄 중 1줄)
  3. 결과를 리포트에 포함합니다              ← 맥락 (아래 2줄 중 2줄)

  ··· (변경 없음, 8줄) ···  ← 클릭 시 8줄 전체 펼침

  트리거: '매출 분석', '매출 보고서'        ← 맥락 (위 1줄)
  ██ , '분기 보고서' ██                     ← 추가
```

### 3.2 전체 확장 diff 권장안

#### Side-by-side 토글 구현

전체 확장 시 폭이 충분(800px+)하므로 **WordPress 패턴의 개선 버전**을 권장:

**① 레이아웃**

```
┌──── 이전 (v2) ────────────┬──── 이후 (v3) ────────────┐
│ 2. 표로 정리합니다        │ 2. ██차트로 시각화합니다██ │
│                           │ ██빈 셀 발견 시 기본값(0) ██│
│                           │ ██으로 자동 채움██          │
└───────────────────────────┴─────────────────────────────┘
```

- WordPress의 "삭제됨(Removed)" / "추가됨(Added)" 헤더 대신, **"이전 (v2)" / "이후 (v3)"** 레이블 사용 → 비개발자에게 더 자연스러운 용어
- 동기 스크롤 적용 (Draftable 참고)
- 단어 수준 하이라이트는 패널 뷰와 동일하게 유지

**② Unified ↔ Side-by-side 토글**

```
[한 줄 보기 | 나란히 보기]     ← 비개발자 친화적 용어
```

- "Unified/Split"은 개발자 용어 → **"한 줄 보기 / 나란히 보기"** 사용
- 기본값: 한 줄 보기 (패널 뷰와 동일한 경험 연속성)
- 사용자 선택 기억

**③ 추가 고려 사항**

- 접힘/펼침 규칙은 패널 뷰와 동일하게 유지 (일관성)
- "변경 간 이동" 내비게이션 버튼 추가 (↑ 이전 변경 / ↓ 다음 변경) — GitHub의 PR 리뷰에서 영감
- 마크다운 원문 / 렌더링 전환 토글 (3.4 참조)

### 3.3 AI 요약↔원문 비교 연동 권장안

리서치 결과, 5개 서비스 모두 **AI 변경 요약 → diff 위치 연동** 패턴을 제공하지 않는다. 이는 KonaI-Agent의 **차별화 포인트**이다.

현행 v7 설계(태그 색상 연동 + 앵커 스크롤)를 다음과 같이 구체화:

**① 앵커 스크롤 구현 패턴**

```
AI 요약 블록:
┌──────────────────────────────────────────┐
│ [추가] 빈 셀 처리 규칙 추가  ← 클릭 가능│
│ [변경] 2단계를 차트 시각화로 수정         │
│ [추가] '분기 보고서' 트리거 추가          │
└──────────────────────────────────────────┘
         ↓ 클릭 시
원문 비교 영역:
  - 해당 변경 위치로 **스무스 스크롤**
  - 해당 변경 블록에 **펄스 애니메이션** (0.5초간 밝은 노란 → 원래 색상)
  - 접힌 영역 안에 있으면 **자동으로 펼친 후** 스크롤
```

Google Docs의 "댓글 풍선 클릭 → 본문 해당 위치 하이라이트" 패턴에서 영감을 받되, AI 요약이 댓글 풍선 역할을 하는 구조.

**② 역방향 연동: diff → 요약 하이라이트**

```
원문 비교에서 특정 변경 블록 hover 시:
  → AI 요약 블록의 대응하는 항목에 밑줄/볼드 처리
  → 요약 블록이 스크롤 밖에 있으면 상단에 플로팅 배지로 표시
```

이는 GitHub의 "파일 목록 → diff" 연동의 양방향 확장 버전.

**③ 색상 연동 규칙 (현행 유지 + 명확화)**

| 요약 태그 | 태그 색상 | diff 배경색 | 의미 |
|-----------|-----------|-------------|------|
| [추가] | 녹색 (#22863a) | 연녹색 (#e6ffec) | 새 콘텐츠 추가 |
| [변경] | 주황 (#e36209) | 연노랑 (#fff8c5) | 기존 콘텐츠 수정 |
| [삭제] | 빨강 (#cb2431) | 연빨강 (#ffeef0) | 콘텐츠 삭제 |

- [변경]은 삭제+추가의 복합이지만, AI 요약에서는 "변경"이라는 자연어 표현이 비개발자에게 더 직관적
- diff에서는 [변경] 항목도 내부적으로 삭제(빨간)+추가(녹색)로 표시하되, 주황색 좌측 보더로 "이것이 변경 사항임"을 추가 시그널링

### 3.4 마크다운 원문 vs 렌더링 diff 권장

#### 우리 스킬(SKILL.md)에 적합한 방식: "렌더링 기본, 원문 토글"

리서치 결론:
- **비개발자** 대상 서비스(Google Docs, Notion, Confluence)는 모두 **렌더링된 상태**에서 변경을 보여줌
- **개발자** 대상(GitHub)만 원문 diff를 사용
- WordPress는 HTML 원문을 노출하여 비개발자에게 혼란을 줌 (반면교사)

SKILL.md는 마크다운이지만, 사용자는 PM/기획자이므로:

**① 기본: 렌더링된(WYSIWYG) diff**

```
## 데이터 분석 프로세스          ← 헤딩으로 렌더링

1. 데이터를 수집합니다
  ██ 1-1. 빈 셀 발견 시…██     ← 녹색 하이라이트, 들여쓰기 리스트로 렌더링
2. ██표로 정리합니다██          ← 빨간 취소선
   ██차트로 시각화합니다██      ← 녹색
```

- 마크다운의 `##`, `**`, `-` 등을 렌더링하여 보여줌
- 비개발자가 실제 스킬의 "완성된 모습"을 보며 변경을 확인할 수 있음

**② 토글: 마크다운 원문 diff**

```
[렌더링 보기 | 원문 보기]     ← 토글

## 데이터 분석 프로세스

1. 데이터를 수집합니다
  ██ 1-1. 빈 셀 발견 시…██
2. ██표로 정리합니다██
   ██차트로 시각화합니다██
```

- 고급 사용자 또는 마크다운 문법 자체의 변경(예: 헤딩 레벨 변경 `##` → `###`)을 확인할 때 사용
- 기본값은 "렌더링 보기"

**③ 렌더링 diff에서 마크다운 문법 변경 표시**

마크다운 문법 자체가 변경된 경우(예: `## 제목` → `### 제목`) 렌더링 보기에서는:

```
렌더링 보기:
  ██ [H2→H3] ██ 데이터 분석 프로세스     ← 작은 배지로 문법 변경 표시
```

- 서식 변경을 나타내는 **인라인 배지**를 사용하여, 렌더링 보기에서도 문법 변경을 놓치지 않도록 함
- Confluence의 "서식 변경 = 파란 하이라이트" 패턴에서 영감

---

## 4. 핵심 인사이트 요약

1. **비개발자 대상 diff의 핵심은 "렌더링 상태에서의 인라인 비교"다.** GitHub 방식의 코드 diff를 그대로 가져오면 안 되며, Confluence/Google Docs 패턴이 올바른 참조 모델이다.

2. **단어 수준 diff는 자연어에서 필수다.** 줄/블록 수준만으로는 긴 단락에서 정확한 변경 위치를 찾기 어렵다. GitHub과 WordPress가 제공하는 "2단계 하이라이트"(연한 줄 배경 + 진한 단어 배경)를 채택해야 한다.

3. **변경 없는 영역의 접힘은 차별화 포인트다.** Google Docs와 Notion은 접힘을 지원하지 않아 긴 문서에서 불편하다. Confluence의 말줄임표 접힘과 GitHub의 점진 확장을 결합한 현행 v7 설계가 적절하다.

4. **AI 요약↔diff 연동은 시장에 없는 기능이다.** 5개 서비스 모두 제공하지 않으므로, 이 기능이 잘 구현되면 강력한 경쟁 우위가 된다.

5. **좁은 패널(400~500px)에서는 Unified 인라인이 정답이다.** Side-by-side는 한국어 문장의 잦은 줄바꿈으로 가독성이 크게 떨어진다. 전체 확장 시에만 Side-by-side 토글을 제공하는 현행 설계가 합리적이다.

6. **용어의 비개발자 적응이 필요하다.** "Unified/Split" 대신 "한 줄 보기/나란히 보기", "diff" 대신 "원문 비교", "삭제됨/추가됨" 대신 "이전/이후" 등 자연어 레이블 사용을 권장한다.
