# KonaI-Agent 기능 구조 설계

> 작성일: 2026-03-21
> 목적: 각 메뉴에 어떤 기능을 왜 넣는지, 메뉴 간 연결은 어떻게 되는지 설계
> 대상: 프로토타입 (내부 제품팀 의사결정용)
> 선행 문서: menu-structure.md (메뉴 구조 확정), cross-menu-connections.md (리서치 기반 연결 맵)

---

## 확정된 메뉴 구조 (menu-structure.md 요약)

```
홈/대시보드 | AI 채팅 | 스킬 | 데이터 | 관리자
```

AI 채팅은 이미 개발 중이므로, 다른 메뉴와의 연결점만 본 문서에서 정의한다.

---

## 1. 홈/대시보드

**목적**: 전사 직원의 의사결정 진입점. AI가 발견한 인사이트와 조직 KPI를 한눈에 보여준다.

### 1.1 홈과 대시보드의 관계

**결정: 통합** — 단일 "홈/대시보드" 페이지에서 탭으로 구분

근거:
- 두 화면 모두 "조직 상황 파악"이 목적이므로 분리하면 중복 네비게이션 발생
- ServiceNow AI Control Tower가 단일 중앙 관제 대시보드 패턴. 엔터프라이즈 AI 플랫폼에 적합
- 채팅→대시보드 경로가 단순해짐 (저장 대상이 한 곳)

참고: Datadog, ThoughtSpot, Databricks, Snowflake는 홈과 대시보드를 분리하지만, 이들은 데이터 분석 전용 플랫폼으로 대시보드 자체가 핵심 기능이기 때문. KonaI-Agent는 AI 에이전트 플랫폼이므로 대시보드는 보조 기능.

### 1.2 탭 구성

| 탭 | 역할 | 넣는 이유 |
|----|------|----------|
| **AI 인사이트** (기본) | AI가 자동 발견한 이상 신호, 추세 변화, 기회를 우선순위순 표시 | 제품 차별점. ThoughtSpot AI Highlights, Datadog Watchdog 패턴. 사용자가 직접 분석하지 않아도 AI가 먼저 알려주는 경험 |
| **KPI 대시보드** | 조직 핵심 성과 지표 모니터링 (현재값 + 변화율 + 트렌드) | 엔터프라이즈 기본 기능. 모든 벤치마크 서비스가 제공 |
| **커스텀 대시보드** | 사용자/팀이 만든 대시보드 목록 + 새 대시보드 생성 | AI 채팅 결과를 저장하는 도착점. Databricks Genie→Dashboard 패턴 |

**프로토타입 제외**: "부서별 성과" 탭 — 부서 구조 데이터가 없는 프로토타입 단계에서는 의미 없음

### 1.3 AI 인사이트 통합 수준

리서치에서 4가지 수준이 관찰됨. 프로토타입에서는 Level 1~3 채택, Level 4는 Phase 2:

| 수준 | 설명 | 채택 | 근거 |
|------|------|:---:|------|
| Level 1: 위젯화 | AI 인사이트를 대시보드 위젯으로 추가 | ✅ | Datadog Watchdog Alerts Widget 패턴 |
| Level 2: 자동 푸시 | AI가 자동으로 인사이트 카드를 홈에 표시 | ✅ | ThoughtSpot AI Highlights 패턴. "AI 인사이트" 탭 |
| Level 3: 채팅 통합 | 채팅 분석 결과를 대시보드로 저장 | ✅ | 킬러 유스케이스 #1(자연어 분석)의 결과 저장처 |
| Level 4: 중앙 관제 | AI 거버넌스/리스크/성과 통합 모니터링 | Phase 2 | ServiceNow AI Control Tower. 관리자 메뉴와 역할 분담 필요 |

## 2. 스킬

**목적**: AI 에이전트가 호출하는 업무 자동화 도구를 탐색하고 관리하는 중앙 허브.

### 2.1 왜 최상위 메뉴인가

스킬은 KonaI-Agent의 핵심 제품 가치. "다중팀 협업 플랫폼"에서 스킬 재사용과 관리가 핵심이므로 독립 최상위 메뉴로 배치. Coze(Plugins), Dify(Tools), Datadog(Integrations)가 동일 패턴.

### 2.2 화면 구성

**결정: 단일 목록 뷰 + 필터** — 탭 분리 없음

프로토타입 단계에서 스킬 수가 적으므로 "내 스킬 / 탐색 / 관리"를 탭으로 나눌 이유가 없다.
하나의 스킬 목록에서 "내 스킬 / 전체" 필터로 전환하고, 관리자에게는 전체 스킬이 보이는 구조.

각 스킬에 활성 사용자 수를 직접 표시하면 별도 통계 화면도 불필요.
ChatGPT가 My GPTs와 GPT Store를 분리하는 건 수만 개의 공개 GPT가 있기 때문이지,
조직 내 스킬이 수십 개인 프로토에서는 과도.

탭 분리는 스킬 수가 증가하는 시점에 재검토.

### 2.3 스킬 생성 위치

**결정: AI 채팅에서 생성** — 스킬 메뉴에 별도 생성 기능 없음

근거:
- 채팅에서 대화하며 "이걸 반복 작업으로 만들자" → 스킬 생성이 자연스러운 플로우
- Artifact 패널에서 스킬 정의를 바로 확인·수정 가능
- Claude Code가 정확히 이 패턴: 대화 중 SKILL.md를 생성하며, 별도 스킬 에디터 없음
- 스킬 메뉴는 "만드는 곳"이 아니라 "만들어진 스킬을 관리하는 곳"

스킬 메뉴에서는 기존 스킬의 편집·공유·삭제만 제공. 편집 시에도 채팅으로 이동하여 대화 기반 수정.

### 2.4 스킬의 범위 정의

스킬이 포괄하는 것: MCP 도구, API 커넥터, 프롬프트 템플릿, 워크플로우(복수 도구 조합)

스킬이 포괄하지 않는 것: 에이전트 자체(에이전트는 스킬을 사용하는 주체), 데이터 소스(데이터 메뉴에서 관리)

이 정의는 Claude Code의 SKILL.md 패턴과 일치: 스킬 = "에이전트에게 특정 능력을 부여하는 재사용 가능한 단위"

## 3. 데이터

**목적**: 에이전트가 데이터에 안전하게 접근하기 위해 필요한 뷰 테이블, 의미 관계(온톨로지), 접근 정책을 관리하는 데이터 거버넌스 허브.

### 3.1 왜 별도 메뉴인가

데이터 담당자 전용 메뉴. 일반 직원은 접근하지 않으며, AI 에이전트가 올바른 데이터에 올바른 권한으로 접근하도록 설정하는 "백스테이지" 역할. OpenAI Frontier의 Business Context + Enterprise Security가 합쳐진 개념.

### 3.2 탭 구성

| 탭 | 역할 | 넣는 이유 |
|----|------|----------|
| **뷰 테이블** | ERP 등 소스 DB에서 에이전트가 쿼리할 테이블 목록 탐색, 메타데이터 관리, 개별 접근 제어 | Snowflake Catalog Explorer, Databricks Unity Catalog 패턴. 에이전트가 접근하는 데이터의 출발점 |
| **온톨로지** | 테이블·컬럼·비즈니스 개념 간 의미 관계 정의. 에이전트의 자연어 이해를 위한 시맨틱 레이어 | OpenAI Frontier Business Context, Snowflake Semantic View, ThoughtSpot Worksheet 패턴. KonaI-Agent의 핵심 아키텍처(Neo4j 온톨로지) |
| **접근 정책** | 역할별 테이블/컬럼/행 수준 접근 권한 중앙 관리 | Snowflake RLS, Databricks Unity Catalog Permissions 패턴. 킬러 유스케이스 #3(데이터 접근 제어+AI 거버넌스)의 핵심 |
| **감사 로그** | 데이터 접근 이력 추적, 정책 변경 기록 | Snowflake Access History, Databricks Audit Log 패턴. 엔터프라이즈 컴플라이언스 필수 |

### 3.3 온톨로지 에디터의 범위

**프로토타입**: 읽기 전용 시각화 (그래프 뷰어) + 간단한 편집 (엔티티 추가, 관계 정의)

**프로토타입 제외**:
- ReactFlow 기반 풀 파이프라인 에디터 — 현재 구현되어 있으나 데이터 파이프라인 에디터는 프로토타입 범위 초과. 리서치 결과 Databricks, Snowflake도 파이프라인 에디터를 데이터 메뉴가 아닌 별도 "워크플로우"나 "노트북"에 배치
- AI 자동 온톨로지 생성 — Phase 2 (OpenAI Frontier가 이 방향이나 아직 초기 단계)

### 3.4 접근 정책의 권한 소유자

**결정: 데이터 메뉴에서 정책을 정의하고, 관리자 메뉴에서는 요약만 표시**

근거:
- 데이터 접근 정책은 데이터 구조에 대한 이해가 필요 → 데이터 담당자가 설정하는 것이 자연스러움
- 관리자 메뉴의 "AI 거버넌스"는 정책이 잘 적용되고 있는지 모니터링하는 역할
- Snowflake 패턴: DBA가 Catalog에서 권한 설정, Admin은 감사 로그로 모니터링

## 4. 관리자

**목적**: 사용자·권한·감사·사용량·AI 거버넌스를 통해 엔터프라이즈급 통제를 실현하는 관리 허브.

### 4.1 2depth 카테고리 구조

5~8개 항목을 1depth로 나열하면 구조가 보이지 않는다. 성격별로 3개 카테고리로 묶고, 좌측 네비게이션에서 카테고리 > 항목으로 접근.

**접근 제어** — 누가 무엇에 접근하는가

| 항목 | 역할 | 넣는 이유 |
|----|------|----------|
| **사용자 관리** | 사용자 계정 생성, 역할 할당, 비활성화 | 엔터프라이즈 기본. 모든 벤치마크 서비스 제공 |
| **권한 관리** | 역할 정의, 기능별·데이터별 접근 권한 매트릭스 | RBAC 기반. Snowflake Role Hierarchy, Databricks Unity Catalog Permissions 패턴 |

**모니터링** — 무슨 일이 일어났는가

| 항목 | 역할 | 넣는 이유 |
|----|------|----------|
| **감사 로그** | 플랫폼 전체 활동 로그 (로그인, 권한 변경, AI 사용 등) | Snowflake Access History, Databricks Audit Log. 컴플라이언스 필수 |
| **사용량** | AI 사용량, API 호출, 토큰 소비, 비용 추적 | OpenAI Usage Dashboard, Databricks Billing 패턴. 비용 관리 필수 |

**AI 정책** — AI가 어떻게 행동해야 하는가

| 항목 | 역할 | 넣는 이유 |
|----|------|----------|
| **AI 거버넌스** | AI 가드레일 설정, 콘텐츠 필터, 모델 접근 제어, 데이터 정책 적용 현황 모니터링 | Copilot Studio DLP, OpenAI Apps Settings, ServiceNow AI Control Tower 패턴. 킬러 유스케이스 #3의 관리자 측 |

**Platform Admin 전용** (플랫폼 관리자 역할에만 노출):

| 항목 | 역할 | 넣는 이유 |
|----|------|----------|
| **테넌트 관리** | 고객사(테넌트) 생성, 설정, 격리 관리 | 멀티테넌트 SaaS 대비. 현재는 1개 테넌트이므로 프로토에서는 스텁 |
| **전체 사용량** | 전체 테넌트 통합 사용량, 시스템 리소스 모니터링 | Databricks Account Console, Snowflake ACCOUNTADMIN 패턴 |
| **시스템 설정** | 모델 배포, API 키 관리, 시스템 전역 설정 | 플랫폼 운영 필수 |

### 4.2 AI 거버넌스의 위치

**결정: 관리자 메뉴 내 탭으로 배치**

선택지가 3개 있었음:
1. 관리자 메뉴 내 탭 ← **채택**
2. 데이터 메뉴에 통합
3. 독립 메뉴

채택 근거:
- AI 거버넌스는 "데이터 접근 정책"보다 넓은 범위 (콘텐츠 필터, 모델 접근, 가드레일 등 포함)
- 관리자 역할이 AI 정책을 설정하는 것이 자연스러움. ServiceNow AI Control Tower, Copilot Studio DLP가 관리자 영역에 배치
- 데이터 메뉴의 "접근 정책"은 테이블/행/컬럼 수준의 세분화된 데이터 정책. AI 거버넌스는 이 정책이 잘 적용되고 있는지 + AI 자체의 행동 제약 설정

### 4.3 감사 로그: 데이터 메뉴 vs 관리자 메뉴

데이터 메뉴에도 "감사 로그" 탭이 있고, 관리자 메뉴에도 "감사 로그" 탭이 있음. 차이:

| | 데이터 메뉴 > 감사 로그 | 관리자 메뉴 > 감사 로그 |
|---|---|---|
| **범위** | 데이터 접근 이력만 (누가 어떤 테이블을 언제 조회/수정) | 플랫폼 전체 활동 (로그인, 권한 변경, 스킬 배포, AI 사용 등) |
| **대상 사용자** | 데이터 담당자 | 관리자 |
| **목적** | 데이터 거버넌스 | 보안·컴플라이언스 |

## 5. 메뉴 간 연결점

AI 채팅이 중심 허브 역할을 하며, 다른 메뉴들은 채팅과 양방향으로 연결된다.

### 5.1 핵심 연결 (프로토타입 필수)

| 연결 | 방향 | 설명 | 근거 |
|------|------|------|------|
| **채팅 → 대시보드** | 채팅 결과를 대시보드 위젯으로 저장 | "대시보드에 저장" 버튼 | ThoughtSpot Pin to Liveboard, Databricks Genie→Dashboard |
| **대시보드 → 채팅** | KPI/인사이트 클릭 → 채팅에서 심층 분석 | "AI로 분석하기" 버튼 | 킬러 유스케이스 #1 (자연어 분석) 플로우의 역방향 |
| **채팅 ↔ 스킬** | 채팅 중 스킬 자동 호출 + 스킬 결과가 채팅에 표시 | @멘션 또는 자동 트리거 | Claude auto-trigger, ChatGPT @GPT mention |
| **스킬 → 채팅** | 스킬 상세에서 "채팅에서 실행" | 스킬 테스트/실행 진입점 | 스킬 생성 후 바로 테스트하는 플로우 |
| **데이터 → 채팅** | 에이전트가 온톨로지+접근 정책을 참조해 자연어 질의 이해 | 시스템 레벨 연결 (UI 링크 아님) | OpenAI Frontier Business Context→Agent 패턴 |
| **관리자 → 전체** | RBAC 정책이 모든 메뉴의 접근 권한 제어 | 시스템 레벨 연결 | 엔터프라이즈 기본 패턴 |

### 5.2 보조 연결 (프로토타입 선택)

| 연결 | 방향 | 설명 | 프로토 포함 여부 |
|------|------|------|:---:|
| **스킬 → 대시보드** | 스킬 실행 결과를 대시보드 위젯으로 추가 | 선택 |
| **스킬 ↔ 데이터** | 스킬이 사용하는 데이터 소스 표시 / 데이터에서 관련 스킬 링크 | 선택 |
| **대시보드 → 스킬** | 대시보드 위젯에서 스킬 실행 트리거 | 제외 (Datadog 전용 패턴, 우리 유스케이스에 해당 없음) |
| **데이터 → 대시보드** | 데이터 접근 정책(RLS)이 대시보드 위젯 표시에 자동 적용 | 포함 (시스템 레벨) |
| **관리자 AI 거버넌스 → 데이터 접근 정책** | AI 거버넌스에서 데이터 정책 적용 현황 요약 보기 → 데이터 메뉴로 딥링크 | 포함 |

### 5.3 거버넌스 흐름 (계층 구조)

```
플랫폼 관리자 (시스템 전역 설정)
    ↓ 테넌트/시스템 정책
관리자 (AI 거버넌스 + RBAC)
    ↓ 역할별 접근 권한 + AI 가드레일
데이터 담당자 (접근 정책)
    ↓ 테이블/행/컬럼 수준 세분화된 정책
에이전트 실행 시 적용
    → 채팅, 스킬, 대시보드에서 데이터 조회 시 3단계 정책 순차 적용
```

이 계층은 Snowflake(ACCOUNTADMIN→SYSADMIN→역할→Object Privileges)와 Databricks(Account→Workspace→Catalog→Object)의 공통 패턴.

| 기능 | 제외 이유 |
|------|----------|
