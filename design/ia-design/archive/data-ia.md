# KonaI-Agent — "데이터" 메뉴 IA 설계

> 작성일: 2026-03-21
> 기준: `/design/research/02-data.md` 리서치 기반
> 대상: 데이터 담당자(거버넌스 + 온톨로지 + 접근 제어 관리)

---

## 1. 메뉴 목적 (한 문장)

**에이전트가 데이터에 안전하게 접근하기 위해 필요한 뷰 테이블, 의미 관계(온톨로지), 접근 정책을 중앙집중식으로 관리하는 데이터 거버넌스 허브.**

---

## 2. 고수준 구조

### 메인 탭 구성

데이터 메뉴는 다음 4개 탭으로 구성된다:

```
데이터
├── 뷰 테이블 (View Tables)
├── 온톨로지 (Ontology)
├── 접근 정책 (Access Policies)
└── 감사 로그 (Audit Log)
```

**설계 원칙**:
- Snowflake, Databricks는 "카탈로그 하나의 인터페이스"에서 데이터 탐색+거버넌스를 통합 (조사항목 6)
- OpenAI Frontier는 Business Context(데이터 소스), Enterprise Security & Governance(정책)을 개념적으로 분리하되, 통합적으로 작동 (조사항목 10)
- KonaI-Agent는 분석 기반으로 **탭 기반 분리**(섹션별 명확한 책임)를 채택하되, 탭 간 네비게이션(Breadcrumb, 관련 항목 링크)으로 통합성 제공

---

## 3. 각 탭의 상세 구조

### 3.1. 뷰 테이블 (View Tables) 탭

**목적**: ERP 등 소스 DB에서 에이전트가 실제 쿼리할 테이블(View Tables) 목록을 탐색하고, 메타데이터 정의, 개별 접근 제어 설정

**리서치 근거**:
- Snowflake: "Catalog → Database Explorer"에서 테이블 탐색 (조사항목 2)
- Databricks: "Catalog Explorer"의 트리 구조 + 탭 기반 상세 정보 (조사항목 2)
- ThoughtSpot: "Data 탭 → Tables"에서 테이블 목록 및 컬럼 상세 (조사항목 2)

**화면 구성**:

#### 3.1.1. 테이블 목록 (좌측 사이드바 + 메인 영역)

**좌측 사이드바**:
- 트리 구조: 스키마 → 테이블 (Snowflake, Databricks 패턴)
- 검색/필터: 테이블명, 태그, 소유자, 생성일로 필터링
- "즐겨찾기" 섹션: 자주 접근하는 테이블 빠른 접근 (Databricks Quick Access 참고)

**메인 영역 (리스트 뷰)**:
| 테이블명 | 스키마 | 생성일 | 소유자 | 행 수 | 상태 |
|---------|-------|-------|-------|-------|------|
| customers | dw_main | 2026-02-15 | Data Team | 1.2M | ✓ Active |

- 정렬: 테이블명, 수정일, 접근 빈도 등
- 액션 버튼: "상세보기", "메타데이터 편집", "접근 정책"

#### 3.1.2. 테이블 상세 페이지

테이블 선택 시 우측 패널 또는 상세 페이지 열림.

**탭 구조**:

| 탭명 | 내용 | 리서치 참고 |
|------|------|-----------|
| **Overview** | 테이블 기본 정보: SQL 정의, 데이터 소스, 생성일, 수정일, 소유자, 설명 | Databricks "Overview" |
| **Columns** | 컬럼 목록: 컬럼명, 타입, NULL 여부, 설명, 태그, 민감도 레벨 | Snowflake "Columns" + Databricks Column metadata |
| **Preview** | 최대 100행 데이터 미리보기 (읽기 전용) | Snowflake "Data Preview", Databricks "Sample Data" |
| **Lineage** | 상위(Source) / 하위(Downstream) 데이터 흐름 시각화 (다이어그램) | Databricks "Lineage" 탭 |
| **Access Control** | 이 테이블에 접근할 수 있는 역할/그룹 목록 + 권한 부여 UI | Snowflake "Privileges", Databricks "Permissions" |
| **Metadata** | AI 생성 설명, 태그, 비즈니스 컨텍스트 어노테이션 | Snowflake "Cortex AI-generated description", Databricks "AI-generated Comments" |

**Columns 탭 상세**:
- 컬럼별 상세 정보:
  - 이름, 데이터 타입, NOT NULL
  - 설명/코멘트 (수정 가능)
  - 태그: 데이터 민감도(공개/내부/민감), 카테고리 태그
  - 마스킹 정책 적용 여부 (on/off toggle)
  - PII 표시: "PII" 배지 (자동 감지 또는 수동 표시)
- 액션: "PII 표시", "태그 추가", "마스킹 정책 적용"

**Access Control 탭 상세**:
- 현재 권한 목록 (읽기만, 읽기+쓰기 등)
- 역할별, 그룹별 권한 조회
- "권한 부여" 버튼 → 다이얼로그:
  - 역할/그룹 선택
  - 권한 선택 (SELECT, INSERT, UPDATE, DELETE)
  - 적용 범위: 전체 테이블 or 행 필터 or 컬럼 제한 (조사항목 3 RLS/CLS 패턴)
  - 유효 기간 (옵션)
- "권한 제거" 액션

**Metadata 탭**:
- "설명 생성" 버튼: LLM이 컬럼/테이블 자동 분석하여 설명 생성 (Snowflake Cortex, Databricks AI-generated Comments 참고)
- 생성된 설명 편집 가능
- 비즈니스 컨텍스트: 이 테이블이 사용되는 비즈니스 프로세스 (자유 텍스트 또는 템플릿)

#### 3.1.3. 빠른 액션 (테이블 목록, 상세 페이지 공통)

- "접근 정책" 버튼 → 접근 정책 탭으로 직접 이동하며, 이 테이블 필터 자동 적용
- "온톨로지에서 보기" → 온톨로지 탭으로 이동하며, 해당 엔티티 하이라이트
- "이 테이블을 쓰는 스킬 보기" → (향후 스킬 메뉴 연결)

---

### 3.2. 온톨로지 (Ontology) 탭

**목적**: 데이터 간의 의미 관계(테이블, 컬럼, 비즈니스 개념 간의 매핑)를 정의하고 시각화. 에이전트가 자연어 질문을 이해할 때 참조하는 "의미 계층"

**리서치 근거**:
- OpenAI Frontier: "Business Context" = "시맨틱 레이어" (조사항목 8)
- Snowflake: "Semantic View"로 logical table, relationship, fact, dimension, metric 정의 (조사항목 8)
- Databricks: Entity Relationship Diagram (ERD) + AI Genie semantic layer (조사항목 8)
- ThoughtSpot: "Worksheet"가 시맨틱 레이어 역할 (조사항목 8)
- 현재 KonaI-Agent: Neo4j 기반 온톨로지 아키텍처 (시스템 설계 문맥)

**화면 구성**:

#### 3.2.1. 온톨로지 캔버스 (메인 영역)

- **비주얼 그래프 에디터** (ReactFlow 또는 유사 라이브러리):
  - 노드: 테이블, 비즈니스 개념, 계산 메트릭
  - 엣지: 관계 (FK 관계, "포함한다", "계산된다" 등)
  - 노드 타입 구분 (색상/아이콘):
    - 파란색: 뷰 테이블
    - 녹색: 비즈니스 개념 (예: "고객", "주문", "매출")
    - 주황색: 계산 메트릭 (예: "평균 주문액")

#### 3.2.2. 좌측 패널: 엔티티 라이브러리

- **Entities 섹션**:
  - 비즈니스 개념 목록 (예: 고객, 주문, 상품)
  - 드래그 앤 드롭으로 캔버스에 추가
  - "새 엔티티 생성" 버튼

- **Tables 섹션**:
  - 뷰 테이블 목록 (뷰 테이블 탭에서 동기)
  - 검색/필터
  - 드래그 앤 드롭으로 캔버스에 추가

- **Relationships 섹션**:
  - 정의된 관계 목록
  - 관계 편집/삭제

#### 3.2.3. 우측 패널: 선택 엔티티 상세

캔버스에서 노드 또는 엣지를 선택하면 우측에 상세 정보 표시.

**노드 선택 시** (엔티티/테이블):
- 이름, 설명 (수정 가능)
- 타입 (비즈니스 개념 / 뷰 테이블 / 계산 메트릭)
- 관련 컬럼 (테이블인 경우) 또는 정의식 (메트릭인 경우)
- 예시 데이터 미리보기 (테이블인 경우)
- "삭제" 버튼

**엣지 선택 시** (관계):
- 관계명 (예: "고객이 주문한다")
- 관계 타입 (FK 기반 / 비즈니스 규칙 기반)
- 소스 엔티티 → 대상 엔티티
- 카디널리티 (1:1, 1:N, M:N) (ERD 패턴)
- 관계 조건 (조인 조건 또는 규칙)
- "편집", "삭제" 버튼

#### 3.2.4. 우측 상단: 액션 바

- **"새 엔티티" 버튼**: 비즈니스 개념 또는 메트릭 신규 생성
- **"관계 추가" 버튼**: 두 엔티티 간 관계 정의
  - 다이얼로그: 소스 선택 → 관계명 → 대상 선택 → 조건(SQL) 입력 → 저장
- **"검증" 버튼**: 온톨로지 일관성 검사 (순환 참조, 미정의 관계 등)
- **"레이아웃 자동 정렬" 버튼**: 그래프 자동 배치 (hierarchical, force-directed 등)
- **"내보내기" 버튼**: JSON 또는 Neo4j Cypher로 온톨로지 다운로드

#### 3.2.5. 검색/필터 (우측 상단 또는 전역)

- 전체 온톨로지에서 엔티티/관계 검색
- 예: "매출" 검색 → 매출 관련 모든 엔티티 하이라이트

---

### 3.3. 접근 정책 (Access Policies) 탭

**목적**: 역할(데이터 담당자, 일반 사용자 등)이 어떤 테이블/컬럼/행에 접근할 수 있는지를 중앙집중식으로 정의하고 관리. 에이전트의 접근 범위 제어 지점.

**리서치 근거**:
- Snowflake: "Governance & security → Users & roles" 역할 관리 + "Catalog → Database Explorer → Privileges" 테이블별 권한 (조사항목 3)
- Databricks: "Catalog Explorer → Permissions" 탭 + Unity Catalog 계층적 권한 + ABAC (조사항목 3)
- ThoughtSpot: "Share" 다이얼로그로 OLS/CLS/RLS 설정 (조사항목 3)
- OpenAI Frontier: "Enterprise IAM"으로 에이전트별 scoped permissions (조사항목 3)

**화면 구성**:

#### 3.3.1. 정책 목록 (메인 영역)

테이블/컬럼별 접근 정책 목록을 표 형식으로 표시.

| 정책명 | 정책 타입 | 대상 테이블 | 대상 역할/그룹 | 권한 범위 | 상태 | 수정일 |
|--------|---------|-----------|--------------|---------|------|-------|
| "고객 마스킹" | Column Mask | customers | analyst | 민감 컬럼 마스크 | ✓ Active | 2026-03-10 |
| "지역별 행 필터" | Row Filter | orders | sales_rep | WHERE region = user.region | ✓ Active | 2026-03-05 |
| "감사자 전체 접근" | Base Access | * | auditor | SELECT on all tables | ✓ Active | 2026-02-20 |

- 정렬: 정책명, 타입, 수정일
- 필터: 정책 타입, 대상 테이블, 상태 (Active/Inactive/Scheduled)
- 액션: "상세보기", "비활성화", "복사", "삭제"

#### 3.3.2. 정책 상세/생성 다이얼로그

"새 정책 생성" 또는 기존 정책 "상세보기" 클릭 시 열림.

**Step 1: 정책 기본 정보**
- 정책명 (텍스트)
- 설명 (텍스트 영역)
- 정책 타입 선택 (라디오 버튼):
  - Base Access (기본 권한: 테이블 레벨)
  - Row Filter (행 수준 보안)
  - Column Mask (컬럼 수준 마스킹)

**Step 2: 대상 선택**
- 대상 테이블 (Base Access인 경우 다중 선택 가능, "*" = 모든 테이블)
- 대상 컬럼 (Column Mask인 경우, 다중 선택)
- 대상 역할/그룹 (체크박스 다중 선택)
  - 역할 목록: 데이터 담당자, 에이전트(에이전트명), 분석가, 일반 사용자 등
  - 또는 사용자 정의 그룹 선택

**Step 3: 권한/조건 정의** (정책 타입에 따라 다름)

**3.3.2.1. Base Access 정책**
- 권한 선택 (체크박스):
  - [ ] SELECT
  - [ ] INSERT
  - [ ] UPDATE
  - [ ] DELETE
- 유효 기간 (옵션):
  - [ ] 무기한
  - [선택] 시작일 ~ 종료일 (datepicker)

**3.3.2.2. Row Filter 정책**
- 필터 조건 입력 (SQL WHERE 절 또는 UI):
  - **UI 모드** (기본):
    - 필터 조건: [컬럼] [연산자] [값]
    - 컬럼 선택 (드롭다운): 테이블의 컬럼 목록
    - 연산자: =, !=, >, <, >=, <=, IN, LIKE 등
    - 값: 상수 또는 변수 (예: `@user.region`, `@user.department`)
  - **SQL 모드** (고급, 토글):
    - 직접 SQL WHERE 절 입력 (예: `region = '@user.region' AND status = 'active'`)
- 예시 쿼리 프리뷰: 이 필터가 적용된 샘플 쿼리 표시
- 테스트 버튼: 샘플 데이터로 필터 동작 검증

**3.3.2.3. Column Mask 정책**
- 마스킹 타입 선택 (라디오 버튼):
  - [ ] 완전 숨김 (SELECT 결과에서 컬럼 제거)
  - [✓] 해시 (해시값으로 대체)
  - [ ] 일부 표시 (예: 휴대폰 번호 뒤 4자리만 표시)
  - [ ] NULL (NULL로 대체)
  - [ ] 커스텀 함수 (사용자 정의 SQL 함수)
- 마스킹 패턴 (타입에 따라):
  - "일부 표시": 패턴 정의 (예: "XXX-XXXX-####" → "휴대폰번호의 뒤 4자리 노출")
  - "커스텀 함수": 함수명 입력 (예: `HASH_MD5(email)`)
- 예외 역할 (옵션): 이 마스킹을 적용하지 않을 역할 (예: 데이터 담당자는 제외)

**Step 4: 검토 및 저장**
- 정책 요약 표시:
  ```
  정책: "고객 마스킹"
  타입: Column Mask
  대상: customers.email, customers.phone
  역할: analyst, junior_analyst (제외: data_owner)
  마스킹: 휴대폰 뒤 4자리만 표시
  상태: 활성 (즉시 적용)
  ```
- "저장" 버튼 → 정책 목록으로 돌아옴
- "취소" 버튼

#### 3.3.3. 역할별 권한 매트릭스 (선택적 뷰)

테이블과 역할의 교차 매트릭스로 권한을 시각화 (Snowflake Tags & Policies Dashboard 참고).

| 역할 | customers | orders | products | users |
|------|-----------|--------|----------|-------|
| data_owner | ✓ RW | ✓ RW | ✓ RW | ✓ RW |
| analyst | ✓ R (Row Filter) | ✓ R (Column Mask) | ✓ R | ✗ |
| agent_chat | ✓ R | ✓ R | ✓ R | ✓ R (mask PII) |

- 색상 코딩: 초록(R), 파랑(RW), 회색(No Access), 주황(조건부)
- 셀 클릭 시 정책 상세 표시

#### 3.3.4. 접근 정책 감사

"감사" 버튼 또는 우측 패널:
- 정책 변경 이력 (누가, 언제, 무엇을 변경했는가)
- 예: "2026-03-10 10:15 data_owner가 '지역별 행 필터' 정책 생성"

---

### 3.4. 감사 로그 (Audit Log) 탭

**목적**: 데이터 접근 이력, 정책 변경 기록, 에이전트의 데이터 쿼리 추적. 거버넌스 투명성과 규정 준수.

**리서치 근거**:
- Snowflake: "Access History" + "Query History"로 사후 추적 (조사항목 9)
- Databricks: "system tables" (audit log) + MLflow Trace로 에이전트 추적 (조사항목 9)
- OpenAI Frontier: "built-in monitoring and detailed logs" (조사항목 9)

**화면 구성**:

#### 3.4.1. 로그 목록 (메인 영역)

| 타임스탬프 | 사용자/에이전트 | 액션 | 대상(테이블/컬럼) | 결과 | 상태 |
|-----------|---------------|------|-----------------|------|------|
| 2026-03-21 14:22:15 | chat_agent_001 | SELECT | orders (30 rows) | ✓ Success | - |
| 2026-03-21 14:18:30 | data_owner | POLICY_MODIFY | customers.email (Column Mask) | ✓ Success | - |
| 2026-03-21 14:15:00 | analyst | SELECT | customers (0 rows) | ✗ Blocked | Row Filter 적용 |

- 정렬: 타임스탐프 (최신순 기본)
- 필터:
  - 사용자/에이전트 (다중 선택)
  - 액션 타입 (SELECT, INSERT, POLICY_CREATE, POLICY_MODIFY 등)
  - 대상 테이블 (다중 선택)
  - 날짜 범위 (datepicker)
  - 결과 (Success, Blocked, Error)

#### 3.4.2. 로그 상세

로그 항목 클릭 시 우측 패널 또는 모달:
- 모든 메타데이터:
  - 타임스탐프, 사용자 ID, 에이전트명
  - 액션 (SELECT, INSERT, POLICY_CHANGE 등)
  - 대상 (테이블/컬럼 지정)
  - 쿼리 (SELECT인 경우, 실행된 SQL 표시)
  - 결과 (반환 행 수, 에러 메시지)
  - 응답 시간
- 정책 적용 여부 (이 쿼리에 어떤 정책이 적용되었는가)
- 다운로드: CSV, JSON 형식

#### 3.4.3. 대시보드 뷰 (선택적)

상단에 요약 카드:
- 오늘 접근: N명, M회
- 차단된 접근: N회
- 정책 변경: M건
- 에이전트별 데이터 접근 건수 (파이 차트 또는 바 차트)

## 4. 다른 메뉴와의 연결점

### 4.1. 데이터 ↔ 채팅 (AI 채팅)

**데이터 → 채팅**:
- 에이전트가 온톨로지와 접근 정책을 참조하여 자연어 질문을 이해하고 쿼리 생성
- 사용자의 역할에 따라 정책이 자동 적용 (Row Filter, Column Mask)
- 채팅 세션: 감사 로그에 기록

**채팅 → 데이터**:
- 채팅 인터페이스에서 "이 데이터의 상세" 링크 → 데이터 메뉴의 해당 테이블 상세 페이지로 이동
- 에이전트의 응답에서 "쿼리 확인" → 감시 로그 상세 페이지로 이동

### 4.2. 데이터 ↔ 대시보드 (Liveboard)

**데이터 → 대시보드**:
- 위젯 데이터 소스가 "데이터" 메뉴의 테이블을 참조
- 위젯 생성 시 테이블 선택 → 데이터 메뉴의 뷰 테이블 탭과 동일한 인터페이스
- 행 필터, 컬럼 마스킹 정책이 위젯에 자동 적용

**대시보드 → 데이터**:
- 위젯 상세에서 "데이터 소스 보기" 링크 → 데이터 메뉴의 해당 테이블로 이동

### 4.3. 데이터 ↔ 스킬

**데이터 → 스킬**:
- 테이블 상세 페이지에서 "이 테이블을 쓰는 스킬" 버튼 → 스킬 메뉴로 이동 (스킬 필터링)

**스킬 → 데이터**:
- 스킬 편집 시 "데이터 소스 선택" → 데이터 메뉴의 뷰 테이블 목록으로 이동
- 스킬의 데이터 접근 권한: 데이터 메뉴의 "접근 정책"에 스킬 역할 지정

### 4.4. 데이터 ↔ 관리자 (Admin)

**데이터 → 관리자**:
- 데이터 메뉴는 "데이터 담당자" 역할만 접근 가능 (역할 기반 접근 제어)
- 접근 정책에서 "역할 관리" 링크 → 관리자 메뉴의 역할 관리 페이지로 이동

**관리자 → 데이터**:
- 관리자 메뉴에서는 "데이터 거버넌스 정책" 요약 뷰만 제공 (편집 불가)
- 정책 상세는 데이터 메뉴로 이동

## 5. 역할별 접근 권한

| 역할 | 뷰 테이블 | 온톨로지 | 접근 정책 | 감시 로그 |
|------|---------|---------|---------|---------|
| **데이터 담당자** | RW (메타데이터 편집) | RW (엔티티, 관계 편집) | RW (정책 생성/수정) | R (조회) |
| **관리자** | R (조회만) | R (조회만) | R (조회만, 정책 승인) | R (조회) |
| **에이전트** | 정책에 따라 R/제한 | 참조만 (쿼리 생성 시) | 적용만 (직접 수정 불가) | 로그 기록 |
| **일반 사용자** | 접근 불가 | - | - | 자신의 감시 로그만 R |

## 6. 온톨로지 기반 설계의 핵심 (OpenAI Frontier 패턴 적용)

리서치에서 OpenAI Frontier는 "시맨틱 레이어"를 강조한다 (조사항목 8). 핵심 차이:

- **Frontier의 접근**: "연결 기반 컨텍스트(connectivity-based context)" — 시스템 간 데이터를 찾고 접근하는 **능력**
- **전통적 시맨틱 레이어**: "거버넌스 기반 번역 레이어(governed translation layer)" — 비즈니스 용어의 **정의와 계산 규칙 표준화**

**KonaI-Agent의 설계**:
- **온톨로지 탭**은 두 가지를 통합한다:
  1. **연결**: 테이블 간 FK, 비즈니스 개념 간 의미 관계 (Frontier 스타일)
  2. **정의**: 비즈니스 메트릭의 계산식, 용어의 표준 정의 (전통적 시맨틱 레이어 스타일)

- **에이전트의 사용**:
  - "고객 매출 합계" 자연어 질문 → 온톨로지에서 매출 정의 및 계산식 참조 → 올바른 쿼리 생성
  - Neo4j 그래프 쿼리: 테이블 간 최적 경로 탐색 + 정책 적용

## 7. 프로토타입 우선순위

### Phase 1: MVP (필수 구현)

```
데이터
├── 뷰 테이블
│   ├── 테이블 목록 (트리 구조)
│   ├── 테이블 상세 (Overview, Columns, Preview 탭)
│   └── Access Control 탭 (읽기만)
├── 온톨로지
│   ├── 그래프 캔버스 (시각화만, 편집 불가)
│   └── 엔티티 검색/조회
├── 접근 정책
│   ├── 정책 목록 (읽기만)
│   └── 정책 상세 (조회)
└── 감시 로그
    └── 로그 목록 (필터 + 검색)
```

**리서치 근거**:
- Snowflake, Databricks, ThoughtSpot 모두 "데이터 탐색 + 거버넌스 조회"가 기본 (조사항목 2, 3)
- 정책 생성은 초기에는 데이터 담당자가 SQL 또는 UI로 사전 정의한 후, 이를 조회하는 형태

### Phase 2: 편집 기능 (고급)

```
접근 정책
├── 정책 생성/수정/삭제
└── UI 기반 Row Filter, Column Mask 설정

온톨로지
├── 엔티티 생성/수정/삭제
├── 관계 추가/삭제
└── 그래프 캔버스 편집
```

**리서치 근거**:
- Databricks ABAC는 2025 Public Preview이므로, 초기 버전에서는 기본 권한만 제공 (조사항목 3)
- Snowflake도 정책 생성은 SQL 기반이므로, UI 기반 생성은 선택적 고급 기능

### Phase 3: 확장 (미래)

```
- AI 기반 메타데이터 자동 생성 (Cortex, Genie 참고)
- Knowledge Base / RAG 데이터 관리 (현재는 채팅 사이드바에서 관리)
- 파이프라인 에디터 → 온톨로지와 통합 (Dify Knowledge Pipeline 스타일)
- 자연어 기반 정책 생성 ("이 테이블의 PII는 자동 마스킹해줘")
```

## 8. 기존 ReactFlow 파이프라인 에디터의 위치

### 8.1. 현재 상황

CLAUDE.md에서 "기존에 ReactFlow 파이프라인 에디터가 있었으나 타겟이 불명확"이라고 언급.

### 8.2. 리서치 근거

- **Dify**: Knowledge Pipeline(v1.9.0+)이 비주얼 캔버스 에디터로 RAG ETL 파이프라인을 관리 (조사항목 5)
  - 데이터 소스 노드 → 파싱 → 청킹 → 임베딩 → 저장
  - "Settings → Data Source"와 별도로 "Knowledge Pipeline"이라는 dedicated workflow editor 존재

- **OpenAI Frontier**: Business Context 내에서 데이터 소스 연결 방식은 공개되지 않음. "Forward Deployed Engineers"가 초기 설정을 지원하는 모델

- **KonaI-Agent의 현재 아키텍처**: ERP DB → View Tables → Neo4j Ontology → AI Agent
  - 이 과정에서 "ETL 파이프라인"(데이터 소스에서 뷰 테이블 생성)은 외부 도구(dbt, Python 스크립트 등)에서 관리
  - 데이터 메뉴 내에서는 파이프라인이 필요하지 않음

### 8.3. 결론

**기존 ReactFlow 파이프라인 에디터는 이 설계에 포함되지 않음.**

- 이유 1: View Tables의 생성/유지는 DW 팀의 책임 (데이터 담당자 역할과 분리)
- 이유 2: 온톨로지 탭의 그래프 에디터로 데이터 간 의미 관계는 이미 시각화 가능
- 이유 3: Dify 참고 시에도 "Knowledge Pipeline"은 RAG 데이터 인제스트 전용이며, 구조화 데이터 관리와는 분리

**대안**:
- 향후 "데이터 통합" 기능이 필요해지면, 별도 메뉴로 추가 (예: "데이터" → "파이프라인" 하위 탭)
- 현재는 불필요하므로 우선순위 낮음

## 10. 추가 고려사항

### 10.1. 다국어 지원

- 테이블명, 컬럼명: 영문 (데이터 소스 기준)
- UI 텍스트: 한글
- 온톨로지 엔티티명: 한글 허용 (비즈니스 개념이므로)

### 10.2. 권한 모델 간소화

초기 프로토타입에서는:
- 역할 기반(RBAC): 데이터 담당자, 관리자, 에이전트, 일반 사용자
- 속성 기반(ABAC): Phase 2에서 도입 (태그 기반 정책 상속)

### 10.3. 성능 고려사항

- 테이블 목록이 1000개를 넘을 경우, 가상 스크롤 또는 페이지네이션 적용
- 온톨로지 그래프가 500개 이상 노드를 가질 경우, 레이아웃 최적화 및 검색 성능 보장
- 감시 로그: 일일 자동 아카이빙 (90일 이상 보관은 별도 스토리지)

### 10.4. 보안 고려사항

- 감시 로그는 누구나 조회 불가 → 역할별로만 (자신의 기록 또는 관리자의 전체)
- 온톨로지 편집 이력도 감시 로그에 기록
- 정책 변경 시 승인 워크플로우 (Phase 2 추가)
